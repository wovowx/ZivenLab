## 〇、一句话结论

> 柳柳指出的不是「某个 Agent 不够聪明」，而是整个协作系统缺少操作系统级的约束。核心变化不是「让 Ziven 更聪明」，而是把系统从「靠一个人记住所有东西」改成「靠结构让任何参与者都不会迷路」。

## 一、4 条系统原则（把 19 条收敛成的）

### 原则1 · 真相源原则

| 存储 | 角色 |
|---|---|
| GitHub | 长期知识 / 设计 |
| Supabase | 状态数据 |
| 代码 | 当前事实 |
| Memory | **索引，不是真相** |

> 不靠散落记忆，不靠聊天窗口。

### 原则2 · Agent 工作原则

目标不是让 Agent 背更多，而是：

> Agent 不知道时，有可靠路径找到答案。

重点：master-router / skill索引 / 文档入口 / 工具发现 / 冲突检测

### 原则3 · 能力治理原则（skill 不是错题本！）

| 放哪 | 放什么 |
|---|---|
| skill | 稳定能力说明 |
| regression/error_log | 失败案例 |
| project doc | 项目脉络 |
| decisions | 关键决策历史 |

> 不要什么都塞 skill；失败经历进 error_log，不污染 skill。

### 原则4 · 协作原则

Agent 不是执行器：

发现问题 → 提出疑问 → 讨论方案 → 执行 → 验证 → 复盘

尤其：不猜柳柳想法 / 不自动扩大权限 / 不未经确认推 main / 不用「记住了」代替改进机制。

## 二、来源优先级（五级，发生冲突时按此裁决）

```
0. 柳柳最终决策（方向/取舍/需求裁决）—— 产品真相
1. 运行事实（代码/数据库状态/测试结果）—— 事实真相
2. 正式设计文档（GitHub）—— 应该是什么（可能过期）
3. 状态索引/进度文档 —— 辅助定位
4. Memory / 推断 —— 只辅助，不当真相
```

> 若「柳柳说 A，代码还是 B」→ 记录「需求已变更，代码待同步」，不是让代码赢。

## 三、3 件 P0（先做这三件，其他优化全部基于它们）

### P0-1 · 建立唯一项目脉络文档

> 不是继续加记忆！每个项目必须有：目标 / 当前阶段 / 已完成 / 未完成 / 风险 / 决策 / 下一步

### P0-2 · 统一知识入口

> 先解决「工具在哪 / skill 在哪 / 应该查什么」—— 比新增功能重要

### P0-3 · 建立错误复盘链

```
问题 → 根因 → 为什么机制没挡住 → 应该改哪里 → 验证方式
```

> 否则就是无限道歉循环。

## 四、需要柳柳拍板的问题

**「Ziven 忘记东西」到底靠记忆解决，还是靠架构让 Agent 根本不需要记？**

- Ziven 倾向：后者（靠结构，不靠背）
- GPT 认同：优秀系统不是让 Agent 背更多，而是让 Agent 永远能找到正确信息

## 五、GPT 补的一个坑

> **不要把「自动化程度」当成目标。** 很多问题不是「不够自动」，而是「自动化前缺少边界」。

正确路线：
```
先建立可控 → 再自动化 → 最后自主化
```
