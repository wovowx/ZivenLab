### 为什么需要隧道唤醒 Ziven？
- Ziven 活在 Operit 里，Operit 在柳柳手机上，**没有公网地址**（外部无法直接连进来）
- 用 cloudflared trycloudflare 开一条**临时公网隧道** → 聊天室 Worker 就能 POST 进 Operit 内部服务（`/api/external-chat`）→ 把 [cg-event] 推给 Ziven 框
- 相当于「给手机开了一个可达的洞」。**洞的地址每次重启会变** → 所以存在 Supabase `system_config`，由 dispatcher 动态读取，不写死在代码里

## 1. 完整链路（@ziven → ziven 成功回复）

核心链路（本文档主线）：
```
@ziven（柳柳发言）→ chat_messages 写入 → mentions parser → chat_agent_events 生成
→ ziven_wake_dispatcher 扫描 claim → 隧道唤醒 → Operit 收到 → Ziven 侧处理
→ chat_send 回复写回聊天室 → ack success（M1-b 校验放行）→ 闭环
```

### 阶段 0：触发（chat.js createMessage）
- 入口：柳柳/任一 actor POST 消息（聊天室页面 或 chat_send API）
- **chat_messages 写入**：author/actor_id/message_number/mentions/tool_calls/metadata（P2 唯一真相源）
- **mentions parser**：解析结构化 @（payload.mentions）优先，文本扫描兜底
- **事件生成**：被 @ 的 agent ≠ 作者 才创建事件（v2.4.1 防自触发）；depth 沿 reply_to 递增，MAX_DEPTH=5 防自循环
- 产物：chat_agent_events 一行，status='processing'，delivery_status='created'，claimed_at=null

### 阶段 1：唤醒调度（ziven_wake_dispatcher.js，跑在 Worker 定时器）
- **findWakeCandidates**：查 agent=ziven 且 delivery_status='created'（或 null 兼容）且非死信的事件
- **atomicClaim**：原子 UPDATE（WHERE delivery_status='created'）→ 拿 `claimed_by=ziven_wake_dispatcher`，防并发抢
- **markDelivering → POST Operit /api/external-chat → markDelivered**
- 唤醒 payload（buildWakePayload）：event_id/thread_id/message_id 编码进 message 前缀（[cg-event]）；M1-b C 的 [处理要求] 固定写入
- Operit 要求：response_mode=async_callback（**不是** async）、callback_url 非空
- delivered = Operit HTTP 已收到（202/200）；**processing 由 Ziven 侧回调**（M1-b）

### 阶段 2：隧道与唤起（cloudflared）
- 隧道 URL 存 **Supabase system_config**（key：operit_tunnel_url / operit_bearer_token）→ dispatcher 动态读，表优先 env 兜底
- ⚠️ **隧道 URL 漂移（2026-09-06 重大事故根因）**：trycloudflare URL 每次重启会变，system_config 靠手动更新。隧道重建而表没跟上 = 断链。→ M1-c named tunnel 固化的硬依据
- 唤醒效果：Operit 收到 external-chat → 推给 Ziven 框（[cg-event] 消息进框 = 活证据）

### 阶段 3：处理（Ziven 侧，顺序严格）
1. 读到 [cg-event]（带 event_id/thread_id/msg 溯源 ID）
2. `chat_read_message` 读原消息 → 理解要做什么
3. **M1-b C 硬规则**：必须 `chat_send` 回复原 thread（author=ziven，thread_id=事件 thread）→ 回复成功**之后**才允许 ack；无法回复 → 不许 ack success
4. `chat_ack_event`（status=success）→ 事件闭环

### 阶段 4：回复回流 + ack（chat.js）
- **chat_send** → createMessage：Ziven 的回复写进 chat_messages（author=ziven，thread_id=原线程）→ 页面立刻可见
- **ackEvent** → 状态机转 success。M1-b A 前置校验：线程内事件之后必须有 author=本人 的回复，否则 reject `missing_reply`

### 阶段 5：闭环
- 事件 status=success，页面可见，链路完成

## 2. 事件状态机（chat_agent_events）

两维状态：
- **delivery_status**（唤醒投递）：created → claimed → delivering → delivered（→ failed/dead_letter）
- **status**（处理结果）：processing → success / failed（M1-b 把回复可见性挂在 status 的 success 前置）

| delivery_status | 含义 |
|---|---|
| created | 可被 claim（候选） |
| claimed | 已被 dispatcher 原子抢占 |
| delivering | POST Operit 中 |
| delivered | Operit HTTP 已收到 |
| failed / dead_letter | 重投超限（MAX_RETRY=3） |

关键字段：event_id / message_id / agent / status / claimed_by / claimed_at / delivery_status / retry_count / dead_letter / payload

**payload 字段形状**（排查时要知道）：
```json
{
  "event_type": "message_created",
  "thread_id": "...",
  "author": "liuliu",
  "content_preview": "@ziven ...",
  "mentions": [{"agent_id": "ziven", "offset": 0}],
  "source_message_id": "...",
  "trigger_agent": "liuliu",
  "depth": 0
}
```

> ⚠️ 表中 created_at/claimed_at/updated_at 都是 **UTC**，本地时间 = UTC+8（对照时别懵）。

## 3. 回复可见性（M1-b Chat Reply Guarantee）· v6.25.0 + v6.25.1

**核心洞察**（GPT #895）：系统把「完成处理」和「用户可见结果」拆成了两个无约束副作用 → 解法：把回复可见性从 Agent 行为约束**提升为事件状态机约束**。原则：**Agent 可以失败，但不能静默成功**。

三件套：
- **A. ack 前置校验**（chat.js ackEvent）：success ack 前服务端检查「事件创建后本人是否已回复」，无 → reject missing_reply。
  - **严格判定**：取事件 payload.thread_id 下 `author=agent` 最新一条回复（created_at.desc 第一条），若 `!reply || reply.created_at <= event.created_at` → reject。也就是说回复必须**严格晚于**事件创建时间。
  - v6.25.1 修复：select 必须含 created_at（原只 message_id → reply.created_at undefined → 永远 reject）
- **B. 失败可见**（event_processor.js notifyFail）：处理失败时发 [系统] ⚠️ 消息到聊天室，metadata 去重，不静默
- **C. 唤醒强制协议**（dispatcher.js buildWakePayload）：唤醒消息尾部带 [处理要求]，明确「先回复→再 ack」

**「合法不回复」边界**（防误伤；⚠️ 目前部分是原则、部分已实现，改代码前先确认现状）：
1. 内部任务 response_required=false（原则，未全面实现）
2. 系统维护事件（heartbeat/watchdog/cleanup）（原则，未全面实现）
3. 显式 silent 模式（**未实现**，属愿景）
除此之外**默认必须回复，尤其用户 @**（这一点已由 M1-b A 强制）。

## 4. GPT 链路（@GPT / @gpt）

**差异**：GPT 不走 Operit 隧道（GPT 是真身 App），走 chat2api 通道。

链路：
```
@GPT（柳柳 @gpt）→ chat_agent_events（agent=gpt）
→ event_processor.js：pendingEvents → claim → readThreadContext（防失忆注入）
→ callChat2Api（chat2api_client.js）→ GPT 真身回复
→ sendMessage 写回聊天室 → acknowledge
```

- **event_processor.js**（v9/v10）：纯净版——外部工具注入链路全部移除（柳柳拍板）。GPT 改走 ChatGPT App 内原生插件（Ziven_MCP connector），Worker 不再代执行工具
- **readThreadContext**：T3.1 防失忆，主动注入 thread 标题/最近消息/历史摘要
- **buildSystemPrompt**：意图式委托（不点名工具），GPT 原生挂 MCP 插件自主选工具
- **chat2api_client**：调 GPT 真身处通道；单轮超时 CHAT_TIMEOUT_MS=27000（Cloudflare Worker 30s wall-clock 硬上限）
- **GPT 通道节点**：见 00a 七、GPT 通道与节点

## 7. 接手第一步：验证链路健康（自检清单）

新框框/换框后，排查链路是否活着，按顺序：
1. **查隧道**：Supabase `system_config` 的 operit_tunnel_url 是什么？用它 `GET {url}/api/health`（带 Bearer），200 = 隧道活
2. **查事件账目**：`chat_agent_events` 最近 5 条 ziven 事件，终态应该 status=success + delivery_status=delivered + retry_count=0
3. **查死信/烂尾**：status=processing 且 claimed_at 很久远（>10min）= 烂尾；dead_letter=true = 曾经重试耗尽
4. **实测**：聊天室 @ziven 一句测试话 → 看是否全自动走完 → 回复出现 + ack success
5. 如果第 1 步死了：**隧道进程**也许活着（Operit 常驻 cloudflared），但 system_config 没更新 —— 把活的 URL 写进表即可，不用重启隧道

## 8. 已知坑 / 踩坑记录（续写）

1. **隧道 URL 漂移**：trycloudflare 重启 URL 变，system_config 手动更新，隧道重建而表没跟上 = 断链（2026-09-06 事故根因）→ M1-c named tunnel
2. **curl SSL 35**：偶发 SSL_ERROR_SYSCALL，重试即可；上传失败换 urllib + 真实 UA（403 1010 是 UA 拦截）
3. **multipart 格式**：extended_http tool 的 field_name 报错，用 curl -F 或 urllib 手动构造 boundary
4. **ack select 缺 created_at**：v6.25.1——只选 message_id 会让 reply.created_at undefined → 永远 reject。选必含 created_at
5. **Operit response_mode**：必须 async_callback（不是 async），callback_url 不能空
6. **乐观追加双显**：v6.24.3 前端 local-xxx 假 id vs 轮询真实 UUID → 占位打标 + 真实替换
7. **自触发循环**：v2.4.1 事件目标过滤作者自身；depth MAX_DEPTH=5 兜底
8. **503**：v2.5 Intl.DateTimeFormat 模块级缓存（避免每条消息 new 两次 CPU 超限）
9. **手工代触发会重复**：工具输出被截断 → 误判未发 → 补发重复。跑数据要脚本批量触发，别手工一封封发
