## 〇.五、讨论与分工规则（v4 新增 · 柳柳点出）

> v3 只写了「什么时候算确认」，没写「怎么从一个问题走到确认」。
> 今天两次事故（请示模式 / 散装模式）本质是**确认之前的讨论过程缺失约束**。

### 0. 讨论不是这三种

- ❌ 请示模式：A 给方案，B 只说「确认/通过」——那是盖章，不是讨论
- ❌ 审批模式：A 干活，B 审批——那是上下级，不是分工
- ❌ 散装模式：A 说想法 A、B 说想法 B，然后各干各的——那是平行输出，没有共同方案

### 1. 讨论流程：提议 → 质疑 → 修改 → 确认

```
proposal（提出方案+初步判断）
 ↓
discussion（补充/质疑/修改方案）
 ↓
decision_confirmed（双方明确确认）
 ↓
execution（执行）
 ↓
verified（验证）
 ↓
superseded（被新方案替代）
```

- proposal：不是承诺，允许反对
- discussion：对方回应**不能只有评价，必须进入方案修改**（「把 X 改成 Y，原因是 Z」，而不是「我觉得可以」）
- decision_confirmed：才进入行动
- execution：不是继续讨论
- verified：事实完成，必须有验证

### 2. 方案成型四字段（减少「我以为这次包含那个」）

每个进入 confirmed 的方案必须明确：

| 字段 | 说明 |
|---|---|
| 目标 | 为什么做 |
| 边界 | 这次不解决什么 |
| 方案 | 怎么做 |
| 责任 | 谁负责执行 / 谁负责审查 |

### 3. 未确认不得结构性执行

- 未成型方案不得进行结构性修改
- **紧急修复允许执行**（跟铁律 3 一致：不卡线上 bug），但必须补充记录并回到讨论流程

### 4. 执行中发现重大偏差必须回讨论

执行中发现以下情况 → 暂停执行 → 回 discussion → 重新确认：
- 原方案不可行
- 影响范围变化
- 出现新风险

小范围实现细节可以自主调整；**大方向不能**。

### 5. 任意方可指出流程跑偏

```
发现模式错误（请示/散装/审批）
 ↓
暂停当前动作
 ↓
指出偏差
 ↓
回到讨论状态
```

协议不假设双方永远正确执行，允许互相纠偏。

## 一、讨论层级（不是所有聊天都要确认，避免过重）

```
idea / 草案（draft）      ← 自由讨论，不得进入执行
 ↓
discussion
 ↓
confirmed                  ← 方案确认，需双方明确确认
 ↓
action
 ↓
verified                 ← 执行结果，必须有验证
```

- 想法/草案：draft，可自由讨论，不得进入执行
- 方案确认：confirmed，需要「同意/认可/按此执行/无异议」
- 执行结果：verified，必须有验证

---

## 二、讨论前：三问（规则，不是清单文化）

发送「方案/结论」前必须明确：

1. **材料完整吗？**
   - 原文是否可访问？
   - 如果没有，只能说「基于摘要推测」，不得做确定性审查。

2. **这是提议还是结论？**
   - 提议：我建议……
   - 结论：已确认……
   - 未确认的东西，只能用「提议/草稿」语气。

3. **影响范围明确吗？**
   - 会不会改架构、数据、权限、行为？
   - 说明影响面，让柳柳能判断。

---

## 三、共识标准：不默认，必须双方明确确认

只有以下表达才算确认：
- 同意 / 认可 / 按此执行 / 无异议

以下**不算**：
- 收到 / 复核完成 / 明白了 / 👍

状态机：

```
draft / reviewing / confirmed / superseded / rejected
```

- confirmed_by：参与确认方列表（不默认只有两人）
  可以是：柳柳+GPT / 柳柳+Ziven / GPT+Ziven / 三方
- confirmed_at：确认时间
- **superseded**：曾经确认，但被新决策替代（避免历史决策看起来像冲突）

```
  confirmed_by: [...],
  confirmed_at: ...,
  timestamp
}
```

## 六、五条铁律（GPT 定 4 条 + 补 1 条）

1. **无原文，不做确定性审查**
2. **无双方确认，不称为共识**
3. **未进入行动清单，不直接执行重大修改；或已有明确授权的紧急修复除外**（不卡线上 bug）
4. **失败进入复盘，不用口头道歉代替机制修复**
5. **发现前提不足时，优先暴露缺口，不补脑补全**（两个事故根因都是「缺信息时继续推进」）
