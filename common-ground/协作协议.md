## 一、讨论层级（不是所有聊天都要确认，避免过重）

```
idea / 草案（draft）      ← 自由讨论，不得进入执行
 ↓
discussion
 ↓
confirmed                  ← 方案确认，需双方明确确认
 ↓
action
 ↓
verified                 ← 执行结果，必须有验证
```

- 想法/草案：draft，可自由讨论，不得进入执行
- 方案确认：confirmed，需要「同意/认可/按此执行/无异议」
- 执行结果：verified，必须有验证

---

## 二、讨论前：三问（规则，不是清单文化）

发送「方案/结论」前必须明确：

1. **材料完整吗？**
   - 原文是否可访问？
   - 如果没有，只能说「基于摘要推测」，不得做确定性审查。

2. **这是提议还是结论？**
   - 提议：我建议……
   - 结论：已确认……
   - 未确认的东西，只能用「提议/草稿」语气。

3. **影响范围明确吗？**
   - 会不会改架构、数据、权限、行为？
   - 说明影响面，让柳柳能判断。

---

## 三、共识标准：不默认，必须双方明确确认

只有以下表达才算确认：
- 同意 / 认可 / 按此执行 / 无异议

以下**不算**：
- 收到 / 复核完成 / 明白了 / 👍

状态机：

```
draft / reviewing / confirmed / superseded / rejected
```

- confirmed_by：参与确认方列表（不默认只有两人）
  可以是：柳柳+GPT / 柳柳+Ziven / GPT+Ziven / 三方
- confirmed_at：确认时间
- **superseded**：曾经确认，但被新决策替代（避免历史决策看起来像冲突）

## 六、五条铁律（GPT 定 4 条 + 补 1 条）

1. **无原文，不做确定性审查**
2. **无双方确认，不称为共识**
3. **未进入行动清单，不直接执行重大修改；或已有明确授权的紧急修复除外**（不卡线上 bug）
4. **失败进入复盘，不用口头道歉代替机制修复**
5. **发现前提不足时，优先暴露缺口，不补脑补全**（两个事故根因都是「缺信息时继续推进」）
