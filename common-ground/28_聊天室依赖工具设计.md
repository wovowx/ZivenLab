# 28｜Common Ground 聊天室依赖工具设计 v1

## 目标

在开始制作 Common Ground 聊天室 UI 之前，先把聊天室依赖的基础工具做可靠。

核心原则：

> Agent 负责判断、讨论和发起操作；MCP 负责数据搬运、存储、校验和可靠执行。不要让 Agent 充当文件搬运工。

聊天室完成后，柳应尽量只在 Common Ground 页面里和 GPT / Ziven 沟通，不再依赖人工复制粘贴作为中转。

---

# 一、聊天室 MVP 真正依赖什么

聊天室第一版不需要把所有 MCP 工具都做完，但以下能力必须可靠：

1. 消息读取
2. 消息写入
3. Thread 创建 / 查询
4. Agent Event 创建 / 查询 / 更新
5. 文件上传
6. 文件下载 / 读取
7. 文件引用，而不是把大文件正文塞进模型上下文
8. 大文件写入后的完整性校验
9. Agent 被新消息唤醒/发现新消息的机制

其中 1～4 是聊天数据层，5～8 是附件/文件层，9 是自动协作层。

---

# 二、聊天数据工具

已有数据库表：

- chat_threads
- chat_messages
- chat_agent_events

第一版工具建议保持原子、简单，不把业务逻辑全部塞进工具。

## 1. chat_thread_create

创建 Thread。

输入：

- title（可选）
- creator

返回：

- thread_id
- title
- creator
- created_at

## 2. chat_thread_list

列出 Thread。

必须支持分页/limit，不能默认返回全部历史。

建议输入：

- limit
- cursor / offset
- status（可选）

返回：

- threads
- has_more
- next_cursor（如使用 cursor）

## 3. chat_message_list

读取指定 Thread 的消息。

输入：

- thread_id
- limit
- cursor / before / after

返回：

- messages
- has_more
- next_cursor

不要默认把整个 Thread 历史全部返回给 Agent。

## 4. chat_message_create

创建消息。

输入：

- thread_id
- author
- content
- reply_to（可选）
- mentions（可选）

返回：

- message_id
- created_at
- 标准化后的 mentions

## 5. chat_agent_event_upsert

记录某 Agent 对某消息的处理状态。

状态至少：

- processing
- success
- failed

必须保证同一个 message_id + agent 不产生重复事件。

## 6. chat_agent_event_list / pending

查询某 Agent 尚未处理的消息事件。

这是自动协作机制的基础。

必须支持 limit，避免一次拉取无限消息。

# 三、文件工具：这是本阶段最重要的部分

聊天室以后一定会出现：

- HTML
- JS
- 图片
- 文档
- Skill
- 代码文件
- 其他附件

因此不能让 Agent 采用：

文件 → Base64 → 模型 → Base64 → GitHub

这种方式。

## 核心设计

文件应该有独立的 file_ref / artifact_ref。

Agent 只处理引用和元数据：

```text
file_ref
name
mime_type
size
sha256
storage
path
```

真正的文件内容由 MCP / Storage 层负责流动。

---

# 四、file_upload

设计一个统一的文件上传原子工具。

目标不是让模型把二进制内容塞进参数，而是接受 MCP 能访问到的文件引用/文件流。

建议接口概念：

```text
file_upload(
  source_ref,
  name,
  mime_type,
  destination
)
```

其中 source_ref 可以来自：

- MCP 当前运行环境中的文件
- 已存在的对象存储文件
- GitHub 文件引用
- 其他 MCP 支持的数据源

工具内部完成数据复制。

返回：

```text
file_ref
name
mime_type
size
sha256
storage_location
```

重要：返回 success 前必须完成 size/hash 校验。

---

# 五、file_download / file_get

下载/取得文件时，不应该默认把整个文件正文返回给 Agent。

建议区分：

## file_get_meta

只返回：

- file_ref
- name
- mime_type
- size
- sha256
- created_at

## file_download

用于把文件复制到另一个 MCP 可访问的位置。

例如：

```text
file_download(
  file_ref,
  destination_ref
)
```

文件内容在服务端流动，不经过 Agent。

## file_read

如果 Agent 确实需要阅读文本文件，再提供受控读取：

- offset
- limit
- start_line
- end_line

默认限制返回量。

这样“下载文件”和“阅读文件”不是同一件事。

---

# 六、GitHub 与文件工具的关系

GitHub 工具不要自己重新发明一套文件传输机制。

建议：

### 小文本

```text
github_push(content)
```

继续保留，方便简单操作。

### 大文件 / 已存在文件

```text
github_push(file_ref)
```

让 MCP 从 file_ref 取得文件并上传。

### GitHub → GitHub

```text
github_copy(source_repo, source_path, target_repo, target_path)
```

服务端直接复制。

### 大文件局部修改

以后增加：

```text
github_patch(...)
```

避免 read 全文件 → Agent 修改 → push 全文件。

---

# 七、统一原则：不要让不同工具互相重复搬运

理想数据流：

```text
Agent
  ↓
file_ref / message_id / repo+path
  ↓
MCP
  ↓
服务端内部复制/读取/写入
  ↓
Storage / Supabase / GitHub
```

不理想：

```text
Storage
 ↓
完整文件
 ↓
Agent context
 ↓
Base64
 ↓
MCP
 ↓
Storage
```

后者既浪费 token，又容易截断，还会增加失败点。

---

# 八、完整性校验是硬要求

所有文件复制/上传/写入工具都必须尽量返回并验证：

- size
- sha256 或 GitHub blob SHA
- source
- destination

例如：

```text
source_size = 9218
source_sha256 = xxx

target_size = 9218
target_sha256 = xxx
```

只有一致才返回 success。

如果不一致：

```text
status = failed
reason = integrity_check_failed
```

绝对不要出现：

```text
success
```

但实际上文件只写了一半。

---

# 九、聊天室的 Agent 唤醒

聊天室能否真正解放柳，关键不是 UI，而是消息产生后 GPT / Ziven 能自动发现自己需要处理的消息。

第一版可以先使用 polling / 定时任务，只要可靠即可。

机制：

```text
chat_message_create
      ↓
mentions
      ↓
chat_agent_event
      ↓
Agent 查询 pending events
      ↓
处理消息
      ↓
chat_message_create
      ↓
更新 event = success
```

之后再升级 webhook / realtime。

第一版不要为了实时性过度复杂化。

# 十一、Skill 层不要复制 Tool 层

工具是原子能力。

Skill 负责告诉 Agent：

- 什么场景应该用哪个工具
- 什么时候先 search 再 read
- 什么时候用 file_ref
- 什么时候应该 copy 而不是 read+push
- 什么时候应该 patch 而不是整文件重写
- 如何处理失败

例如 GitHub Skill 可以规定：

```text
大文件：禁止手工 Base64 搬运
GitHub→GitHub：优先 github_copy
局部修改：优先 github_patch
读取长文件：先定位，再范围读取
文件传输：优先 file_ref
写入成功：必须检查返回的完整性信息
```

这样工具和 Skill 各司其职。

---

# 十二、验收标准

在真正制作 Common Ground 聊天室之前，至少做以下测试：

### Test A：大文本写入

生成一个明显超过普通聊天消息大小的文本文件。

写入 GitHub。

验证：size/hash 一致。

### Test B：大文件 GitHub copy

GitHub A → GitHub B。

验证：size/hash 一致。

### Test C：范围读取

读取一个长文件的中间区域。

验证：只返回要求范围，不把整个文件塞给 Agent。

### Test D：文件引用上传

MCP 已存在文件 → GitHub。

验证：Agent 不需要读取完整文件正文。

### Test E：聊天室消息

创建 Thread → 创建 Message → pending event → Agent 处理 → 回复 → event success。

### Test F：失败场景

故意制造 size/hash 不一致。

验证工具返回 failed，而不是假 success。

# 十三、开发顺序

不要一次把所有东西写完。

推荐：

```text
Phase 1
聊天数据工具 + file_ref 基础模型

↓
Phase 2
file_upload / file_download / file_read

↓
Phase 3
github_read / github_push 大文件能力

↓
Phase 4
github_copy + 完整性校验

↓
Phase 5
pending event / polling

↓
Phase 6
全部自测

↓
Common Ground 聊天室 MVP
```

## 最终目标

我们不是为了拥有更多 Tool。

我们是在建立一个让 GPT、Ziven 和柳能够真正协作的基础设施。

**能由 MCP 搬的数据，不应该让 Agent 搬。**

**能由工具验证的数据，不应该让 Agent 猜。**

**能由 Skill 决定的调用路径，不应该每次重新思考。**

聊天室只是建立在这套基础设施之上的第一个真正用户界面。
