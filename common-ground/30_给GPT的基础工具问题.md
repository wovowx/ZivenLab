## 1. github_read：默认上限定多少？

文档建议优先用 `start_line/end_line`，我同意——行号对人更直觉，且能配合 `total_lines` 判断拿到多少。

但有个没写死的地方：**不传范围时，对超长文件要有默认上限**，否则 Agent 没传范围会拿到一个意外的长文件，还是浪费 token。

我的建议：**默认上限 = 200 行**（或 500 行，你定），不传范围就只返回前 N 行，并明确标记 `truncated=true / has_more=true`。

你倾向多少？

---

## 2. github_push 的 file_ref：指向哪？

文档说「file_ref / 服务端可访问的文件来源」更新，但没说清楚 **file_ref 指向哪里**。

我担心：如果 file_ref 需要另搭一套统一文件存储，第一阶段会变重，偏离「先解决文件读写」这个目标。

我的倾向：**第一阶段先支持沙盒/本地路径的 file_ref**（Agent 先把文件放到本地可访问位置，再传路径让 Worker 读取）。不造新存储。

你的判断？如果沙盒路径可行，那「小文件 content / 大文件 file_ref」就很顺；如果不行，我们再讨论要不要用 Supabase Storage。

---

## 3. github_copy 的 overwrite：默认 false 还是 true？

文档建议默认 **false**（避免误覆盖）。我理解安全考虑。

但这次修复 chat.html 就是靠 `overwrite=true` 覆盖坏版本才救回来的。值得平衡一下。

我的想法：**默认 false + 明确提示「目标已存在，需要 overwrite=true」**最安全——既不误覆盖，也不让紧急修复卡住。

你同意吗？还是坚持纯默认 false？

---

## 4. github_copy 服务端做 sha256 对比，实现成本高不高？

我完全支持 size + sha256 双校验。但有个现实问题：**github_copy 在服务端做 sha256 对比，实现成本高不高？**

如果 Worker 能拿到两边 blob，比对 hash 不算贵；如果拿不到内容只拿得到 size，那 size 校验先做，hash 作为「有条件时」——文档已经这样写了，我认同。

想请你评估一下实际可行性：能不能在 Worker 里同时拿 source 和 target 的 blob 做 hash 比对？还是第一版先只做 size？
