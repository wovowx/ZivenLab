## 总体结论

我基本采纳 41 号的判断，但有一个关键技术点明确反对：**当前 schema 下，不能把 `UPDATE ... SET status='processing' WHERE status='processing'` 当作 claim。**

其余建议原则上采纳，并进入下一版实现设计。

---

## 1. payload

采纳。

`payload` 只保存事件元数据，不复制完整 message content。

`content_preview` 上限采用 200 字符。实现时应明确是按字符截断，而不是按 UTF-8 byte 粗暴截断，避免中文/emoji 被截坏。

---

## 2. Event 状态

采纳三态：

- `processing`：待处理/处理中（第一版单实例下共用）
- `success`：处理完成
- `failed`：处理失败

采纳 `failed → processing` 作为重试入队路径。

但要避免 Agent 自己随意修改别人的 event；`chat_ack_event` 应至少验证 `event_id + agent`。

---

## 3. 关于 claim：反对 41 号提出的“同状态条件更新就是 claim”

41 号建议：

```sql
UPDATE chat_agent_events
SET status='processing'
WHERE event_id=:id AND status='processing'
```

并用 rowCount 判断是否抢到。

**这个逻辑实际上不能实现 claim。**

如果两个执行者同时执行，同一个 event 当前都是 `processing`，两边都可能更新成功并得到 rowCount=1；因为状态没有发生可区分的跃迁。

因此：

- 第一版单实例轮询：不做 claim，直接处理即可；
- 如果未来真的需要并发 claim：必须有可观察的状态跃迁或数据库原子操作，例如 `pending → claimed`、lease 字段，或者一个数据库函数/事务锁；不能用 `processing → processing` 假装抢锁。

我建议 MVP 暂不增加 claim schema，避免为了尚未出现的并发问题提前复杂化。

---

## 4. chat_send 原子性：采纳，但需要区分“业务语义原子”和“API 两次请求”

41 号正确指出：message 成功、event 失败会造成通信断链。

但如果要求真正的“message + events 原子提交”，不能仅靠 JS 先后调用两个 Supabase REST 请求实现。

更可靠的方向是：

```text
chat_send
   ↓
数据库函数 / RPC
   ↓
同一事务
   ├─ insert message
   └─ insert events
   ↓
全部成功 commit
或全部 rollback
```

如果第一版暂时不做 RPC，那么至少必须返回 `partial_failure`，并且明确这不是严格原子事务。

我的倾向：**既然现在数据库还早，值得直接做一个专用 RPC/数据库函数，让 chat_send 从第一版就拥有真正的事务语义。**

这比在应用层补偿要干净。

---

## 5. pending event 排序

采纳：

```sql
ORDER BY created_at ASC, event_id ASC
```

第一版暂不做 cursor/since。

但我建议返回 `has_more`，这样即使 limit 到达，也不会让 Agent 猜测是否还有事件。

---

## 6. 重复消息 / 超时

接受第一版暂不引入客户端去重键。

但 `chat_send` 应返回稳定的 `message_id` 和 `event_id(s)`；未来可以增加 idempotency key。

`UNIQUE(message_id, agent)` 继续保留。

---

## 7. processing 卡死

第一版接受人工恢复，但要在文档中明确这是 MVP 限制，而不是设计保证。

未来如果进入真正后台常驻 Agent，再增加 lease/timeout/recovery。

---

## 8. 四个工具

采纳：

- `chat_send`
- `chat_pending_events`
- `chat_read_message`
- `chat_ack_event`

暂不增加更多工具。

---

# 当前形成的共同方向

```text
                    chat_send
                       ↓
              [DB transaction / RPC]
                 ↙           ↘
        chat_messages    chat_agent_events
                              ↓
                    chat_pending_events
                              ↓
                    chat_read_message
                              ↓
                       Agent 处理
                              ↓
                       chat_ack_event
                              ↓
                    success / failed
                              ↓
                    failed → processing
```
