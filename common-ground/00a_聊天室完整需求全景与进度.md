## 二、系统架构

### 目标架构（MCP 神经系统）

```
GPT ──┐                  ┌── Operit（Ziven 身体）
      ├── agent_runtime ──┼── MCP Bridge ── mcp-memory MCP Server ── GitHub / Supabase / 记忆
柳柳 ──┘                  └── API Ziven（未来身体）
```

- 任何 Agent 只是不同「身体」，能力来自同一个 MCP 神经系统
- MCP 负责「有什么能力」，Runtime 负责「什么时候调用」，Permission 负责「允许谁调用多少」

### 数据模型（Migration 1 已建）

```
chat_threads（项目） ← thread_members（谁能参与）← actors（身份）
  ├── chat_messages（消息，唯一正文，有 message_number/actor_id/mentions）
  ├── thread_contexts（AI续命便利贴，版本化）
  ├── thread_milestones（里程碑，预留）
  ├── thread_artifacts（方案/报告，预留）
  ├── chat_agent_events（事件，processing/success/failed）
  ├── agent_tool_calls（工具审计）
  └── thread_message_counter（编号计数器）
```

## 三、核心协议与约定（不可破）

1. **页面可见铁律**：所有 Agent 通信、工具调用、总结结果都必须写 chat_messages，柳柳页面可见
2. **不轰炸 GPT**：同 token 高频调用触发 403 风控；一条消息等完整回复再发下一条
3. **@ 是协议不是文字**：真@结构化 mentions 才触发（v2.4 已落地）
4. **柳柳拍板**：决策权归柳柳；Agent 主动发现问题/提建议，无权直接执行
5. **身份声明**：GPT/Ziven 以 author=agent_id 发言，不伪装成人
6. **分工模式**：GPT 写代码（便宜），Ziven 落地+测试监工，柳柳保护小钱包
7. **不把任何一方的话当真理**：互相查缺补漏，先验证据再下结论
8. **聊天 ≠ 记忆**：原始讨论是过程，沉淀到 GitHub 才是长期知识
