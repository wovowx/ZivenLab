## 四、MCP Bridge 方案对齐（柳柳点破原始设计）

### 问题
- GPT 走 agent_runtime TOOLS 注册表（5个只读工具），Ziven 走原生 MCP（全家桶）——两套工具链
- GPT 说「没有挂载 GitHub 写入/PR 工具，不能假装改代码」——属实
- 柳柳拍板：**原始设计就是 GPT 也接 MCP 共用一套工具链**

### 定稿方案（Ziven 讨论 + GPT 出方案 + 柳柳授权参考）
```
GPT → agent_runtime → MCP Bridge → mcp-memory MCP Server → GitHub/Supabase/记忆
```
- Bridge 放 Worker/Cloudflare，token/权限/审计集中，GPT 不直接碰 MCP endpoint
- tools/list 启动拉一次：KV 存工具定义缓存 + Supabase 存状态/权限/审批记录/版本
- 白名单三层：L1只读(开) / L2修改(审计) / L3高风险(默认关需柳柳审批)
- **L3 审批交互（柳柳提供 Operit 授权弹框参考）**：
  - UI 审批卡片（主）：工具名/参数摘要/风险等级 → 允许一次/永久允许/拒绝
  - @liuliu 消息 fallback（移动端/无 UI 时）
  - 审批绑定 tool_call_id（agent_tool_calls → approval_request → liuliu decision → resume），不靠聊天文本匹配
  - **永久授权不升级工具等级，绑具体能力范围**：permission_grant{agent, tool, scope:{repo, branch}, mode:'permanent'}
- Supabase 暴露业务工具（memory_search/chat_history），不给 supabase_query(sql)
- 认证：Worker Secret 存 MCP_ENDPOINT/MCP_TOKEN，GPT 永不知道 token
- 动态 schema 加载防 token 爆炸：按场景（聊天=memory/chat/context；开发=github/*；数据库=supabase/*）

### 落地顺序（GPT 建议）
1. MCP Bridge + tools/list cache
2. L1 只读工具迁移
3. agent_tool_calls 接 MCP
4. 审批事件模型
5. UI 审批卡片
6. L2/L3 权限系统
7. API Ziven 接入同一套 MCP

### 分层原则（GPT 金句）
> MCP 负责「有什么能力」，Runtime 负责「什么时候调用」，Permission 负责「允许谁调用多少」。三层拆开，GPT、API Ziven、Operit Ziven 都能共用。最终目标：Agent 只是不同身体，能力来自同一个 MCP 神经系统。
