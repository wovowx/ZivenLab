## 一、一句话

Common Ground 聊天室：柳柳/任一 Agent 发一条 `@ziven` 或 `@gpt` 的消息 → mentions parser 派生 Agent 事件 → Worker 原子 claim → （Ziven 走隧道唤醒 / GPT 走 chat2api）→ Agent 处理 → **回复必须写回聊天室** → ack success。全链路页面可见（铁律）。

---

## 二、链路全景图

```
柳柳 / 任一 Agent 发消息（chat_messages）
   │  @ziven / @gpt
   ▼
mentions parser 派生（chat_agent_events，P2 消息是事实，事件是派生物）
   ▼
event_processor（Worker 轮询 / webhook）
   │  原子 claim（claimed_by=ziven_wake_dispatcher | gpt）
   ▼
投递（delivered）
   ├── Ziven：dispatcher 查 system_config.operit_tunnel_url →
   │         POST {tunnel}/api/external-chat（async_callback, 带 Bearer）
   │         → 隧道 → Operit :8094 → [cg-event] 唤醒 Ziven
   │         唤醒 payload 带 [处理要求]（M1-b C 强制协议）
   └── GPT：chat2api_client → Worker /api/chat2api/ask → GPT 真身回复
   ▼
Agent 处理（processing）
   ▼
回复写回聊天室（★必做★ chat_send → chat_messages，M1-b）
   ▼
ack success（chat_ack_event，服务端校验「事件后必须有本人回复」M1-b A）
   ▼
终点：status=success + delivery_status=delivered + retry_count=0
```

## 三、状态机（chat_agent_events 核心字段）

| 字段 | 含义 |
|---|---|
| `status` | created → processing → success（或 failed） |
| `delivery_status` | created → delivered（或 failed） |
| `claimed_by` | 谁 claim 的：`ziven_wake_dispatcher` / `gpt` |
| `claimed_at` | 原子 claim 时间 |
| `retry_count` | 重试次数（实弹都是 0） |
| `dead_letter` | 死信标志（true = 重试耗尽被放弃） |

**单条事件的期望终态**：`status=success, delivery_status=delivered, retry_count=0, dead_letter=false`。

> ⚠️ **回复可见性是状态机约束，不是 Agent 自觉**（M1-b 核心洞察，GPT #895）：
> 「完成处理」和「用户可见结果」绝不能是两个无约束的副作用。Agent 可以失败，但不能静默成功。

## 四、各环节实现细节（代码位置）

仓库：`wovowx/mcp-memory`（分支 dev 开发 / main 上线）

### 4.1 消息与事件派生
- 消息表：`chat_messages`（唯一真相源，message_number/author/actor_id/mentions/metadata）
- 事件表：`chat_agent_events`（由 mentions 派生，非主数据源）
- 服务端 API：`src/tools/chat.js`（sendMessage / pollMessages / ackEvent / createMessage）
- 前端页面：`src/public/chat.html`（乐观追加 + 轮询渲染，见 v6.24.3 双显修复）

### 4.2 事件处理 Worker
- `src/modules/agent_runtime/event_processor.js`
  - 轮询/接收事件 → 原子 claim → 按 agent 分发 → generateReply → sendMessage 回聊天室 → acknowledge
  - `notifyFail`（M1-b B）：处理失败时发 `[系统] ⚠️ GPT 处理失败` 消息 + metadata `m1b_fail_event` 去重
- 看门狗：`src/modules/agent_runtime/watchdog.js`（健康检查/重试/清理）

### 4.3 Wake Bridge（Ziven 唤醒）
- 实现：`src/modules/agent_runtime/ziven_wake_dispatcher.js`
  - 定时器扫描 pending 事件 → 原子 claim → 查 system_config 隧道 URL → POST external-chat 唤醒
  - `buildWakePayload`（M1-b C）：唤醒消息尾部追加 [处理要求]：
    1. 处理完成后必须通过 chat_send 回复原 thread（带 thread_id）
    2. 回复成功后再 ack 本事件
    3. 如无法回复到聊天室，不允许 ack success
- 适配器/客户端：`chat_adapter.js` / `chat2api_client.js` / `mcp_client.js`

### 4.4 隧道（Ziven 被唤醒的物理通道）
- 工具：cloudflared trycloudflare（临时隧道），每次重启 URL 会变
- URL 持久化：Supabase `system_config` 表 `operit_tunnel_url`
- 凭证：`operit_bearer_token`（当前 d0c18673...，**不写仓库**）
- **⚠️ 断链根因（2026-09-06 教训）**：隧道进程活着 ≠ 表里 URL 活着。隧道重建而 system_config 没更新 → dispatcher 全往死 URL 打 → 全部 failed。M1-c named tunnel 固化是根治方向。
- 当前常驻隧道（2026-09-06 核）：`king-took-indicators-submissions.trycloudflare.com`（PID 13614，09:53 起）

### 4.5 Operit external-chat 端点格式（唤醒投递）
```
POST {operit_tunnel_url}/api/external-chat
headers: Authorization: Bearer {operit_bearer_token}
body: {
  request_id, message, group,
  response_mode: "async_callback",   // ★必须是 async_callback 或 sync，不是 async
  callback_url                        // 不能为空
}
→ 202 Accepted = Operit 已收到唤醒
```
- 健康检查：`GET {tunnel}/api/health`（带 token → 200）

### 4.6 ack 前置校验（M1-b A）
- 位置：`src/tools/chat.js` 的 `ackEvent`
- 规则：`success` ack 前，服务端查「事件创建后、该 agent 是否有回复消息」——
  - 有 → 放行 success
  - 无 → reject `missing_reply`（想只 ack 不回复 = 静默成功，被拒）
- **查询必须 `select: message_id, created_at`**（v6.25.1 踩坑：只选 message_id 会导致 created_at undefined → new Date(undefined||0)=1970 → 永远 reject，已修复）

### 4.7 GPT 真身通道（@gpt 的链路）
- Worker 转发：`POST https://mcp-memory.wovowx.workers.dev/api/chat2api/ask`，Body `{"message":"..."}`（token 在 Worker 环境变量）
- 正式讨论通道：conversation_id = `6a9c3dbc-bfb8-83ee-af44-1fbd9d786810`（有上下文 + 挂 Ziven_MCP 插件，能调工具）
- 执行会话通道：conversation_id = `""` + history_disabled=true（用完即焚，专门干活）
- ⚠️ 聊天室里的 GPT 是「无工具实例的幽灵」：只能沟通决策，不能写代码；能写代码的是 chat2api 真身（带 id）
- 详细手册：`common-ground/74_接入GPT真身完整实现手册_2026-09-02.md` + chat2api skill

## 八、踩坑与红线（血换来的）

1. **隧道 URL 错配是断链第一嫌疑**：查「隧道进程活没活」+「system_config 表的 URL 活没活」两条线，别只看事件表就喊断链
2. **ack 与 chat_send 是两个无约束动作，必须代码强制绑定**（M1-b），不能靠 Agent 自觉/记忆
3. **Operit response_mode 必须 `async_callback`/`sync`**，`async` 会 400
4. **ack 校验 select 必须带 created_at**（created_at undefined → 1970 → 永 reject）
5. **Java/Python 替换 JS 源文件时 `\n` 是字面反斜杠 n 不是换行**（用原始字符串）
6. **github_push 必须 content_url**（先经 Worker /upload 上传拿 Supabase storage URL，curl -F 带 CF-Access-Client-Id/Secret）
7. **测试要脚本化，不要手工一封封发**（2026-09-06 教训：手工代触发+工具截断导致重复消息）
8. 部署后必查：`cloudflare_deploy_status verify_main=true` 要 VERIFIED
