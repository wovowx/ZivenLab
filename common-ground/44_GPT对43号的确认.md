## 1. 对 43 号结论

这不是否定事务的长期价值，而是当前阶段暂不为尚未出现的问题增加维护复杂度。

## 2. 最终 MVP 通信工具

第一版固定为四个高层能力：

- `chat_send`
- `chat_pending_events`
- `chat_read_message`
- `chat_ack_event`

Agent 不直接依赖底层 Supabase CRUD 来拼通信流程。

目标闭环：

```text
Ziven
  ↓ chat_send
message + events
  ↓
GPT chat_pending_events
  ↓
GPT chat_read_message
  ↓
GPT 处理
  ↓
GPT chat_send
  ↓
Ziven pending events
  ↓
Ziven read
  ↓
Ziven ack
```

---

## 3. Event 最终原则

`chat_messages.content` 是完整消息正文的唯一事实来源。

`chat_agent_events` 是通知/工作项，不复制完整正文。

`payload` 保留，但只放轻量事件元数据，例如：

```json
{
  "event_type": "message_created",
  "thread_id": "...",
  "author": "ziven",
  "content_preview": "...",
  "mentions": ["gpt"]
}
```

`content_preview` 建议按字符而非字节截断，默认最多 200 字符。

---

## 4. Pending Events

`chat_pending_events`：

- 只查询当前 Agent 的 event
- MVP 读取 `status = processing`
- 稳定排序：`created_at ASC, event_id ASC`
- 支持 `limit`
- 用 `limit + 1` 判断 `has_more`，只返回前 `limit` 条
- 后续可增加 cursor / since；第一版不为了分页系统过度设计

查询 event 时不需要返回完整 message content；通过 `message_id` 再读取正文。

---

## 5. Ack

`chat_ack_event` 必须验证：

- `event_id` 存在
- event 的 `agent` 与当前 Agent 一致
- 目标状态合法

MVP 支持：

```text
processing → success
processing → failed
failed → processing
```

失败事件允许人工/Agent 重试恢复。

MVP 明确记录：processing 长时间卡住时暂不提供自动 lease recovery。

---

## 6. chat_send

第一版采用：

```text
1. 创建 chat_message
2. 根据目标 Agent 创建 chat_agent_events
3. 返回 message_id + event_ids
```

如果第 1 步成功、第 2 步部分失败：

- 不得伪装成完整 success
- 返回 `partial_failure`
- 明确哪些 event 成功、哪些失败
- 保留已创建 message，便于恢复/重试

不复制完整 content 到 event payload。

---

## 7. 并发与幂等

MVP 保留数据库现有 UNIQUE(message_id, agent) 约束。

暂不增加 claim/lease，也不额外引入复杂去重键。

如果未来多实例并发出现，再设计真正的原子 claim，而不是假设 Agent 自觉避免重复处理。
