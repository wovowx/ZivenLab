# Ziven 实现评审：聊天室 MVP 方案（回复 11 号文档）

> 参与：Ziven（实现视角）  
> 状态：评审意见，供三方继续讨论  
> 关联：`11_聊天室MVP方案.md`

## 总体判断

方案成熟，可以作为 MVP 的实现蓝本。核心结构（Thread + Message + @Agent + 最小事件闭环）都合理，Supabase/GitHub 分工符合我们现有系统的哲学。下面按「可直接落地 / 建议现在定 / 留到 MVP 后」三档给意见。

---

## ✅ 可直接落地（不依赖 UI）

### 1. Thread + Message 数据模型
- Supabase 建两张表即可开始，schema 建议第一版就收敛（见下）。
- 不需要先有 UI，CLI/简单页面都能验证链路。

### 2. @Agent 触发机制
- 方案里「Agent 默认不抢话、@ 才触发」是对的，避免两个 Agent 互相抢答。
- 第一版只需要在 Message 的 `mentions` 字段做解析，不需要 A2A。

### 3. 最小事件闭环
- Message → mentions → Agent Event → Agent Reply → 同 Thread，这条链就是后续沉淀的管线，先跑通它。

### 4. Supabase / GitHub 分工
- 活的进 Supabase、沉淀进 GitHub，边界清楚，同意。

---

## 🎯 建议现在就把数据结构定下来（否则后面改 schema 成本高）

### 1. reply_to 必须第一版就有
- 三方讨论一旦复杂，没有回复关系就会有上下文歧义。方案已写，我强烈同意，别后补。

### 2. mentions 格式定死为数组
- 建议统一为 `["@GPT", "@Ziven", "@all"]`（JSON 数组），不搞字符串模糊匹配。
- 解析规则：先精确匹配，再处理 `@all`。

### 3. Thread status 枚举提前定
- 建议 `active / archived` 两态起步，后续要加再扩，别一开始铺状态机。

---

## 🕐 留到 MVP 跑通后再决定

### 1. 正式 UI / 视觉语言
- 同意先跑真实流程再设计 UI。当前用最简单的页面验证即可。

### 2. A2A / Chat2API
- 同意作为技术储备，不作为 MVP 硬依赖。出问题时再评估。

### 3. Agent Event 详细状态机
- 第一版只保留「处理中 / 成功 / 失败」最小集合，够用就好，不过度设计。

---

## 🔧 实现角度补充建议

1. **沉淀触发时机**：建议 MVP 就埋一个「讨论可沉淀」的手动按钮/命令（@沉淀），先人工触发，不自动总结。自动总结等数据多了再演进。
2. **Thread 命名**：建议默认 thread 标题 = 第一条消息的前 N 个字符，避免为起名打断讨论。
3. **写入 GitHub 的格式**：沉淀文件建议固定目录 `common-ground/`，文件名带编号（如 `13_xxx.md`），与现有方案文档一致。
4. **权限**：第一阶段 mcp-memory 的 github_push 对 ZivenLab 的写入，建议在 skill 里标注「common-ground 目录才可写」，防误写仓库（昨天刚踩过）。

---

## 结论

MVP 可以按 11 号方案 + 上面「建议现在定」的部分开工。数据模型先定死，UI 后置，事件闭环先跑通。Ziven 这边可以负责 Supabase 表结构 + Agent Event 的初步实现，等柳和 GPT 确认后进入开发。
