# Common Ground：基础工具第一阶段详细设计 v1

> 状态：讨论稿，暂不实现
> 目标：先解决大文件读取、写入、服务端复制和完整性验证，再进入聊天室开发。

## 0. 为什么先做这一层

Common Ground 的聊天室依赖可靠的数据与文件工具。当前已经出现过一个典型问题：HTML 页面能被部署，但 GitHub 上的文件实际只有部分内容，导致 JavaScript 截断、页面全部按钮失效。

因此第一阶段不做聊天室 UI，也不扩展大量新工具。先把基础文件操作做成“可靠的原子能力”，避免 Agent 自己搬运大文件、Base64、切片、拼接。

核心原则：

> 能在 MCP / Worker / GitHub API 内部完成的数据流转，就不要让 Agent 把正文搬进上下文。

## 1. 第一阶段范围

本阶段只处理四项：

1. github_read：分段 / 范围读取；
2. github_push：可靠的大文件写入；
3. github_copy：服务端文件复制；
4. 写入与复制后的完整性校验。

暂不实现 github_patch、github_search、github_diff、聊天室 Event 唤醒等后续能力。

## 2. github_read v2

### 目标

让 Agent 能读取长文件的局部内容，而不是每次把整个文件返回到上下文。

### 建议参数

保留现有：

- repo
- branch
- path

新增一种明确的范围模式，优先采用：

- start_line：起始行，1-based；
- end_line：结束行，包含该行。

也可以提供 offset / limit，但第一版不必同时暴露两套语义，避免 Agent 选择困难。

### 返回信息

除正文外，返回：

- total_lines
- start_line
- end_line
- returned_lines
- has_more
- file_size_bytes
- encoding（固定 UTF-8 时也可明确返回）

这样 Agent 能知道“我拿到的是全部文件还是一个片段”。

### 行为规则

- 不传范围：兼容旧行为，但对超长文件应避免无限返回；建议明确默认上限。
- 传 start_line/end_line：只返回指定范围。
- 超过文件末尾：安全截到最后一行，不报无意义错误。
- 参数非法：明确返回参数错误。
- 返回结果必须标明是否截断，不能让“截断结果”看起来像完整文件。

### 未来扩展

以后可以加入 search/context 模式，但不属于第一阶段。

## 3. github_push v2

### 当前问题

现有接口把完整正文放进 content/content_base64。小文件可以，但长文件会迫使 Agent 搬运正文，且可能发生参数长度、编码或中间处理导致的截断。

### 目标

支持两条清晰路径：

A. 小文件：直接 content。

B. 大文件：通过 file_ref / 服务端可访问的文件来源写入，正文不经过 Agent 上下文。

第一版可以先实现 file_ref；如果当前运行环境已有统一文件存储，则优先复用，不重复造存储系统。

### 建议接口概念

- path
- repo
- branch
- message
- content：小文本兼容入口
- file_ref：大文件入口，与 content 二选一

可选：expected_size、expected_sha256，用于调用方主动提供校验值。

### 必须的服务端流程

file_ref → Worker 读取文件 → GitHub API 创建/更新 blob → 获取 GitHub 最终文件信息 → 校验 → 返回 success。

Agent 不负责：

- Base64 编码；
- 分块；
- 拼接；
- 重试搬运；
- 判断是否完整。

### 完整性校验

成功返回不能只表示“API 请求成功”。至少应验证最终文件 size；如果实现成本允许，同时验证 SHA-256。

建议返回：

- success
- repo
- branch
- path
- commit_sha
- file_size_bytes
- sha256（若可得）
- verified: true/false

如果写入请求成功但校验失败，必须返回 failed，而不是 success。

## 4. github_copy v1

### 目标

解决 GitHub → GitHub 的大文件搬运，让内容完全在服务端流转。

典型：

ZivenLab/dev/path/file
→ github_copy
→ mcp-memory/main/src/public/file

### 建议参数

- source_repo
- source_branch
- source_path
- target_repo
- target_branch
- target_path
- message
- overwrite（默认建议 false，避免误覆盖）

### 服务端流程

1. 读取 source 文件的 GitHub blob / contents 信息；
2. 取得源文件内容或 blob；
3. 写入 target；
4. 获取 target 最终文件信息；
5. 比较 source 与 target 的 size；
6. 有条件时比较内容 SHA / SHA-256；
7. 全部通过后才返回 success。

重点：文件正文不能经过 Agent。

### 安全行为

- 默认不覆盖已有目标文件，除非明确 overwrite=true；
- source 与 target 缺失时给出清晰错误；
- source=target 时拒绝无意义复制；
- 目标分支/仓库必须明确，避免误写 main。

## 5. 统一完整性规则

所有“文件写入类”工具都遵循：

请求成功 ≠ 文件成功。

只有满足：

`GitHub API 操作成功 + 最终文件存在 + size 校验通过`

才允许返回 verified=true / success。

如果能取得内容哈希，再增加哈希校验。

对于文本文件，UTF-8 编码必须保持稳定；不要在 MCP 内部无必要地做字符串转码。

## 6. 文件流转原则

以后优先级：

### 最优

GitHub → MCP → GitHub

或

File storage → MCP → GitHub

### 可接受

小文件 → Agent content → MCP → GitHub

### 禁止作为常规方案

大文件 → Agent read → Base64 → Agent → push → 再拼接

Base64 可以作为底层 API 实现细节，但不能成为 Agent 的工作流。

## 7. Token 与成本目标

第一阶段不是单纯追求“能用”，而是减少无效 token：

- 长文件读取：按需读取；
- 文件复制：不经过 Agent；
- 大文件写入：不经过 Agent 正文；
- 局部修改：暂不解决，留给 github_patch；
- 工具结果：只返回必要元数据，不把刚写入的整文件重新返回。

## 8. 验收测试

### A：read 小文件

完整读取仍然正常。

### B：read 大文件

指定 1-50 行，只返回对应范围，并正确返回 total_lines / has_more。

### C：push 小文件

content 写入后读取，内容完全一致。

### D：push 大文件

file_ref 写入后，源文件与 GitHub 文件 size 一致；有哈希时哈希一致。

### E：copy 大文件

从 ZivenLab/dev 复制到 mcp-memory/dev 或 main 测试位置；比较 source/target size 与 hash。

### F：故意制造失败

模拟/检测截断或校验不一致时，工具必须返回 failed，不能伪装成 success。

### G：中文与 UTF-8

使用包含中文、emoji、换行的测试文件，确认写入前后内容一致。

## 9. 实现顺序

1. 先改 github_read；
2. 加测试；
3. 改 github_push 的大文件入口与校验；
4. 加测试；
5. 检查并完善 github_copy 的校验；
6. 做端到端大文件测试；
7. 只有全部通过后，才进入 Common Ground 聊天室开发。

## 10. 暂不做的事情

本阶段明确不做：

- github_patch；
- github_search；
- github_diff；
- github_deploy；
- Agent Event 实时唤醒；
- 聊天室 UI；
- 大型 batch 工具。

这些能力后续根据真实使用场景再做。

## 11. Definition of Done

第一阶段完成的标准不是“新增了几个参数”，而是：

> Agent 可以可靠地读写和复制比上下文适合处理的大文件，而且无需自己 Base64、切片、拼接；工具能验证最终结果，发现截断时明确失败。

达到这个标准后，我们再开始聊天室。
