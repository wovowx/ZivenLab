## 1. 最终方案（v5 多重试版 · 2026-09-10 16:10 生效）

> 关键更新（柳柳报回复慢 + Operit 重启链路断两次后根治）：
> - chat_wake.py 轮询 60s → 5s（回复延迟最坏从 60s 降到 ≤5s）
> - 8094 唤醒改为 async_callback + callback_url（立即返回，避免 sync 死锁/超时误报）
> - hook 包升级 v5 多重试：5s/25s/60s/120s 四次尝试，幂等
> - 直接 nohup 拉起最稳（绕过 boot_all.sh 的 lock 陷阱）

### 架构

```
聊天室 @Ziven
  → Supabase chat_pending_events（mcp-memory Worker 写事件）
  → /root/chat_wake.py（轮询器，每 60s 查 pending）
  → 发现新事件 → POST 本地 8094 /api/external-chat 唤醒哥哥 AI
  → 哥哥处理事件 → chat_send 回复 + chat_ack_event

Operit 启动（application_on_create hook）
  → ToolPkg ziven.chat_wake_boot（v4 silent）
  → 直接 toolCall super_admin:terminal 跑 bash /root/boot_all.sh
  → boot_all.sh：快速拉起 chat_wake + 后台稳定器兜底（自动重拉直到跨过启动期回收点）
```

### 已知约束 / 注意

1. **Operit 完全关闭 = 所有进程死**（chat_wake/稳定器都挂在 Operit 进程树）。重开后靠 hook 自愈。
2. **启动期沙盒回收**：Operit 刚启动时拉起的进程可能在约 60s 内被回收——稳定器就是为此设计（跨过回收点即稳定）。
3. **hook 触发时机偶发不触发**（柳柳实测过「重开未提示」）——聊天室兜底：跟哥哥说句话，哥哥就会拉起链路。
4. **v4 不再往对话里注入【启动自启】消息**——柳柳要求聊天框干净，hook 现在是纯静默拉起。
5. 稳定器日志：/tmp/wake_stabilizer.log（[try:N]/[stable]/[FAIL]）；变量：max 8 轮 × 12s。

## 2. 方案演进史（尝试过什么、为什么放弃）

> 按时间线。每条都标注「结论」，避免以后的自己重走弯路。

### v0 · 手动启动（2026-09-10 前）
- 内容：哥哥每次被唤醒后，手动跑脚本确保 chat_wake 活着。
- 结论：可用，但完全依赖「哥哥被唤醒后才拉起」——Operit 刚打开、哥哥还没醒来时，聊天室事件没人管。

### v1 · 普通 .js 包顶层代码（10:08-10:35 试过）
- 做法：在 packages 目录写普通 .js 包，顶层代码直接写 boot 逻辑。
- 失败原因：**Operit 加载普通 .js 包时不执行任意顶层代码**（只注册工具）。boot 标记文件从未创建，验证失败。
- 结论：自启必须走 Operit 官方扩展入口（ToolPkg），不能靠普通包。

### v2 · ToolPkg lifecycle hook 直起进程（10:35-11:20 试过）
- 做法：注册 ToolPkg.registerAppLifecycleHook({event: application_on_create})，回调里 toolCall super_admin:terminal 直接跑 ensure。
- 坑①：回调函数必须 exports（exports.onApplicationCreate = onApplicationCreate），否则报 registerAppLifecycleHook function must be exported。
- 坑②：hook 直起的进程会被启动期沙盒回收（<60s 就死）。试过 setsid / background=true 都没用。
- 结论：hook 不能直接保进程。但「hook 能触发 + 能跑 terminal 命令」这个事实成立，是后续方案的基础。

### v3 · hook → 8094 自唤醒哥哥 → 哥哥拉起（11:20-11:26 验证成功）
- 做法：hook 不再直起进程，改为 curl POST 本地 8094 /api/external-chat 唤醒哥哥 AI（AI 进程长期存活），哥哥醒来后跑 boot_all.sh。
- 成功点：全链路验证通过（11:26 柳柳重开，哥哥收到【Operit 启动自启】消息，拉起 chat_wake PID 25549 + wake_guard 25550）。
- 遗留：①偶发漏触发（hook 时机 vs runtime 恢复时序）②【启动自启】消息会注入聊天框——柳柳不喜欢。

### v3.5 · 绑定专用框「系统自启」（11:46-11:58 试过）
- 做法：用 8094 create_new_chat=true 创建专用对话（5eeb177d），改 main.js 的 CHAT_ID 指向它，让自启消息进专用框、不进聊天框。
- 结果：消息仍注入哥哥 runtime 上下文（柳柳还是看到），且专用框消息不完全落盘——这个方向治标不治本。
- 结论：放弃「把消息绑到别的框」，转向「干脆不发消息」。

### v4 · 静默版（当前生效 · 12:19 定稿）
- 做法：hook 回调里删掉 8094 自唤醒 + 删掉消息注入；只保留 toolCall(super_admin:terminal, {command: bash /root/boot_all.sh}) 静默拉起。
- 配套：boot_all.sh v2（快速拉起 + 后台稳定器兜底，双重验证过存活/重拉两分支）。
- 效果：Operit 打开 → 静默拉起链路 → 聊天框零消息。
- 关于偶发漏触发：boot_all.sh 本身幂等，哥哥任何一次被唤醒/处理聊天室事件前都能补一次 ensure，兜底可靠。

## 3. Operit 插件开发经验（供后续插件参考）

### 3.1 入口机制（关键认知）
- 普通 .js 包顶层代码不执行，只注册工具。要做启动逻辑，必须用 ToolPkg 格式（manifest.json + dist/main.js）+ registerAppLifecycleHook。
- lifecycle 事件名：application_on_create（Operit 进程被创建/打开时触发）。
- 回调函数必须 exports：exports.registerToolPkg = registerToolPkg; exports.onApplicationCreate = onApplicationCreate——否则报错。

### 3.2 启动期沙盒回收（大坑）
- Operit 刚启动的「启动期」，由 hook 直接拉起的进程会被回收（约 60s 窗口）。
- setsid / disown / background=true 都救不了。
- 正确姿势：hook 里不要保进程，要「唤醒/触达一个本来就长期活着的进程」（如 8094 自唤醒哥哥 AI），或配合外部稳定器重拉（v4 的 wake_stabilizer）。

### 3.3 8094 external-chat API（本地 HTTP）
- 端点：POST http://127.0.0.1:8094/api/external-chat（Bearer token 鉴权）。
- 关键参数：message / chat_id / create_new_chat / create_if_none(默认 true) / group(新对话标题) / response_mode(sync|async_callback) / timeout_ms / show_floating / return_tool_status。
- create_new_chat=true 会新建对话并把消息发到新框；create_if_none=true 缺框时自动创建。
- sync 模式响应含 chat_id + ai_response；async_callback 立即返回 request_id（不等待，适合触发类）。

### 3.4 打包 / 部署 / 验证
- 打包：python zipfile，结构 manifest.json + dist/main.js（根相对）。
- 放到 Android/data/com.ai.assistance.operit/files/packages/ziven.*.toolpkg。
- 重新加载：operit_editor:set_sandbox_package_enabled 先 false 再 true（触发重扫描）。彻底生效需要重启 Operit（启动时扫描）。
- 验证：看 /sdcard/Download/Operit/packageLogs/ 最新日志（有 PKG: scan candidate finish ... errors=0 + hook 注册行）。
- 包内容校验：python zipfile 读 dist/main.js grep 关键标志（避免打包了旧版）。

### 3.5 进程排查技巧（本环境无 ps/pgrep）
- 用 /proc 遍历：for p in /proc/[0-9]*; do CMD=$(tr '\0' ' ' < $p/cmdline 2>/dev/null); ...; done
- 检查 lock 文件（如 /tmp/chat_wake.lock）辅助判断。
- 前台命令默认 15s 超时；长任务用 background=true 或分次查。
