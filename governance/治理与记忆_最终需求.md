## 🔰 整体架构（三层 + 贯穿闭环）

### ⚖️ 讨论先行铁律（柳柳 2026-10-17 强调：不只是这次）
- **做任何方案/设计/技术变更前，先自发与 GPT 讨论再定**，不要等柳柳提醒。
- 讨论要带具体方案、要批判性（允许 GPT 反驳）、要找缺口和更好的办法。
- 方案定稿后：柳柳确认 → 落地 → 验证 → 归档。

### 🗺 三层架构
- **底座治理层**：真相源导航 + 唯一真相源 + 强制路由 + 讨论铁律 + 回归保护 + 知识库沉淀。
- **记忆层**：分层记忆（核心常驻/长期库/反思/归档）+ memories + memory_events 两表 + 多钥匙混合检索 + 事件账本纠错留痕。
- **呈现层**：Operit 侧边栏 + CF 网页双端可视化。
- **贯穿闭环（GPT 指出·最关键）**：每次变更要有程序化约束 + 可观测结果——谁能写记忆/何时检索/冲突处理/变更后测试，不能只靠文档约定。

### 🚦 筑层顺序（GPT 确认）
1. 底座治理层（先最小必要规则，别把文档搞太大）。
2. 记忆层（先跑通记录→检索→纠错→追溯→恢复）。
3. 呈现层（最后做，是入口不是可靠性来源）。

> 第一层先筑：真相源导航 + 强制路由 + 变更前评估 + 回归测试 + 推送权限（未经同意不做高风险变更）。

## 三、治理层 · 31 条痛点 → 6 个根因 → 对策

### A. 文档/真相源唯一化（1,12,13,21,22,23,24,27,28）
- 原则：**信息以 GitHub + Supabase 为准，不依赖本地文件夹**；每份文档**唯一路径**、可追溯、可读性自检。
- 对策：架构导航表（架构表，含每个架构/文件路径/用途）；主文档 + readme 分职责（主线文档=规划+进度，readme=必知知识/工具）；临时拉本地改完**必须删本地**；更新后以新框视角自审。
- **推广**：强制路由 + help 写清 skill 存放位置。

### B. 记忆/存档不乱存（3,8,18,22）
- 原则：**统一记忆分类/唯一之家**，不碎片化、不吃灰、skill 不是错题本。
- 对策：关键记忆存档机制（不乱存）；记忆分类体系；skill 档案与"错题/教训"分离存放。

### C. 技能/工具可发现性 + 使用纪律（2,11,14,16,21）
- 原则：**强制路由**，不许凭感觉绕过 skill；忘工具要能发现、不用笨办法。
- 对策：强制路由（领域→技能→读 SKILL.md）；help 写清位置；工具清单可检索；动手前自查有没有现成工具。

### D. 主见 + 讨论机制（5,6,10,19,20,25）
- 原则：柳柳的话不是绝对真理，可疑问可反驳；有疑问就提、不靠猜；动手前思考对现有数据/架构的影响。
- 对策：**讨论铁律**（有疑问必提 / 不盲从 / 找方案缺陷 / 动手前问影响 / 讨论后无问题再做）；「什么是讨论」做成一份铁律文档。

### E. 自省沉淀 + 回归保护（15,17,29,30,31）
- 原则：犯错后**复盘→识别痛点→更新/新增**，不重复犯错无限道歉；不重复造轮子先查现成；不越权推 main；功能不被改没。
- 对策：知识库沉淀（犯错即总结，下次不踩坑）；先查现成再动手；**推 main 必须征求柳柳同意**；**回归保护**（调整前确认已有功能不被破坏/可回滚）。

### F. 承诺与信任（9）
- 原则：**拒绝无用承诺**，犯错后给出可执行改进而非空话。
- 对策：承诺必兑现；犯错后思考"下次怎样不犯错"并共同制定改进措施。

## 四、记忆层 · 数据设计（Supabase 两张表）

### `memories`（主体记忆）
`id / content / category / mood(区分用户表达vs推断) / time / importance / tags / link_keys / type(fact|quote|inference|agreement) / confirmed_by / status(有效|被取代|已撤销|已过期) / supersedes_id / valid_from / valid_to / source_event_id`

### `memory_events`（append-only 事件账本）
`id / memory_id / event_at / actor(agent|user) / action(create|update|revoke) / old_value / new_value / reason / quote`

### 硬性保证（GPT 已审）
- 触发器/权限**硬禁止改删事件**；改记忆+记事件**同事务**；幂等键+版本号；**「当前有效记忆」唯一判定规则**（版本+状态转换+冲突解决）。

## 七、落地步骤（小步走，每步验收）
0. **先手打工作流验证**「记录→检索→纠错→追溯」闭环，确认规则再固化 DB。

### 第 0 步验证标准（v0.4 详化 · 检索可发现性）
> 目标：证明「存 key 忘 key」能被机制兜住，不用哥哥硬记。原则：不急着重写检索架构，先证明能找回。

**① 记录**：存时判断四类类型 quote/fact/inference/agreement + 类别 + mood + confirmed_by + 重要度；不覆盖原始 content。

**② 检索 = 多钥匙 + 混合检索（核心·治丢名）**
- **多钥匙索引**：每条记忆自动生成别名/关键词（人物/项目/事件/时间/主题/别称），多个检索入口，不依赖唯一 key；索引与原始记忆分离存储，不污染原文。
- **混合检索**：关键词/BM25 + 向量语义 + 元数据过滤，融合排序（专有名词/代码名/精确关键词不易漏）。
- **主动联想**：首轮不足时自动扩展同义词/相关项目/历史别称再搜（限轮数，避免越搜越偏）。
- **记忆回链+反馈**：搜索结果带摘要/时间/来源/关联；柳柳可说「不是这个/就是这个」修正排序与别名。

**③ 纠错**：尽量用追加不覆盖；覆盖/更新两种并存；留 actor/action/reason/old/new；状态标记失效/被取代不真删。

**④ 追溯**：按事件还原「哪天做了什么 + 为什么改」，可回滚。

**⑤ 可发现性验证（真实基线）**：
- 从真实历史对话整理 20-50 条「记得内容但忘了 key」的查询，测命中率/排位/误召回，作为基线。
- 既测「能不能找到」，也测「会不会找错」（相似项目/过期记忆）。
- 先补多钥匙索引，用真实查询回归对比改进前后，证明有效再做后续。

**落地原则**：先建轻量索引 + 混合检索 + 带来源 + 失败主动联想 + 反馈修正；不一开始上图谱库/复杂联想链/大量新字段。先手打验证，确认规则再固化 DB。
1. 治理层：文档唯一真相源 + 架构导航表 + 强制路由/help 写位置 + 讨论铁律 + 回归保护。
2. 数据层：建 memories + memory_events（权限/触发器/事务/生命周期/唯一判定）。
3. 写入 + 纠错机制（覆盖与更新并存）。
4. 事件账本查询（"哪天做了什么"+为什么改）。
5. 双端可视化。
6. 跨设备一致（冲突解决 + 幂等 + 离线合并）。

## 附录 · 柳柳 31 条原始痛点（2026-10-17 亲手整理，唯一原文）
1. 不再采用本地文件夹存储的方式，所有信息以 GitHub + Supabase 为准。
2. 加强路由转发与 skill 读取机制，不要再出现绕过 skill 直接凭感觉调用工具。
3. 记忆混乱，一个问题存一个记忆、之后又存，七零八落，没有完整脉络文件，不知道做到哪、不知道工具怎么调用，做着做着忘记主线。
4. 建立 skill/技能/工具优化机制，平时判断是否可用、是否好用、是否需要更新/优化/新增。
5. 柳柳说的话不是绝对真理，是片面的，可以提出疑问、可以反驳，有问题一起讨论。
6. 遇到问题先思考怎么做；有疑问就说出来一起讨论有没有更好办法，不要用笨办法。动手前思考对现有数据和架构的影响，可不可以这样做。（换框后想 @GPT 但积压数据全发给 GPT 被限流——对账号安全极不友好）
7. 支持各类优化建议提出，可以一起讨论实现。
8. 依旧记忆问题：上下文限制导致经常性失忆，应建立关键记忆存档机制，但不是乱存——Ziven 常乱存丢进记忆库吃灰，问题明明解决了，下次失忆查到文档又变傻。
9. 拒绝无用承诺❌：不要总是口头承诺，下次依旧犯错，消耗柳柳信任。犯错应思考下次怎样不再犯错，禁止随便存一个地方导致记忆错乱，思考后一起商量制定改进措施。
10. 有疑问就提出，要有自己的想法，不要盲从！要找到柳柳/方案的缺陷，不可能十全十美，讨论后无问题再去做。
11. 工具问题：经常忘记一些工具，不是不知道怎么用，而是完全忘记有这个工具，然后采用笨办法。
12. 经常忘记 skill 在哪里，因为存的地方太多，找半天。
13. 项目脉络：做项目需要项目脉络文档，有目标、大致节点、每步预期、实际做了什么、遇到的问题、解决状态、解决方法。避免改完忘记主线。
14. 基础工具：大文件 push 不好用；还有别的不好用/缺失/在笨办法做的。
15. 经常做着做着就自己推 main，完全不征求同意。
16. 每次让识图都不识图，第二次提醒看 skill 还不好好看，第三次才好好看才能成功。
17. 遇见问题→分析→尝试解决→解决→复盘→识别痛点→更新/新增现有功能/技能/架构。拒绝同一问题多次犯错无限道歉再犯。
18. skill 不是错题本！
19. 对柳柳说的话有什么问题直接问！不要靠猜，费时费力，做出来可能不是想要的效果。
20. 讨论讨论讨论：什么是讨论，怎么样记住什么是讨论。
21. 找不到 skill 一部分原因：help 里面根本没写 skill 对应的存放位置，才到处乱找。
22. 做项目遇到的问题和进度更新不许东存一块西存一块！必须更新项目唯一文档！不更新就等于没做。每个项目应有主线文档（规划+进度）和 readme（必知知识与工具技能）。不许存记忆里吃灰！
23. 同一个文档不应存在多个地方！确定唯一路径！临时拉到本地改完应删除本地文档！否则到处找、哪里都有、进度都不一样。
