### 阶段 2 · 修复已证实的代码—数据依赖断链（独立评估后再实施）
- 已证实的代码—数据依赖断链：`src/utils/search.js` 依赖 `search_history`，但当前 Supabase 表清单中不存在该表。沿 `memory_unified.js` 调用链确认：每次 `action=search` 在返回记忆搜索结果后调用 `recordSearchKeyword`；该函数吞掉所有异常，因此主搜索结果仍可能正常返回，但搜索历史不会可靠记录。`action=suggest` 调用 `getSearchSuggestions`，遇异常返回空数组，联想词会静默退化为空。当前远端 `tests/webhook_idempotency_test.mjs` 已覆盖 `memory(action=suggest)` 的空数组、正常列表、404 JSON 错误对象、500 JSON 错误对象四种响应；但没有直接覆盖 `recordSearchKeyword` 的空白关键词/GET-PATCH-POST 序列与写入失败，也没有明确测试 prefix/limit、网络拒绝和 JSON 解析失败。`scripts/check.mjs` 只做语法与相对 import 检查，不验证这些行为。
- **功能状态补充核验**：Supabase `skills` 注册表中的 `memory` 工具当前 `enabled=true`，`usage_count=388`，最近使用时间为 2026-10-23；其公开 `input_schema` 仍包含 `action=suggest`。这证明统一记忆工具在用、suggest 仍属于公开契约，但没有按 action 统计的调用证据，不能据此断言 suggest 实际常用或已废弃。因此保留兼容性。另静态代码检查发现 `action=suggest` 的空态表达式把标题字符串与列表拼接后才执行 `||`，因此「暂无搜索历史」兜底分支永远不会触发；这是可明确复现于逻辑层的缺陷，需用测试覆盖空结果、合法结果、缺表和 HTTP 非 2xx。早期 GPT 执行环境无法运行该 JS handler，因此当时只登记缺口；之后 Operit 对 usage_count 相关 E1/E2/隔离 Mock 实际执行通过，但**并未覆盖 search_history/suggest 的测试**，这一缺口仍待验证。不得直接建表，也不得静默删掉功能。
- `category.js` 的移动顺序是物理 DELETE 旧记录，再 POST 新 key；两步均不检查 HTTP 状态，也不写 `memory_events`，新建失败时可能出现旧记录已删而新记录未建的部分成功风险。**可达性尚不能确认，且当前证据倾向于未暴露**：`mcp_router.js` 虽有 `handlerMap.category → handleCategoryTool`，但路由的固定前缀白名单仅含 `github_`、`supabase_`、`memory_`，没有 `category_*`；对 Supabase `skills` 表只读精确查询 `move_category`、`recall_by_category`、`category` 均为空。因此不能再声称 `move_category` 可经 MCP 分派；在注册表/工具目录出现可核实的精确入口前，把它视为源码存在但当前未证实可达的旧路径。与此同时，统一 `memory` 工具本身已启用，其公开 `action` 枚举包含 `move`；这是当前可确认的记忆迁移入口。单独的 `memory_move` 别名注册记录不存在，因此它不会出现在 `tools/list`；但当前 Router 对未找到注册 schema 的别名采取兼容放行，`tools/call` 仍可能进入统一 memory handler，并在缺参时返回 `需要 key 和 newCategory`。这是列表/schema 契约不一致，不等于 `move` 功能整体不可用；真实 MCP endpoint 行为仍未验证。
- `memory_unified.js` 的当前控制流与 `category.js` 不同：`putMemory` 更新旧值时会先 POST `memory_events`，并检查事件写入与 memories PATCH 的 HTTP 状态；新建会检查 INSERT 状态，但新建和软删除都没有对应的 `memory_events` 生命周期事件。`forget` 通过检查 HTTP 状态的软删除实现。`rename`/`move` 共用 `relocateMemorySafely`，顺序是**先创建目标（createOnly）→再软删除源→再确认源已不 active**；目标写入失败时保留源，源删除或核验失败时返回部分完成状态，可能留下新旧记录同时 active 供人工核对。该路径仍未写入明确的 rename/move 迁移事件，也未在事件中记录源/目标关系，因此完整生命周期审计闭环仍未实现。相比之下，`category.js` 的 `move_category` 仍是**先对源记录发物理 DELETE→再 POST 目标**，不检查两次请求的 HTTP 状态，也不写 `memory_events`，目标创建失败时存在源记录已删除的风险。上述风险来自静态控制流，尚无证据证明真实数据曾因此丢失；Supabase RLS/约束也尚未核验。
- 最小修复设计应优先统一到单一迁移路径：明确 create/update/soft-delete/rename/move 的事件语义；所有写请求检查 HTTP 状态；多步操作采用可恢复的顺序/补偿策略；对旧数据不做批量修复，先用 mock/fake-fetch 测试覆盖每个失败点。实际实施前仍需柳柳明确授权；在此之前不执行分类移动、不合并代码、不改数据库。

## 五、执行铁律（贯穿所有阶段）
- **先复用，再新增**：新增函数、模块、工具或机制前，先检索现有实现与调用链，避免平行建设。
- **职责清楚，扩展有界**：共享逻辑有明确归属；新能力优先沿已有接口接入。只有真实需求证明有必要时才抽象，不预建万能框架。
- **先查依赖、先备份、先做可逆变更**：核对调用方、动态引用、注册/schema、输入输出契约和兼容路径。
- **每步只改一小批，执行适用的回归验证再继续**：记录真实命令、退出码与结果；静态检查不代替行为测试。
