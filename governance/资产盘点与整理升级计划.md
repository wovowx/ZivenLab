> **先搭好框架，再去整理存量。** 有一个目标分类/判定体系（记忆层设计定稿）之前，不做「逐条归位」——否则等于没有唯一判定就乱搬，正是要治的乱。

### 阶段 2 · 存量职责与依赖整理（当前阶段；只读审计与文档收敛）
- 已证实的代码—数据依赖断链：`src/utils/search.js` 依赖 `search_history`，但当前 Supabase 表清单中不存在该表。沿 `memory_unified.js` 调用链确认：每次 `action=search` 在返回记忆搜索结果后调用 `recordSearchKeyword`；该函数吞掉所有异常，因此主搜索结果仍可能正常返回，但搜索历史不会可靠记录。`action=suggest` 调用 `getSearchSuggestions`，遇异常返回空数组，联想词会静默退化为空。当前 `tests/` 未见针对这两个函数或缺表情景的行为测试；`scripts/check.mjs` 也未覆盖它们。
- **功能状态补充核验**：Supabase `skills` 注册表中的 `memory` 工具当前 `enabled=true`，`usage_count=388`，最近使用时间为 2026-10-23；其公开 `input_schema` 仍包含 `action=suggest`。这证明统一记忆工具在用、suggest 仍属于公开契约，但没有按 action 统计的调用证据，不能据此断言 suggest 实际常用或已废弃。因此保留兼容性。另静态代码检查发现 `action=suggest` 的空态表达式把标题字符串与列表拼接后才执行 `||`，因此「暂无搜索历史」兜底分支永远不会触发；这是可明确复现于逻辑层的缺陷，需用测试覆盖空结果、合法结果、缺表和 HTTP 非 2xx。当前 GPT 侧 Code Runner 返回 `handler type not implemented: js`，本轮无法实际执行 Node 行为测试，所以只登记，不宣称已修复/通过；不得直接建表，也不得静默删掉功能。
- `category.js` 的移动顺序是物理 DELETE 旧记录，再 POST 新 key；两步均不检查 HTTP 状态，也不写 `memory_events`，新建失败时可能出现旧记录已删而新记录未建的部分成功风险。**当前未发现它的有效外部注册入口**：`mcp_router.js` 有 `handlerMap.category → handleCategoryTool`，也在 `isKnownToolName` 中识别 `category_` 前缀；但实际 dispatch 对该前缀没有直连分支，而是落到 `skills` 注册表查找 handler。对 `skills` 的只读精确查询未找到 `move_category`、`recall_by_category` 或 `category` 注册项，因此不能据此认定 `category.js` 已暴露给 MCP；它目前是源码存在、外部可达性未证实的旧路径。与此同时，统一 `memory` 工具已启用，公开 `action` 枚举包含 `move`，这是当前可发现的记忆迁移入口。单独 `memory_move` 别名注册记录不存在，因此 `tools/list` 不会因别名本身展示它；但源码路由对 `memory_` 前缀直接放行并调用 `handleMemoryTool`，缺少注册 schema 时 `getToolSchema` 返回 null、不会执行必填字段校验。故它在源码路由层可能可被直接调用但不可发现，且没有注册 schema 保护；不能再声称它必然因缺 schema 被拒绝。
- `memory_unified.js` 当前实际控制流存在比旧记录更直接的失败风险：`putMemory` 更新旧值时先 POST `memory_events`，再 PATCH `memories`；但这两次 fetch 都没有检查 `resp.ok`。新建记忆的 POST 同样不检查 HTTP 状态，也没有显式写入 create 事件。`deleteMemory` 通过 PATCH 将源记录设为 `status=deleted`、填写 `valid_to`，但不检查 HTTP 状态，也不显式写 revoke/delete 事件。`forget` 调用后即返回“已删除”，不验证软删除是否成功。`rename`/`move` 当前没有 `relocateMemorySafely`：两者都先调用 `deleteMemory(源)`，再调用 `putMemory(目标)`，没有事务、补偿或源/目标状态核验；目标写入失败时源可能已被软删除，且非 2xx 响应可能被当作成功继续执行。`memory_events` 目前只看到 update 路径的显式写入，且该写入本身也未检查状态；rename/move 的来源、目标与原因没有形成明确迁移事件。因此，当前代码并未实现此前文档所述的“目标先创建、源后软删并核验”的安全迁移顺序，完整生命周期审计闭环也未实现。相比之下，`category.js` 的 `move_category` 是**先对源记录发物理 DELETE→再 POST 目标**，同样不检查两次请求的 HTTP 状态，也不写 `memory_events`。此外，`src/tools/data.js` 的 import 路径复用 `putMemory`，并在函数返回后直接增加 added/updated 计数；由于 `putMemory` 不检查写请求 HTTP 状态，导入结果也可能在底层写入失败时报告成功计数。以上是静态控制流风险，不代表已证实真实数据丢失；Supabase RLS/约束及触发器行为仍需独立证据核验。
- 最小修复设计应优先统一到单一迁移路径：明确 create/update/soft-delete/rename/move 的事件语义；所有写请求检查 HTTP 状态；多步操作采用可恢复的顺序/补偿策略；对旧数据不做批量修复，先用 mock/fake-fetch 测试覆盖每个失败点。实际实施前仍需柳柳明确授权；在此之前不执行分类移动、不合并代码、不改数据库。

### 阶段 2（续）· 工具注册、Skill 与共享实现职责核对
- 已确认 `helpers.js` 与 `response.js` 中 `buildErrorResponse` 函数体相同；`index.js` 使用 `response.js`。已抽查当前 `src/` 全部 JS 文件的静态 import 头部，未发现从 `helpers.js` 导入 `buildErrorResponse` 的调用方；但 GPT 侧 Code Runner 无法执行 JS/grep，尚未完成机器级全仓符号搜索或动态导入排查。当前只标记为高置信度冗余候选，不删函数、不合并文件；待可执行搜索和回归验证后再决定最小收敛。
- 已确认 `mcp_router.js` 在工具返回未命中错误前缀的文本时自动调用 `handleIncrementUsage`，而 `increment_usage` 本身被排除在自动计数之外。`memory_move` 的精确注册查询为空，因此 `tools/list` 不会列出该别名；但当前 `mcp_router.js` 对 `memory_` 前缀直接通过 `isKnownToolName`，`dispatchGuard` 只有在取到 schema 且 schema 声明 required 时才检查必填参数。注册缺失时 `getToolSchema` 返回 null，并不会以 `TOOL_SCHEMA_UNAVAILABLE` 拒绝。随后 dispatch 会把 `memory_move` 直接交给 `handleMemoryTool`，而该 handler 的 actionMap 明确映射 `memory_move → move`。因此准确状态是“未注册、目录不可见，但源码路由仍可能直接执行且缺少注册 schema 校验”；这与公开 `memory(action=move)` 契约不同。需继续按具体工具对照前缀门禁、实际 dispatch 分支、注册表/schema 与 `tools/list`，不能把它们当成同一清单。不要把“返回非错误前缀”直接当成业务成功的强验证。
- `memory_unified.js` 与 `category.js` 的重叠须先确认真实注册入口、审计一致性和失败原子性；未完成前不合并。
- 文件/媒体职责只读核对已有结果：`/upload` 与 `ai.js` 共用 `uploadFileToSupabase`，属于复用；`storage.js` 有 `queryFiles` 实现，但 Supabase 注册表的 `query_files`、`delete_file`、`update_file` 均指向 `ai.js`，当前 `handleAITool` 没有这些处理分支，会返回空字符串。该注册—实现断链已记录在差距矩阵；`file-management` 与 `image_upload` Markdown Skill 依赖 `query_files`，前者还依赖 `delete_file`/`update_file`。若通过 mcp-memory Worker 的当前注册路由调用，这些入口会落到 `ai.js` 的空分支；connector 侧是否存在独立实现尚未实测，因此不扩大为所有宿主都失效的结论。本轮不改注册或代码，后续进入处理阶段再定修复范围。继续核对 Markdown Skill 与 JS 工具注册项边界，不能仅凭名称相似就合并。
- 只读核对还发现注册管理的反馈链存在静态风险：`getEnabledSkills` 在 HTTP 非 2xx 时返回空数组，无法区分“查询失败”和“没有启用工具”；`skill_add/update/delete` 未检查底层写操作的布尔结果，可能误报成功；Router 的 usage_count 仅按少数错误前缀判断结果，空串或 `❌` 业务失败可能误计。另有多个 enabled 指南/文本类注册项（如 `architecture`、`github-use-guide`、`master-router`、`读懂柳柳`、`publish-workflow`、`code-runner-guide`、`database-capability-guide`、`需求梳理`、`memory-retrieval-hybrid`）缺少 `handler_config.handler`，按当前 Worker dispatch 会返回 `handler type not implemented`。这些条目可能本来是宿主读取的指南而非可执行工具；先确认设计语义，再决定是否调整暴露面。本轮均已登记在差距矩阵，不修代码、不删注册。另 `knowledge.js` 只返回 Supabase `skills.description`，不读取 `file_path` 指向的 Markdown `SKILL.md`；如 `file-management`、`image_upload` 的数据库描述仅是摘要，完整步骤留在仓库文件。需先明确各宿主如何读取 Markdown Skill，以及数据库描述与文件内容谁是权威，不把摘要视作完整流程。工具 schema 也存在缓存漂移边界：`GITHUB_TOOL_DEFS` 与 `CHAT_TOOL_DEFS` 的同步逻辑只补缺失注册项、不更新已存在项，但 `dispatchGuard` 从注册表读取 schema；后续需按证据明确元数据权威和同步策略，当前不批量更新注册表。
- 只有在调用方、输入输出契约、兼容性和回归覆盖都明确后，才合并重复实现；不为减少文件数量而强行合并。

- README 的目录说明已在 `mcp-memory/dev` 校正。`.github/workflows/pages.yml` 在 `main` push 时把仓库根目录 `.` 整体上传为 Pages artifact；根目录没有 `index.html`，而实际 HTML 位于 `src/public/`。其中 `chat.html` 使用相对同源 `/api/chat/...` 路径，静态 Pages 不会自动转发到 Worker API；`memory-universe.html` 则内嵌硬编码的个人记忆示例，而非实时数据库读取。故当前发布范围不仅包含源码、测试、迁移与跨宿主桥接文件，还存在静态页面功能不匹配及个人内容公开风险。GitHub 官方文档明确 Pages 网站可能对互联网公开，即使仓库本身是 private（取决于计划与站点可见性），因此不能用 README 的“私有仓库”说明推断网站私有。
- 该 workflow 目前也未显式设置 `pages: write` 与 `id-token: write`；GitHub 官方自定义工作流文档将两者列为部署所需最低权限。**目前可核实的是工作流静态配置与文件内容；本工具没有提供 GitHub Pages 设置/Actions 运行历史读取，因此 Pages 站点是否已成功部署、站点访问模式和当前外部可访问内容仍未确认。**
- **`/memory-universe` 路由风险（暂缓处理）**：Cloudflare Worker 的 `src/index.js` 未把该路径纳入前置认证门禁，随后直接 fetch GitHub `main` 上的 `src/public/memory-universe.html` 并返回 HTML；该页面含硬编码个人记忆样例。Cloudflare 部署工具显示 `mcp-memory` 的 main 已于 2026-10-21 `VERIFIED`，且 main 当前源码仍包含此路由；**尚未用外部 HTTP 客户端实测匿名请求是否能访问**。柳柳已明确该页面当前未投入使用、属于半成品，因此本轮不立即修复、不停服务、不部署；将其登记为**正式启用前的阻断验收项**：清理硬编码个人样例、接入合适认证、验证匿名访问被拒绝。若未来确认开始对外使用，再重新评估优先级。未经柳柳同意不改 main、不部署、不停站。
- 结论：Pages 发布范围是高优先级风险项；不要在未确认真实发布目标前把整个仓库当作安全发布目录。最小候选方案是先确认 Pages 是否仍需要；若需要，应建立明确、经过脱敏的发布目录，只放预期网页资产，并核实 API 路由与权限；若不需要，则经授权停用 Pages 工作流。官方依据：GitHub Docs「Creating a GitHub Pages site」及「Using custom workflows with GitHub Pages」。
- 按现有 `scripts/check.mjs`、学习回归测试及需要补充的定向测试建立验证基线；静态检查通过不能冒充端到端验证。
