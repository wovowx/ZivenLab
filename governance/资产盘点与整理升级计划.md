### 阶段 2 · 修复已证实的代码—数据依赖断链（独立评估后再实施）
- 优先级最高的已证实问题之一：`src/utils/search.js` 依赖 `search_history`，但当前 Supabase 表清单中不存在该表，搜索历史/建议功能可能失效。
- 先确认该功能是否仍需要、调用结果和错误降级，再选择最小修复；不得直接建表，也不得静默删掉功能。
- 源码与注册路径已只读核实：`mcp_router.js` 的 `handlerMap` 将 `category` 指向 `handleCategoryTool`，且接受 `category_*` 前缀，因此 `move_category` 可经 MCP 分派触达，不是孤立代码。`category.js` 的移动顺序是物理 DELETE 旧记录，再 POST 新 key；两步均不检查 HTTP 状态，也不写 `memory_events`，新建失败时可能出现旧记录已删而新记录未建的部分成功风险。
- `memory_unified.js` 的当前控制流与 `category.js` 不同：`putMemory` 更新旧值时会先 POST `memory_events`，并检查事件写入与 memories PATCH 的 HTTP 状态；新建会检查 INSERT 状态，但新建和软删除都没有对应的 `memory_events` 生命周期事件。`forget` 通过检查 HTTP 状态的软删除实现。`rename`/`move` 共用 `relocateMemorySafely`，顺序是**先创建目标（createOnly）→再软删除源→再确认源已不 active**；目标写入失败时保留源，源删除或核验失败时返回部分完成状态，可能留下新旧记录同时 active 供人工核对。该路径仍未写入明确的 rename/move 迁移事件，也未在事件中记录源/目标关系，因此完整生命周期审计闭环仍未实现。相比之下，`category.js` 的 `move_category` 仍是**先对源记录发物理 DELETE→再 POST 目标**，不检查两次请求的 HTTP 状态，也不写 `memory_events`，目标创建失败时存在源记录已删除的风险。上述风险来自静态控制流，尚无证据证明真实数据曾因此丢失；Supabase RLS/约束也尚未核验。
- 最小修复设计应优先统一到单一迁移路径：明确 create/update/soft-delete/rename/move 的事件语义；所有写请求检查 HTTP 状态；多步操作采用可恢复的顺序/补偿策略；对旧数据不做批量修复，先用 mock/fake-fetch 测试覆盖每个失败点。实际实施前仍需柳柳明确授权；在此之前不执行分类移动、不合并代码、不改数据库。

### 阶段 3 · 收敛代码职责与工具注册（以复用为先）
