# 现状架构（Current Architecture）

- 文档性质：当前实现事实地图，不是目标蓝图。
- 仓库/分支：wovowx/ZivenLab，dev。
- 核对日期：2026-10-24。
- 用途：让新会话恢复系统真实组成、入口、依赖、已知差距与下一步，避免仅凭聊天记忆重做盘点。
- 铁律：源码存在不等于入口可达；配置存在不等于线上已部署；静态检查不等于行为测试通过；目标设计不等于当前实现。

## 1. 证据等级

| 等级 | 含义 | 表述纪律 |
|---|---|---|
| S：源码确认 | 当前分支的源码、配置或文档 | 只说“源码中存在/配置为……” |
| R：注册/数据确认 | Supabase 注册表、表清单、schema dump | 标明查询结果与统计口径 |
| T：运行时验证 | 真实工具调用、测试输出、HTTP 响应或部署验证 | 写清条件、结果与时间 |

## 3. Worker / MCP 入口与调用关系

1. mcp-memory/src/index.js：Worker HTTP 路由、部分 API、静态页面与定时任务入口。
2. mcp-memory/src/modules/mcp_router.js：MCP initialize、tools/list、tools/call 与工具分派。
3. mcp-memory/src/tools/memory_unified.js：统一记忆读写、检索、导入导出与移动入口；使用 src/utils/search.js 等模块和 Supabase。
4. GitHub 工具当前 Router 实际导入 src/tools/github_v64.js；本次 mcp-memory/dev/src/tools 目录枚举只看到 github_v64.js，未看到 github.js。以当前分支真实目录与 Router import 为准，不沿用旧文件清单。
5. src/modules/、src/utils/包含搜索、响应、技能/存储、执行会话、运行时与 Patch Engine 等模块。模块存在不等于路由可达、注册有效或线上正在使用。
6. `src/skills/` 中的 Markdown Skill 与 Supabase `skills` 注册表不是同一层：前者描述行为/流程，后者承载工具注册与 schema/元数据。须分别检查路由、注册和实际调用证据。

### 当前工具分派关系（源码静态核对，不代表运行时已验证）

| 工具/模块 | `mcp_router.js` 的实际分派方式 | 架构边界 |
|---|---|---|
| `memory_unified.js` | `memory` 与 `memory_*` 在 tools/call 中直接分派 | 前缀可达与 `tools/list` 可发现是两回事；无注册 schema 时 required 参数校验可能跳过 |
| `github_v64.js` | `github_*` 直接分派；可由定义被动补注册 | 当前 Router 导入此实现；当前目录未见 `github.js` |

| `chat_mcp.js` | `CHAT_TOOL_DEFS` 中的精确工具名直接分派，并可同步注册 | 属于 MCP 工具；与 HTTP 聊天入口不同 |
| `ai.js`、`data.js`、`knowledge.js`、`delete_branch.js` | 通常由注册项的 `handler_config.handler` 选择对应 handler | 必须核对精确注册项和配置，不能只看 handlerMap。`knowledge.js` 实际只回传 Supabase `skills.description`，不读取 `file_path` 指向的 Markdown `SKILL.md`；例如 `file-management`、`image_upload` 的数据库描述是简短摘要，而完整流程位于仓库 Markdown 文件。因此“技能文件存在于仓库”“注册表有 file_path”“Worker 调用能返回完整 Skill 内容”是三个不同状态。只读查询发现 `query_files`、`delete_file`、`update_file` 均 enabled 且指向 `ai.js`；当前 dev 已为三者补齐处理分支：`query_files` 复用 `storage.js` 的 `queryFiles`，`update_file` 更新允许字段的文件元数据，`delete_file` 依次查元数据、删 Storage 对象、删元数据并核对删除响应至少返回一行。技能注册管理反馈及文件工具隔离 Mock E1/E2 已由 Operit 在 `wovowx/mcp-memory/dev` SHA `757807dbc596e86a9aab1d3d6e3cea9e9f2caa58` 验证（E1 exit 0；E2 68/68）；E3 真实 MCP endpoint 未执行。`file-management` 与 `image_upload` 两个 Markdown Skill 依赖这些工具，但 connector 侧是否存在独立调用实现仍未运行时核验，因此不据此断言所有宿主同名工具均失效。此为源码+注册表静态判断，ChatGPT connector 的实际调用链尚未运行时核验，不据此断言所有宿主的同名工具都失效。
| `category.js` | handlerMap 中存在，但没有 category 前缀直连分支；fallback 需要注册项 | 当前精确只读查询未找到 `move_category`、`recall_by_category`、`category` 注册项，暂视为源码存在、外部可达性未证实 |
| `cf_proxy`、`increment_usage` | 精确名称有专门 dispatch 分支 | 仍需区分工具注册/目录可见性与实际调用证据 |
| `chat.js`、`chat_webhook.js` | 由 `src/index.js` 的 HTTP 路径分派 | 与 `chat_mcp.js` 不是同一入口；聊天室/唤醒运行链按既定决定保持暂停 |
| `utils/storage.js` | `/upload` HTTP 路由与 `ai.js` 的 data URI 图片预处理共同调用 `uploadFileToSupabase` | 当前看到的是共享实现复用，不应重复造上传逻辑；`ai.js` 的 `query_files` 已复用 `storage.js` 的 `queryFiles`，并有隔离 Mock E1/E2 验收证据（SHA `757807dbc596e86a9aab1d3d6e3cea9e9f2caa58`，E2 68/68）。不再把 `queryFiles` 记为未接入；其他调用方是否存在仍需全仓搜索后再判断。 |

注意：`isKnownToolName` 只决定初始门禁是否放行；最终是否执行还取决于后续 dispatch 分支、注册表记录与 handler 配置。当前 `dispatchGuard` 已实现有限 JSON Schema 子集校验：`required`、`type`、`enum`、`properties` 递归、数组 `items` 递归与数值 `minimum/maximum`；不支持的关键字不作为拒绝理由，缺少 schema 时保持兼容放行。这不是完整 JSON Schema 实现。Operit 在 `wovowx/mcp-memory/dev` SHA `8a92ec12131e81e034fafc339d2ba51ee5f7a359` 实测 E1 exit 0、E2 54/54；后续 SHA `757807d…` 的 E2 68/68 保留此前回归。不能把“前缀被识别”“在 tools/list 中出现”“schema 子集校验通过”“实际 handler 执行成功”当作同一状态。

### 路由与统计限制

- Router 的可达性由前缀识别、tools/call 的实际 dispatch 分支、skills 注册表、handler_config 与 schema 校验共同决定；这些层不能简化成单一“有/无注册”判断。对 `memory_` 前缀，当前源码直接交给 `handleMemoryTool`；若别名没有注册 schema，`tools/list` 不会展示它，且 `getToolSchema` 返回 null 时不会执行 schema required 校验。
- Supabase 注册表中统一 memory 工具为 enabled=true，公开 action schema 包含 suggest 与 move。只读查询未找到独立 `memory_move` 注册项，因此它不会由注册表出现在 `tools/list`；但当前源码 actionMap 将 `memory_move` 映射为 `move`，且 `memory_` 前缀可直接分派。该别名的源码可调用性与目录可发现性不同，缺少独立注册 schema 也意味着必填参数校验可能缺失。
- usage_count 自动计数会参考返回文本是否命中 `err:`、`❌`、`RELEASE_GUARD:`、`DISPATCH_GUARD_REJECT:` 等错误前缀，不等价于严格业务成功判定。当前 dev 已排除空字符串和这些标准化失败结果；usage 计数自身失败不会覆盖原工具响应，相关 Mock 断言包含在 SHA `757807dbc596e86a9aab1d3d6e3cea9e9f2caa58` 的 E2 68/68 中。仍没有按 `memory` action 的真实使用统计；技能管理工具因没有对应普通注册行而不由通用自动计数记录，这是已观察到的统计语义边界。
- `src/utils/skills.js` 的技能注册管理反馈问题已在 dev 最小修复，并由 Operit 实测 E1/E2 验证：查询 HTTP 非 2xx 会抛出可识别异常；add/update/delete 写入要求 `Prefer: return=representation` 返回至少一条记录才报告成功，零行与底层失败均返回可识别 `err:`；非空 `skill_list` 实际返回技能名。证据绑定 SHA `757807dbc596e86a9aab1d3d6e3cea9e9f2caa58`，E1 exit 0、E2 68/68；E3 未执行。**Router 层仍有错误语义缺口：** `isKnownTool()` catch `getCachedSkills()` 的异常后返回 `false`，所以 `tools/call` 前置门禁可能把注册表 HTTP/网络故障包装成 `UNKNOWN_TOOL`，无法区分“查询失败”和“工具不存在”。此外 `tools/list` 在返回目录前会调用 `syncChatTools()`，缺失 Chat 注册项时会写入 Supabase；这是现有自修复副作用，尚未做 endpoint 验证。
- 当前 Supabase `skills` 只读结果还发现多个 enabled 注册项没有可执行的 `handler_config.handler`：`architecture`、`github-use-guide`、`master-router`、`读懂柳柳` 为 `handler_type=text` 且配置为空对象；`publish-workflow` 为 text 且配置为空；`code-runner-guide`、`database-capability-guide`、`需求梳理` 为 `handler_type=js` 但配置为空；`memory-retrieval-hybrid` 也没有可执行 handler 配置。它们的描述看起来分别是文档/流程或能力指南，但 Worker 的 `tools/call` 最终只按 `handler_config.handler` 查 `handlerMap`，找不到时返回 `handler type not implemented: <type>`。因此当前是“可出现在 tools/list，但没有可执行 handler”的静态不一致；这些条目是否本来只供宿主读取、是否应继续暴露，需先确认设计语义，不在本轮直接补 handler 或删注册。
- `github_v64.js` 将 `GITHUB_TOOL_DEFS` 视为工具元数据真相源、Supabase `skills` 为缓存。需要区分两条同步路径：`autoSyncGithubTools` 会比较已有项的 schema/description 并返回 `changed` 名单，但不会自动更新这些项；Router 的 `passiveSyncGithubTool` 仅在注册项缺失时新增，已有项直接跳过。`chat_mcp.js` 的 `syncChatTools` 也只补缺失项。与此同时 `dispatchGuard.getToolSchema` 从 Supabase 注册表读取 schema，因此既有注册项可能持续与源码定义漂移。只读抽样已发现 `github_create_branch` 注册表 schema 含 `required: []`，而源码定义没有该字段；两者对必填语义等价，但归一化 JSON 结构会不同，注册表 description 也与源码文案不同。`chat_pending_events` 的注册表 description 是短版，而源码有更完整的描述。此为抽样证据，不代表所有字段都存在行为差异；尚未完成全量 diff，不批量重写注册表。
- MCP serverInfo.version=6.5.0，而 package.json=6.3.4。差异已确认，是否统一待评估，不应只因数字不同直接修改。

| `src/skills/**/SKILL.md` | 面向宿主/Agent 的流程说明、规范与能力指南 | 需要由宿主或明确加载器读取；Supabase `skills.file_path` 目前未被 `knowledge.js` 消费 | Markdown 内容、Supabase 注册元数据、Worker handler 是三个不同层。只读查询确认 `file-management`/`image_upload` 的 `file_path` 指向仓库 Markdown，但 Worker `knowledge` handler 只回传数据库 `description`；`需求梳理`、`master-router`、`architecture`、`github-use-guide`、`code-runner-guide`、`database-capability-guide`、`memory-retrieval-hybrid` 等启用项的 `handler_config` 缺失或无可用 `handler`，按当前普通注册项分派会返回 `handler type not implemented`，不会自动加载文件。此为源码+注册表静态结论，未验证 Operit/GPT App 是否有独立加载路径。 |

**模块整理结论（本阶段）**：
- 当前可安全确定的是职责与静态依赖边界，不是每个资产的运行频率或所有宿主的实际调用情况。
- 高优先级的后续设计题集中在：工具注册—handler 对齐、Skill 内容来源/加载契约、记忆写入与迁移可靠性、注册 schema 同步与成功反馈。
- `permission_guard.js` 等“源码存在但入口接入未证实”的模块先保留，不因未见直接 import 就删除。
- 不启动行为测试、不改生产代码/数据库/部署；本节仅作为重构前依赖地图。

## 4. 记忆路径与数据库现状

### 4.1 记忆路径

- 主要统一入口：memory_unified.js；检索实现包括 utils/search.js。
- 关键词 memory search 对部分自然问句曾比 query_memory 语义召回更稳定；检索质量应以固定查询集、预期键和误召回检查判断。
- memories 有 trigger_intents、entities、related_memory_ids 字段；字段存在不等于每条检索路径均完整使用，也不等于持续效果已验证。
- 统一入口包含 remember/update/rename/forget/import/export/move 等 action，但各 action 的错误处理、软删除与事件审计完整度并不相同。
- memory_events 是变更账本的一部分；尚不能证明创建、软删除、重命名、移动等所有生命周期路径均形成完整事件链。

### 4.2 表清单

最近一次 supabase_schema action=schema_dump 返回 25 张表：23 张业务表 + 2 张测试表（sb1_0_test_memories、sb1_0_test_memory_events）。

- 这是该次 schema 快照的观察结果，不保证不同环境/时间/工具口径完全相同。
- 核心记忆表：memories、memory_events、memory_aliases。
- 其他表涵盖工具/技能注册、执行与会话绑定、协作/聊天室、文件及治理/补丁提案等域；准确字段以实时 schema 为准，语义文档见 governance/database/database-overview.md 与 governance/database/domains/。
- RLS 策略、全部约束、两张测试表来源及自动 schema 落盘/CI drift 检测尚未完成核验。
- 不因发现缺表依赖就直接建表；先确认调用路径、容错、使用情况与预期行为。

## 6. 宿主差异与跨宿主交接
