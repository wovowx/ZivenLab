- 文档性质：当前实现事实地图，不是目标蓝图。
- 仓库/分支：wovowx/ZivenLab，dev。
- 核对日期：2026-10-26（阶段 1–3 地图同步；阶段 4 usage_count 最小修复后的 dev 源码与回归资产复核）。

## 1. 证据等级

| 等级 | 含义 | 表述纪律 |

## 3. Worker / MCP 入口与调用关系

1. mcp-memory/src/index.js：Worker HTTP 路由、部分 API、静态页面与定时任务入口。
2. mcp-memory/src/modules/mcp_router.js：MCP initialize、tools/list、tools/call 与工具分派。
3. mcp-memory/src/tools/memory_unified.js：统一记忆读写、检索、导入导出与移动入口；使用 src/utils/search.js 等模块和 Supabase。
4. GitHub 工具当前 Router 实际使用 src/tools/github_v64.js；不能仅凭 github.js 同名文件推断其为活动实现。
5. src/modules/、src/utils/包含搜索、响应、技能/存储、执行会话、运行时与 Patch Engine 等模块。模块存在不等于路由可达、注册有效或线上正在使用。
6. src/skills/中的 Markdown Skill 与 Supabase skills 注册表不是同一层：前者描述行为/流程，后者承载工具注册与 schema/元数据。须分别检查路由、注册和实际调用证据。

### 路由与统计限制

- Router 使用固定工具名前缀和注册表 schema 门禁；无有效路由或 schema 的源码函数可能不可见或被拒绝。
- Supabase 注册表中统一 memory 工具为 enabled=true，公开 action schema 包含 suggest 与 move。独立 memory_move 别名精确查询为空，因此不能说 move 功能整体不可用。
- usage_count 自动计数会参考返回文本是否命中错误前缀，不等价于严格业务成功判定；也没有按 action 的真实使用统计。Operit 的隔离 Mock 曾复现 `handler type not implemented: text` 会误触发 usage_count PATCH。柳柳授权后，`mcp-memory/dev/src/modules/mcp_router.js` 的 `toolOk` 已将该前缀列入失败排除条件，测试资产 `tests/router_registry_contract_test.mjs` 也已进入远端 dev。Operit 本地报告 `npm run check` exit 0、既有 E2 104/104、新 Mock 16/16；GPT 静态计数最初发现远端测试文件有15个 `check(...)` 调用点；之后已在授权测试文件范围内补入一条已注册 `memory_remember` handler 的失败不计 usage 断言，当前远端静态计数为16，与Operit原始16/16报告数量一致。但补入断言后的精确远端版本尚未重跑，状态仍为 NOT RE-RUN。GPT 未独立重跑 Node 命令。此修复仅在 dev，未部署；E3 真实 endpoint 未运行，不能把 Mock 结果等同于生产行为已验证。
- MCP serverInfo.version=6.5.0，而 package.json=6.3.4。差异已确认，是否统一待评估，不应只因数字不同直接修改。

### 阶段 3 · 源码/路由/注册表依赖核对（只读证据，2026-10-26）

#### 主入口与调用链

```text
Cloudflare Worker
├─ fetch() / scheduled()                         src/index.js
│  ├─ HTTP API / upload / 页面路由
│  ├─ POST /mcp → handleMCPRequest               src/modules/mcp_router.js
│  ├─ /chat / webhook → tools/chat*.js
│  ├─ execution session API → modules/execution/execution_session_manager.js
│  └─ scheduled() → watchdogSweep → processPendingEvents → dispatchZivenWake
│     （聊天室/唤醒执行链按既定暂停边界保留，不在本阶段排障）
└─ MCP tools/call
   ├─ dispatchGuard：工具名/注册表/schema 子集
   ├─ 特定前缀/工具直接分派（memory_、github_、supabase_、chat、cf_proxy）
   └─ 其他名称：Supabase skills 注册表 → handler_config.handler → handlerMap
      ├─ memory → tools/memory_unified.js → helpers.js + search.js + Supabase
      ├─ github → tools/github_v64.js → patch_engine.js；发布闸使用 release_guard.js
      ├─ ai → tools/ai.js → skills.js / storage.js
      ├─ database → tools/database.js
      ├─ chat → tools/chat_mcp.js → tools/chat.js
      └─ knowledge / delete_branch / increment_usage → 对应工具模块
```

- 共享基础模块：`src/utils/response.js` 提供统一 HTTP/MCP 响应；`helpers.js` 提供记忆 key/标题、时间与分页工具；`skills.js` 是 Supabase `skills` 注册表读写与启用过滤入口；`storage.js` 被 Worker 入口与 AI/文件工具复用。这里是代码依赖关系，不等于每个工具都已通过端点实测。
- `src/modules/agent_runtime/mcp_client.js` 默认在同一 Worker 进程内直接调用 `handleMCPRequest`，仅显式配置 `MCP_HTTP_TRANSPORT=true` 时走 HTTP `/mcp`；这是内部复用同一 Router 的实现路径。它有 30 秒工具发现缓存；Router 的技能注册缓存 TTL 为 5 分钟。
- 工具注册表只读快照：2026-10-26 查询到 `skills` 共 69 行，其中 enabled=true 66 行、enabled=false 3 行（`describe_image`、`generate_image`、`generate_video`）。`tools/list` 的代码路径只返回 enabled 行，并会先调用 `syncChatTools`，因此该读取操作在缺少聊天室工具注册项时可能写入补齐记录。
- 当前注册记录有 14 行缺少 `handler_config.handler`。其中 4 个 `github_*` 名称仍会被 Router 的前缀分派直接交给 GitHub handler；其余名称（例如 `master-router`、`code-quality-guard`、`code-runner-guide`、`memory-retrieval-hybrid`、`需求梳理`）在当前通用分派分支会落到 “handler type not implemented” 路径。此为源码+注册表的静态判断，尚未逐个调用真实 MCP endpoint。
- Router 的已知名称前缀白名单含 `category_*` 与 `database_*`，但 tools/call 直接分派只显式处理 `supabase_*`、`memory_*`、`github_*` 以及明列的 Chat/CF 工具；`category_*` / `database_*` 若无注册表记录，仍会在后续注册表查找处成为 unknown tool。当前实时 `skills` 查询中没有 `category` 或 `data` handler 配置，也没有 `list_categories`、`recall_by_category`、`move_category`、`import`、`export` 这些独立工具名。
- **Router 存在显式特例，不能只凭 `handler_config.handler` 推断实际执行路径。** `create_patch_proposal` 在 `tools/call` 中有早期专门分支，直接调用 `handleCreatePatchProposal`，先于通用注册表 `handlerMap` 分派；当前实时 `skills` 记录中该工具 `enabled=true`、`handler_config.handler=database`、`input_schema=null`。所以 `tools/list` 会把它的 `inputSchema` 暴露为 `{}`，客户端看不到 handler 内部要求的 `target_file`、`change_summary`、`reason`；`dispatchGuard` 因 schema 缺失采取兼容放行，必填项只在专门 handler 内检查。另该专门分支直接 return，绕过后续 `toolOk` 与 `autoIncrementUsage`，因此目前这条成功/失败路径均不会走自动 usage_count 计数。这里有两项独立契约缺口：公开 schema 缺失、用量打点绕过；都属于源码/实时注册表可确认的静态事实，不能据此推断线上调用整体失败。`github_*`、`memory_*`、`supabase_*` 等名字前缀分支也会优先于通用 metadata handler 分派。
- `memory` 是当前启用的统一记忆工具，其 schema 本身已提供 `suggest`、`move`、`list_categories`、`by_category`、`import`、`export` 等 action。源码还保留 `memory_move` 等 `memory_*` 兼容别名映射，但这些别名不在注册表、不会由 `tools/list` 宣告。Router 的 `getToolSchema()` 在查不到注册 schema 时返回 `null`，而 `dispatchGuard()` 明确将 schema 缺失按兼容策略放行；因此此类别名在 `tools/list` 不可见，却仍可能通过 `tools/call` 进入 handler，且没有别名专属参数校验。这是已由静态代码确认的列表/调用/schema 契约不一致，不是“缺 schema 就必然被拒绝”。是否保留别名、是否要公开列出/补齐 schema，需阶段 4 结合兼容性和真实行为回归决定。
- `src/tools/data.js`、`src/tools/category.js` 仍被 Router import 并列在 `handlerMap`，但当前注册表无 `data` / `category` handler 记录。前者复用 `memory_unified.js` 导出的读写函数；后者自行实现 `getAllMemories/getMemoryByKey/deleteMemory/putMemory`，与统一实现职责重叠，且其旧 `move_category` 流程先删源后写目标、未校验各写请求状态。暂列“旧实现候选/待检查动态引用”，不删除、不合并，直到阶段 4 确认完整引用与兼容契约。
- `src/modules/permission_guard.js` 定义 `checkCapabilityAccess`，但当前 `index.js` 与 `mcp_router.js` 未导入它；Router 文件头也明确写明当前分派层不负责 capability/approval/audit。当前可见硬门禁集中在工具名/部分 schema 子集、GitHub 主分支写入阻断和 `release_guard.js` 版本闸门。该能力守卫是否应接入、`tool_policies` 表是否有其它运行时消费者，仍需独立核实，不在本阶段直接改权限行为。
- `src/modules/patch_engine.js` 经 `github_v64.js` 导入 `validatePatch/applyPatch`，说明 Patch Engine 有源代码调用链；其导出的 `selfTest()` 不因存在本身就视为已执行。release guard 则从 Router 直接导入并参与 GitHub 操作的前置校验。
- HTTP 路由由 `src/index.js` 明确分派：MCP、Chat/Webhook、Chat2API、Northflank、执行会话、上传、debug 与 `/memory-universe`。在通用路由分支之前未见统一认证中间件；`/memory-universe` 路由源码直接从 `mcp-memory/main/src/public/memory-universe.html` 取页面并返回，未在该分支执行认证。网络层是否另有保护、其它端点是否有独立保护、匿名外部可达性均不以源码静态判断代替实际 HTTP 验证。

## 4. 记忆路径与数据库现状

### 4.1 记忆路径

- 主要统一入口：memory_unified.js；检索实现包括 utils/search.js。
- 关键词 memory search 对部分自然问句曾比 query_memory 语义召回更稳定；检索质量应以固定查询集、预期键和误召回检查判断。
- memories 有 trigger_intents、entities、related_memory_ids 字段；字段存在不等于每条检索路径均完整使用，也不等于持续效果已验证。
- 统一入口包含 remember/update/rename/forget/import/export/move 等 action，但各 action 的错误处理、软删除与事件审计完整度并不相同。
- memory_events 是变更账本的一部分；尚不能证明创建、软删除、重命名、移动等所有生命周期路径均形成完整事件链。

### 4.2 表清单

2026-10-26 最近一次 `supabase_schema action=schema_dump` 机器响应返回 25 张表：23 张业务表 + 2 张测试表（`sb1_0_test_memories`、`sb1_0_test_memory_events`）。本次输出含列/FK片段，但未核验触发器、RLS 与全部约束。

- 这是该次 schema 快照的观察结果，不保证不同环境/时间/工具口径完全相同。
- 核心记忆表：memories、memory_events、memory_aliases。
- 其他表涵盖工具/技能注册、执行与会话绑定、协作/聊天室、文件及治理/补丁提案等域；准确字段以实时 schema 为准，语义文档见 governance/database/database-overview.md 与 governance/database/domains/。
- RLS 策略、全部约束、两张测试表来源及自动 schema 落盘/CI drift 检测尚未完成核验。
- 不因发现缺表依赖就直接建表；先确认调用路径、容错、使用情况与预期行为。
