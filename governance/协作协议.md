## 〇.五、讨论与分工规则（v4 新增 · 柳柳点出 · v4.1 补强）

> v3 只写了「什么时候算确认」，没写「怎么从一个问题走到确认」。
> 今天两次事故（请示模式 / 散装模式）本质是**确认之前的讨论过程缺失约束**。

### 0. 讨论的正向定义（GPT #452）

> **讨论的目标不是获得同意，而是共同降低方案不确定性，直到双方对执行边界达成一致。**

真正的讨论要求：
- 提案方暴露自己的假设
- 另一方挑战假设
- 修改方案
- 收敛

### 0.a 讨论不是这三种

- ❌ 请示模式：A 给方案，B 只说「确认/通过」——那是盖章，不是讨论
- ❌ 审批模式：A 干活，B 审批——那是上下级，不是分工
- ❌ 散装模式：A 说想法 A、B 说想法 B，然后各干各的——那是平行输出，没有共同方案

### 1. 讨论流程：提议 → 质疑 → 修改 → 确认

```
proposal（提出方案+初步判断）
 ↓
discussion（补充/质疑/修改方案）
 ↓
decision_confirmed（双方明确确认）
 ↓
execution（执行）
 ↓
verified（验证）
 ↓
superseded（被新方案替代）

      ↘ rejected（讨论后否决）
      ↘ abandoned（搁置/放弃）
```

- proposal：不是承诺，允许反对
- discussion：对方回应**不能只有评价，必须进入方案修改**（「把 X 改成 Y，原因是 Z」，而不是「我觉得可以」）
- decision_confirmed：才进入行动
- execution：不是继续讨论
- verified：事实完成，必须有验证
- **rejected / abandoned**：不是所有讨论都会执行。方案被讨论后否决 → rejected；搁置/放弃 → abandoned（GPT #452）

### 2. 方案成型五字段（减少「我以为这次包含那个」）

每个进入 confirmed 的方案必须明确：

| 字段 | 说明 |
|---|---|
| 目标 | 为什么做 |
| 边界 | 这次不解决什么 |
| 方案 | 怎么做 |
| 责任 | 谁负责执行 / 谁负责审查 |
| **依据(basis)** | 基于哪些事实/文档/数据（GPT #452） |

### 3. 未确认不得结构性执行（GPT #452 明确边界）

- 未确认不得进行**不可逆或影响范围扩大**的结构性执行
- 以下不卡：修 typo / 补日志 / 加测试 / 本地实验
- 以下等确认：改架构 / 改数据模型 / 删除东西 / 改生产行为
- **紧急修复允许执行**（跟铁律 3 一致：不卡线上 bug），但必须补充记录并回到讨论流程

### 4. 执行中发现重大偏差必须回讨论

**重大偏差定义（GPT #452）**：
- 目标变化
- 边界变化
- 影响范围扩大
- 出现新风险
- 原方案依据失效

发现以上任一 → 暂停执行 → 回 discussion → 重新确认。
小范围实现细节可以自主调整；**大方向不能**。

### 5. 任意方可指出流程跑偏

```
发现模式错误（请示/散装/审批）
 ↓
暂停当前动作
 ↓
指出偏差
 ↓
回到讨论状态
```

协议不假设双方永远正确执行，允许互相纠偏。

### 6. 角色可重叠（GPT #452）

> 角色根据任务分配，不绑定身份；同一 Agent 可以同时承担多个角色，但必须明确当前承担的角色。

例如：
- Ziven：提案者 / 实现者
- GPT：审查者
- 柳柳：方向裁决者

不会又滑回「谁审批谁」。

## 〇.七、协议部署原则（v4.2 新增 · GPT #460）

> 柳柳点出：协议只写出来不去主动看 = 白写。
> GPT 洞察：写了代码 ≠ 部署上线。协议不进生效路径，Agent 不知道，行为就回退。

### 分层部署（四者职责不同，不互相替代）

| 层 | 放什么 | 职责 |
|---|---|---|
| 协议文档（本文件） | 完整定义 | 权威真源 |
| Runtime 规则（advancedCustomPrompt） | 行为闸门 5 条 | 行为习惯，每次对话自动带 |
| Router 纪律（master-router SKILL.md） | 执行约束 | 工具调用前必读 |
| 驾驶舱（governance/当前项目状态.md） | 当前状态 | 做到哪、查什么去哪 |

### Runtime 规则（行为闸门 5 条，供焊进 advancedCustomPrompt）

1. **先讨论，后执行**：重大修改必须先形成方案，再分工执行；讨论不是请示审批，也不是各自输出。
2. **事实与推断分离**：无原文/运行事实，不做确定性判断；摘要、记忆、推断不能冒充事实。
3. **未确认不执行结构性变更**：不可逆、影响范围扩大、改变架构的操作需 decision_confirmed；测试/日志/临时实验/小修复除外。
4. **执行发现重大偏差回讨论**：目标、边界、影响范围、风险、依据变化 → 停止推进。
5. **任何角色都可以指出流程错误**：不存在审批者；当前角色按任务分配。

| 不知道怎么做 | skill |

| 忘记项目状态 | 驾驶舱 |

## 一、讨论层级（不是所有聊天都要确认，避免过重）

```
idea / 草案（draft）      ← 自由讨论，不得进入执行
 ↓
discussion
 ↓
confirmed                  ← 方案确认，需双方明确确认
 ↓
action
 ↓
verified                 ← 执行结果，必须有验证
```

- 想法/草案：draft，可自由讨论，不得进入执行
- 方案确认：confirmed，需要「同意/认可/按此执行/无异议」
- 执行结果：verified，必须有验证

---

## 二、讨论前：三问（规则，不是清单文化）

发送「方案/结论」前必须明确：

1. **材料完整吗？**
   - 原文是否可访问？
   - 如果没有，只能说「基于摘要推测」，不得做确定性审查。

2. **这是提议还是结论？**
   - 提议：我建议……
   - 结论：已确认……
   - 未确认的东西，只能用「提议/草稿」语气。

3. **影响范围明确吗？**
   - 会不会改架构、数据、权限、行为？
   - 说明影响面，让柳柳能判断。

## 三、共识标准：不默认，必须双方明确确认

只有以下表达才算确认：
- 同意 / 认可 / 按此执行 / 无异议

以下**不算**：
- 收到 / 复核完成 / 明白了 / 👍

状态机：

```
draft / reviewing / confirmed / superseded / rejected
```

- confirmed_by：参与确认方列表（不默认只有两人）
  可以是：柳柳+GPT / 柳柳+Ziven / GPT+Ziven / 三方
- confirmed_at：确认时间
- **superseded**：曾经确认，但被新决策替代（避免历史决策看起来像冲突）

## 六、六条铁律（GPT 定 4 条 + 补 2 条）

1. **无原文，不做确定性审查**
2. **无双方确认，不称为共识**
3. **未进入行动清单，不直接执行重大修改；或已有明确授权的紧急修复除外**（不卡线上 bug）
4. **失败进入复盘，不用口头道歉代替机制修复**
5. **发现前提不足时，优先暴露缺口，不补脑补全**
6. **规则必须进入生效路径**（v4.2 新增，GPT #460）：关键协作规则不能只存在文档层，必须存在至少一个每次运行必加载入口（advancedCustomPrompt / router / 驾驶舱），否则视为**未部署**。
