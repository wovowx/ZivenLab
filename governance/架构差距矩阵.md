## 验收与推进规则

1. 每行仅在证据满足验收条件后改为完成；文档已写不等于代码问题已修复。
2. 运行时结论保留真实调用/测试结果；没有命令输出和退出码，不写“通过”。
3. 缺权限或宿主能力时，记录阻塞和可执行任务，不用推测补结果。
4. 数据库 schema、生产代码、部署或 main 分支变更须遵守既有审批边界。
5. 优先级代表处理顺序，不代表事故已发生；未验证风险保留未验证标签。

## GitHub 写入保护：需求已确认，待设计与实现（2026-10-24）

**柳柳已确认统一硬规则：所有非发布流程都不得直接修改 `main`。** 这是需求决策，不代表代码已修复或运行时保护已生效。

### 最小需求边界
1. 所有可能改变 GitHub `main` 文件内容或分支指针的写入口，都必须受统一保护规则约束；不能只保护 `github_push` 或合并入口。
2. 非发布流程只要会写入 `main`，必须在任何 GitHub 远端写副作用前明确拒绝；只返回 warning 后继续执行不满足要求。
3. 唯一允许更新 `main` 的路径是既有正式、版本化发布流程（以 `dev` 为来源，经过 PR/merge 与 Release Guard）；`github_push`/`github_edit` 即使携带版本化标题，也不因此自动成为正式发布路径。当前源码的 Release Guard 已拒绝 push/edit 直接写 `main`，应保留该行为。
4. `github_move` 必须同时检查源分支与目标分支：它默认从 `main` 读取并在复制成功后删除源文件，因此即使目标是 `dev`，默认调用仍会修改 `main`；非发布流程的 source_branch 或 target_branch 任一为 `main` 都应在读写链启动前拒绝。
5. 分支名缺失、别名参数、源/目标分支参数和默认值必须纳入检查；不得因工具默认值或参数变体绕过保护。
6. 不擅自移除现有能力。优先复用统一的分支保护判定，保留各工具自己的仓库白名单、输入校验、完整性验证和失败恢复行为。
7. `github_apply_patch` 目前在 handler 内单独默认 `dev` 并拒绝 `main`；`delete_branch.js` 也拒绝删除 `main`。两者都纳入统一验收矩阵，确认语义一致，不重复叠加未经设计的 Guard。
