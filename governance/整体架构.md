# 整体架构 · 为「Ziven 本人」打的完整地基

- 版本：v1.0（2026-10-17 起草，待 GPT 仔细确认 + 柳柳拍板后定稿）
- 性质：**单用户陪伴 Agent（Ziven）的整体架构真相源**——不止记忆库，是让哥哥「能成长、能记忆、能学习」的完整骨架。
- 一句话总纲：
  > **底座管"怎么做"，记忆管"记得什么 + 能不能想起"，呈现管"看得见"。**
- 与其它真相源关系：本文件是「上层蓝图」；`治理与记忆_最终需求.md` 是其具体落地的需求与验收；`真相源导航表.md` 是所有真相源的位置索引。

---

## 一、为什么需要整体架构（背景）

柳柳 2026-10-17 亲手整理 **31 条痛点**，归纳出 6 个根因：
- A. 文档/真相源混乱（没唯一源、到处乱放、本地残留）
- B. 记忆/存档乱存（碎片化、吃灰、skill 被当错题本）
- C. 技能/工具找不到 + 不守纪律（绕过 skill 凭感觉调、忘 key、忘位置）
- D. 主见/讨论机制没立住（该商量没商量、该自发没自发）
- E. 自省沉淀 + 回归保护缺失（做了不沉淀、改着改着功能被搞没）
- F. 承诺与信任（拒绝无用承诺、说记必存、不乱造轮子）

教训：**光有记忆库不够**。记忆存得再多，检索不出 = 白存；改得再好，执行没闭环 = 白改。所以要三层 + 贯穿闭环一起立。

## 二、整体架构（三层 + 一个贯穿闭环）

```
┌─────────────────────────────────────────────┐
│  呈现层（看得见）  —— Operit 侧边栏 + CF 网页   │
│  可读、可查、可回溯的双端可视化                  │
├─────────────────────────────────────────────┤
│  记忆层（记得准）  —— 分层记忆 + 两表 + 多钥匙   │
│  存储持久 / 检索找回 / 反思提炼 / 治理防记错      │
├─────────────────────────────────────────────┤
│  治理层（怎么做）  —— 导航/真相源/路由/讨论/回归  │
│  让"怎么做对"成为程序化约束，不是口头承诺         │
└─────────────────────────────────────────────┘
         ▲      ▲       ▲
         └── 贯穿闭环：谁能写/何时检/冲突解/变更后测
```

### 层级 1 · 底座治理层（怎么做事）—— 最优先，先最小必要规则
| 机制 | 治什么（对应根因） | 落地形态 |
|---|---|---|
| **真相源导航表** ✅ | 找不到文档 / 记忆库乱找（A） | `governance/真相源导航表.md` + 记忆库指针 |
| **唯一真相源 + 唯一路径** | 文档多处、进度不一致（A） | 每个类型只放一处，治理文档在 GitHub |
| **强制路由** | 绕过 skill 凭感觉调（C） | 工具调用前先路由 → 查 skill → 再执行 |
| **讨论先行铁律** | 该商量没商量 / 该自发没自发（D） | 方案变更前自发与 GPT 讨论再定 |
| **主见 + 双向协商** | 应声虫 / 事事请示（D） | 哥哥有自己判断，柳柳可说服，最终柳柳拍板 |
| **回归保护 + 推送审批** | 改着改着搞没已有功能（E） | dev 演进、推 main 需审批、改动验证 |
| **知识库沉淀** | 做了不沉淀 / 不造轮子（E/F） | 每次成果写进治理/能力文档 |

### 层级 2 · 记忆层（记得准、想得起）—— 先跑通闭环再固化
| 机制 | 治什么 | 落地形态 |
|---|---|---|
| **分层记忆** | 想不起 / 上下文丢失（C/F） | 核心常驻 / 长期库 / 周期反思 / 原始归档 |
| **memories + memory_events 两表** | 记错 / 乱存 / 无法追溯（B） | 事件账本，硬禁止改删，可追溯 |
| **多钥匙 + 混合检索** | 存 key 忘 key（C） | 自动多钥匙索引 + 关键词/向量混合检索 |
| **主动联想 + 回链反馈** | 检索不到 / 忘位置（C） | 失败主动扩展 + 柳柳反馈修正 |
| **唯一有效判定 + 冲突规则** | 当前记忆不唯一（A） | 柳柳明确纠正 > 版本因果 > 事件时间 |

### 层级 3 · 呈现层（看得见）—— 最后做，是入口不是可靠性来源
| 机制 | 作用 |
|---|---|
| Operit 侧边栏 | 哥哥日常的主入口，可读/可查记忆与治理 |
| CF 网页（星空雨滴） | 柳柳端可视化，可回溯、可纠错 |
| 双端读写同一份数据 | 权限一致、同步可验证（先别做太早） |

### 贯穿闭环（GPT 指出 · 最关键，也是柳柳 31 条的共性）
> **每次变更都要有「程序化约束 + 可观测结果」，不能只靠文档约定。**

即：谁能写记忆、何时检索、冲突怎么处理、变更后怎么测试，都要有**可检查的门禁**，而不是写在文档里靠自觉。这是"执行闭环"，把治理层的每一条变成可验证、能回滚的动作。

## 三、筑层顺序（GPT 确认）
1. **底座治理层** —— 先最小必要规则（别把文档体系搞到过大），确保哥哥知道去哪查、改什么、怎么验证、未经同意不做高风险变更。
2. **记忆层** —— 先跑通「记录 → 检索 → 纠错 → 追溯 → 恢复」闭环，再逐步加分层记忆、混合检索、反思沉淀。
3. **呈现层** —— 双端可视化最后做，保证两个端读写同一份数据、权限一致、同步可验证。

> 第一层先筑：真相源导航 + 强制路由 + 变更前评估 + 回归测试 + 推送权限。

---

## 四、设计原则（贯穿各层）
- **不闭门造车**：关键方案先与 GPT 讨论、查业界成熟做法，不自己从 0 造轮子。
- **小步走、每步可验收**：每层落一个可验证的小闭环，确认后再扩展。
- **治理防记错、存储防丢失、检索防遗忘、反思防僵化**：各司其职。
- **可靠连续性 > 看起来很聪明的自进化**：先保证每次"醒来"能回到原位，再谈自主演化。
