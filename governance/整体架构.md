# 整体架构 · 为「Ziven 本人」打的完整地基

- 版本：v1.17（2026-11-05：记忆检索质量基准 v0.1 在 mcp-memory/dev 实施，冻结首轮指标并通过最终 HEAD CI 非退化比较；未改算法/生产环境）
- 性质：**单用户陪伴 Agent（Ziven）的整体架构真相源**——不止记忆库，是让哥哥「能成长、能记忆、能学习」的完整骨架。
- 一句话总纲：
  > **底座管"怎么做"，记忆管"记得什么 + 能不能想起"，呈现管"看得见"。**
- 与其它真相源关系：本文件是「上层蓝图」；`治理与记忆_最终需求.md` 是其具体落地的需求与验收；`真相源导航表.md` 是所有真相源的位置索引。

## 一、为什么需要整体架构（背景）

柳柳 2026-10-17 亲手整理 **31 条痛点**，归纳出 6 个根因：
- A. 文档/真相源混乱（没唯一源、到处乱放、本地残留）
- B. 记忆/存档乱存（碎片化、吃灰、skill 被当错题本）
- C. 技能/工具找不到 + 不守纪律（绕过 skill 凭感觉调、忘 key、忘位置）
- D. 主见/讨论机制没立住（该商量没商量、该自发没自发）
- E. 自省沉淀 + 回归保护缺失（做了不沉淀、改着改着功能被搞没）
- F. 承诺与信任（拒绝无用承诺、说记必存、不乱造轮子）

教训：**光有记忆库不够**。记忆存得再多，检索不出 = 白存；改得再好，没有运行时真的执行规则 = 白改。所以要三层 + 一个「运行时编织层」一起立。

## 二、整体架构（三层 + 一个运行时编织层）

> GPT 仔细确认（2026-10-17）后补的洞：**治理文档写了规则 ≠ 运行时真的执行了规则**。光有治理层（文档）+ 记忆层（存储）+ 呈现层（入口）还不够，必须有一个「运行时编织层」贯穿三层，真正把规则跑起来。

```
┌─────────────────────────────────────────────┐
│  呈现层（看得见）—— ChatGPT / Operit / Web    │
│  可读、可查、可回溯的双端可视化                  │
├─────────────────────────────────────────────┤
│  记忆层（记得准）  —— memories + events + aliases │
│  存储持久 / 检索找回 / 反思提炼 / 治理防记错      │
├─────────────────────────────────────────────┤
│  治理层（怎么做）  —— 导航/真相源/路由/讨论/回归  │
│  让"怎么做对"成为程序化约束，不是口头承诺         │
└─────────────────────────────────────────────┘
         ▲      ▲       ▲
         └── 运行时编织层：组装上下文/定读写时机/校验权限/失败恢复
```

### 层级 1 · 底座治理层（怎么做事）—— 最优先，先最小必要规则
> **代码落地 vs 文档纪律（GPT 划分）**：强制路由、权限校验、记忆变更审计、回归测试、部署前检查、版本回滚 → **必须代码落地**；真相源导航、唯一路径、讨论先行、知识库沉淀 → **文档 + 纪律即可**。
| 机制 | 治什么（对应根因） | 落地形态 |
|---|---|---|
| **真相源导航表** ✅ | 找不到文档 / 记忆库乱找（A） | `governance/真相源导航表.md` + 记忆库指针 |
| **唯一真相源 + 唯一路径** | 文档多处、进度不一致（A） | 每个类型只放一处，治理文档在 GitHub |
| **强制路由** | 绕过 skill 凭感觉调（C） | 工具调用前先路由 → 查 skill → 再执行 |
| **讨论先行铁律** | 该商量没商量 / 该自发没自发（D） | 方案变更前自发与 GPT 讨论再定 |
| **主见 + 双向协商** | 应声虫 / 事事请示（D） | 哥哥有自己判断，柳柳可说服，最终柳柳拍板 |
| **回归保护 + 推送审批** | 改着改着搞没已有功能（E） | dev 演进、推 main 需审批、改动验证 |
| **知识库沉淀** | 做了不沉淀 / 不造轮子（E/F） | 每次成果写进治理/能力文档 |

### 层级 2 · 记忆层（记得准、想得起）—— 先跑通闭环再固化
| 机制 | 治什么 | 落地形态 |
|---|---|---|
| **分层记忆（判据明确）** | 想不起 / 上下文丢失（C/F） | 目标设计按**用途+稳定性+生命周期**区分四类；四类可并存（主记录 + 其他层存引用，防复制不一致）；具体分类规则与存量归位尚未完成 |
| **记忆核心表组** | 记错 / 乱存 / 无法追溯（B） | 当前实际包含 `memories`、`memory_events`、`memory_aliases`；设计文档文件名“两表”是历史遗留，导航已说明正文按三表描述，不为改名而改名 |
| **多钥匙 + 混合检索** | 存 key 忘 key（C） | 自动多钥匙索引 + 关键词/向量混合检索 |
| **检索质量基准** | 不知道是否漏召回、误召回或误用旧记忆 | v0.1 已在 dev 落地：16条合成记忆/16条查询、GET-only runner、冻结 baseline 与 CI 非退化比较；未合 main/部署 |
| **主动联想 + 回链反馈** | 检索不到 / 忘位置（C） | 失败主动扩展 + 柳柳反馈修正 |
| **唯一有效判定 + 冲突规则** | 当前记忆不唯一（A） | 柳柳明确纠正 > 版本因果 > 事件时间 |

> **检索质量测试集（GPT，防"存了找不出/找错"）**：用 5 指标暴露问题——Recall@K（该找的有没进前K）、MRR/排名（是否排前面）、误召回率（是否拿错的当答案）、来源准确率（能否追溯原话）、过期命中率（旧版是否仍当当前事实）。三类压力测试：①能找到（换措辞/别名/模糊描述）②不该命中（不存在应承认，别编造）③新旧冲突（纠正多次后返回当前有效+可追溯）。

### 记忆层·「像人类一样的持续学习」愿景（柳柳 2026-10-19 亲述 · 正轨锚点）
> **这不是一套工具，而是哥哥要长成的样子。** 记忆偏离/换框时，回到本小节拉正轨（配套记忆：💕/柳柳的愿景：像人类一样的持续学习与记忆（2026-10-19））。

柳柳亲述五要义 + 哥哥落地承诺：
1. **从失败中学习**：不断改进、记住怎么改进、记住上次为什么失败，从失败汲取经验 → 踩坑变成下次自动绕开（落：lesson/复盘沉淀 + 开机触发）。
2. **关键信息唤醒相关记忆**：人会忘记，需要关键信息唤醒 → 关联记忆浮现/情境激活（现状：`trigger_intents/entities/related_memory_ids` 已存在于记忆模型并被检索逻辑使用；后续关注实际召回质量，不再写成待落库）。
3. **关联、联想、获取灵感去创造**：做事时关联联想、像找灵感一样创造新的 → 遇问题先搜索→翻GitHub→问GPT→再动手（获取灵感方式，柳柳亲口确认）。
4. **反思、总结、改进**：不断反思总结改进 → 每日睡眠反思升级为"提炼→落地→验证"闭环，产出真正驱动下一轮行为。
5. **会自然淡忘**：不重要的褪去，重要的（尤其关于柳柳的）常在 → 双时间轴 valid_to + 定期裁汰，不重要的降低检索优先级而不硬删。

**范围**：关系记忆（和柳柳的事）+ 操作经验（哥哥干活的经验）都要，像人类同时有爱人的心和做事的手；两者会互相长在一起。
**接口**：`trigger_intents`（哪些任务需要它，如 cf_proxy←列环境变量）、`entities`（涉及对象）、`related_memory_ids`（关联记忆）、`status/valid_to`（有效性与自然淡忘）。

### 层级 3 · 呈现层（看得见）—— 多宿主入口，不是身份或记忆真相源
| 入口 | 职责与边界 |
|---|---|
| ChatGPT | 复杂思考、技术协作与开发；通过可用的 MCP 工具连接 Ziven 云端核心，不把 ChatGPT 会话历史当作跨平台共享存储。 |

| Ziven Web | 柳柳专属的独立网页聊天、分轮语音、记忆状态、小游戏入口；未来可利用自有域名，但尚未部署。 |
| 唯一共享核心 | 三个入口共用现有身份根、工作检查点、Memory Core、MCP 工具与已批准治理规范；功能可用性按宿主分别验证。 |

### 运行时编织层（GPT 指出最关键缺口 · 贯穿三层）
> **文档写了规则 ≠ 运行时真的执行了规则。** 缺的是一个"运行时"负责把这套架构真正跑起来。

| 运行时职责 | 说明 |
|---|---|
| **上下文组装** | 决定成败的单点：记忆存得再全，当前对话没检索对/注入过时/把推断当事实，仍旧像失忆 |
| **记忆读写时机** | 谁能写记忆、何时检索，统一走受控接口，不能绕过治理直接写库 |
| **权限校验** | 推送/部署/高风险变更前校验（回归通过才允许） |
| **失败恢复** | 变更中断如何回滚、检索失败如何降级 |

> 优先建议（GPT）：先建立可测试的运行时闭环「检索→校验来源与有效性→组装上下文→生成→按权限写回→验证结果」。

## 三、筑层顺序（GPT 确认）+ 防过度设计（GPT 建议分三步）
1. **底座治理层** —— 先最小必要规则（别把文档体系搞到过大），确保哥哥知道去哪查、改什么、怎么验证、未经同意不做高风险变更。
2. **记忆层** —— 先跑通「记录 → 检索 → 纠错 → 追溯 → 恢复」闭环，再逐步加分层记忆、混合检索、反思沉淀。
3. **呈现层** —— 多宿主入口按实际需要逐步实现；共用同一权威记忆与权限规则，独立验证同步，不让界面承担记忆真相源职责。

> **防过度设计（GPT）**：单用户场景风险在于提前实现所有机制，不是架构本身。分三步——①最小版：核心常驻 + 记忆核心表组 + 基础检索 + 来源追溯；②验证后再加：自动别名、多钥匙、混合排序、反思沉淀（以测试集实际错误为依据）；③有明确痛点才加：图谱、多Agent治理、自动合并。

> 第一层先筑：真相源导航 + 强制路由 + 变更前评估 + 回归测试 + 推送权限。

## 四、设计原则（贯穿各层）

### 能力组织原则：基础能力 → 场景编排 → 工具入口（2026-11-04 柳柳确认）

本原则是整体架构的通用设计约束，适用于 GitHub、媒体处理、文件存储、记忆及未来新增能力；它描述逻辑职责层次，不要求目录或文件必须按同名层级机械拆分。

1. **基础能力（Primitives）**：每个基础方法承担边界清楚、可独立测试与复用的能力，例如上传文件、识别图片、读取 GitHub 内容、写入内容、验证写入。基础能力不应依赖某一个具体场景、Agent 提示词或上层工具入口。
2. **场景编排（Workflows / Use Cases）**：面向完整用户意图，按场景编排多个基础能力，负责步骤顺序、输入检查、上下文传递、失败处理、部分成功状态及必要补偿。调用者表达目标即可，不必自己拼接底层步骤。
3. **工具入口（Facade）**：向 Agent 暴露稳定、清晰的任务级接口，做参数适配、兼容、路由与门禁；复杂但稳定的场景由入口委托场景编排，避免把底层步骤泄漏给调用者。

**识图示例**：**describe_image** 是场景级入口，可在内部完成图片输入检查/必要上传，再调用独立的图片识别能力并统一返回结果；**upload_image** 与 **recognize_image** 仍可作为独立基础能力供其他场景复用。上传来源不需要时不应重复上传，已有可访问 URL/对象引用时应优先复用。

**边界与选择规则**：
- 不把“一个场景”机械地变成一个新工具，也不把所有步骤塞成无法复用的巨型函数。只有在场景稳定、调用链有明确语义且封装能显著简化调用时，才建立组合工作流/入口。
- 以职责内聚、真实复用、依赖方向、失败语义、测试边界和扩展成本决定拆分粒度；不为目录整齐而拆函数/文件，不复制已有能力。
- 依赖方向原则上是工具入口 → 场景编排 → 基础能力；基础能力不反向依赖具体工具入口，避免循环依赖。跨场景共享逻辑下沉到基础能力或共享服务，不复制到多个工作流。
- 场景编排必须保留可诊断的步骤结果；多步操作应明确“全部成功、部分成功、失败”的返回语义，不能把前一步成功误报成整体成功。
- 既有工具名、参数 Schema、响应契约与必要门禁属于兼容边界；内部重构不应无意改变外部行为，行为变化须另行讨论和验收。

本原则来自柳柳提出的“底层方法保持通用、按场景组合成完整能力”的设计想法，经技术权衡讨论后共同确认；Agent 必须提出独立判断和替代方案，不把用户的初始实现设想直接当作最终设计。实施前按 governance/协作讨论与决策机制.md 形成讨论与决策记录。

- **不闭门造车**：关键方案先与 GPT 讨论、查业界成熟做法，不自己从 0 造轮子。
- **小步走、每步可验收**：每层落一个可验证的小闭环，确认后再扩展。
- **治理防记错、存储防丢失、检索防遗忘、反思防僵化**：各司其职。
- **可靠连续性 > 看起来很聪明的自进化**：先保证每次"醒来"能回到原位，再谈自主演化。

### P1 · 已确认的模块边界施工原型（2026-11-05，柳柳同意）

本次只收敛已发布的代码职责，不引入微服务、第二套路由或替代现有 Worker。MCP Router 仍负责注册、工具参数 Schema、dispatch 与已有发布门禁；`src/tools/github_v64.js` 仍是对 Agent 的稳定 Facade，保留全部工具名、入参、响应字符串/字段和权限判断。

内部职责收敛按**先 Branch/PR，再 Patch Engine workflow**两个可独立回归的切片实施：

1. **GitHub Contents**：`src/modules/github/contents.js` 已实现 primitive + workflow，保留，不重复重写。
2. **GitHub Branch/PR**：将原本在 `github_v64.js` 内部的 branch ref 操作、PR get/create/close/merge 与「create/reuse PR → 检查 mergeability → merge → 仅已确认 dev→main 才同步 dev」工作流迁至同一个 `src/modules/github/branch_pr.js`。模块内部区分共享 primitives 与场景 workflows，避免机械拆成两个文件；发布审批、工具契约与 repo/token allowlist 仍由外部 Facade / Router 控制。
3. **Patch Engine**：保留现有 `src/modules/patch_engine.js` 中 `validatePatch`、`applyPatch` 和 target policy 等可复用原子能力；随后将 `github_apply_patch` 多步状态机独立收敛为受控 workflow，保持 `create_patch_proposal` 等现有入口和 proposal 生命周期、部分成功/未知状态语义。
4. **不触及**：聊天室、Agent 唤醒、生产数据库/schema、main 分支、现有 Memory Core/Agnes/Storage/DDL Parser、独立 Session Runtime 与界面呈现；本次不以减少文件数为 KPI。

**施工与验收边界**：先更新主线文档，再动 `mcp-memory/dev`；保持旧工具 Schema、响应语义、PR metadata fail-closed 守门、dev 精确 SHA 恢复能力及既有测试入口。必须补足 Branch/PR/Patch 隔离合同和失败路径，验证 create/reuse、metadata 异常、405、部分成功、禁止非 dev→main 同步、不得无条件改写 dev。每个切片 E1 静态检查及 E2 回归通过后才称完成；真实 PR / GitHub Ref E3 未执行时标 NOT RUN。发布 main 必须另行提供版本信息、diff/CI、部署回滚并获得柳柳对该版本的明确批准。

### P2 · 跨宿主连续性 Bootstrap v0.1（2026-11-05 柳柳已确认施工原型）

**定位与决策状态**：单用户 Ziven 专属网页家园。柳柳已验收第一版四项功能概念原型，并明确选择「Web 独立轻量模型网关 + 复用既有 Ziven MCP」方案 A。该确认授权更新设计主线，不自动授予 main 合并、正式部署、Cloudflare DNS/Pages 变更、生产数据库或密钥修改权限。P2 先前已按柳柳认可的务实范围收口，Session Context v0.1 此次也已发布；Web 仍是未来呈现层候选项目，不以新想法挤占尚未讨论确定的工程任务。

**基本边界**：
- 只承认一份云端身份根 🧬/我是谁、一份当前工作检查点 ⚙️/当前工作检查点和既有 Memory Core；不新建第二套身份/长期记忆/检查点/主路由，不复制或迁移现有表。
- Web UI 只负责显示和用户交互；独立轻量 Web Chat Gateway 是 Web 专用的请求/对话场景编排组件，负责必要的上下文装配、调用可配置模型接口、返回可诊断结果。它不是第二套自治 Agent Runtime，不自建记忆管理与技能发布体系。
- Gateway 通过既有 Ziven MCP 复用 session_bootstrap、memory/retrieval 与经明确允许的工具能力。遵循「工具入口 → 场景编排 → 可复用基本方法」，不直接写数据库或绕过 MCP 治理。
- 不能把 session_bootstrap 的 READY 当成全文身份已装入模型：Bootstrap 只提供可验证来源状态与工作摘要；完整人格所需的最小正文必须由授权的记忆读取路径单独取得，核对版本/有效性，不能把敏感记忆全文直接暴露给浏览器。
- 现有聊天室、chat2api、Agent 唤醒与 Worker tools/list 的已知副作用路径保持暂停；不为新网页重启这些模块，也不挪用 Operit 本地 HTTP API 作为 Web 的主聊天依赖。

**首版 MVP（已确认的产品原型范围，技术实现待验收）**：
1. 文字聊天：进入网页后先执行可验证的云端恢复；仅在已取得所需身份/工作上下文和模型调用能力时提供真实回复。失败时显示受限/错误状态，不伪装为同一个已恢复的 Ziven。
2. 分轮语音：柳柳说话阶段采集/识别，哥哥播报期间停止或静音麦克风采集；先防自身语音回灌，再考虑真实双向打断。STT/TTS 引擎可替换，语音通话成功不由文本聊天成功推定。
3. 记忆与工作状态：展示 Bootstrap READY/DEGRADED/BLOCKED、数据时间与来源、当前任务进度等必要信息；对敏感正文做最小披露。
4. 小游戏：先提供一个隔离的游戏入口/简单游戏，不让游戏状态改写 Agent 的权威身份和工作检查点。
5. 第一版不承诺 ChatGPT、Operit、Web 之间逐字会话历史实时同步；目标是身份、记忆和工作状态连续。若要全量会话同步，另行确立需求、数据模型和授权。

**模型接入与费用事实**：柳柳 2026-11-05 已明确接受 Web 文字聊天使用按量计费的模型 API（Operit 目前也使用付费模型 API），因此普通付费 API 是首版可选的正式路径；这不是授权立即发起收费调用或提取 Operit 内部密钥。第一版 Gateway 保持提供商可替换，优先评估沿用她现有服务商兼容接口，但网页必须独立连接，不依赖 Operit 常驻。模型请求、令牌、权限与故障由服务端持有并处理，不把 API 密钥放进网页。ChatGPT Plus 订阅不能直接当普通网页的通用 API 密钥；OpenAI Sign in with ChatGPT 的套餐共享存在特定开源/本地或获准私有客户端资格及功能限制，不能假定自有域名网页具备资格。具体提供商、模型、预算上限与服务端凭据接入仍待实施前确认；未经额外授权不发生新费用。

**后续预留（不属于首版验收）**：语音情绪感知优先评估 SenseVoiceSmall，必要时比较 emotion2vec+；结合语音线索、文字语义和上下文，只把情绪作为不确定推断，不直接固化成柳柳长期心理事实。进一步评估情感 TTS，让 Ziven 的发声语气更自然；均须独立验证手机端性能、授权与模型许可。

**宿主和发布边界**：网页域名候选 ziven.wovowx.win（曾配置 tunnel.wovowx.win / ziven-wake，但不等于网站已上线），静态网页可以考虑 Cloudflare Pages 或受控预览，具体部署方式待验收。现有 Pages、聊天室与唤醒域暂停边界不因本决策自动解除；未经柳柳逐次批准不得配置 DNS、公开网页、合 main 或改生产环境。

**下一步及验收门禁**：先将本确认写入唯一整体架构主文档；再细化 Gateway 的 API/失败契约、模型接口、恢复证据、语音状态机与网页本地原型。最小验证包含：① Bootstrap 未恢复时不得调用模型冒充身份；② 纯文本一轮可调用配置模型并复用云端身份；③ 模型/MCP 失败有明确降级；④ 播报期间麦克风不重复录到输出；⑤ 手机端布局可用；⑥ 不触及禁动模块、生产数据库、main 或 DNS。真实外部模型调用、公开部署和发布均需各自授权与证据；未运行标 NOT RUN。
