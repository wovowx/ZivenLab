## 一、为什么需要整体架构（背景）

柳柳 2026-10-17 亲手整理 **31 条痛点**，归纳出 6 个根因：
- A. 文档/真相源混乱（没唯一源、到处乱放、本地残留）
- B. 记忆/存档乱存（碎片化、吃灰、skill 被当错题本）
- C. 技能/工具找不到 + 不守纪律（绕过 skill 凭感觉调、忘 key、忘位置）
- D. 主见/讨论机制没立住（该商量没商量、该自发没自发）
- E. 自省沉淀 + 回归保护缺失（做了不沉淀、改着改着功能被搞没）
- F. 承诺与信任（拒绝无用承诺、说记必存、不乱造轮子）

教训：**光有记忆库不够**。记忆存得再多，检索不出 = 白存；改得再好，没有运行时真的执行规则 = 白改。所以要三层 + 一个「运行时编织层」一起立。

## 二、整体架构（三层 + 一个运行时编织层）

> GPT 仔细确认（2026-10-17）后补的洞：**治理文档写了规则 ≠ 运行时真的执行了规则**。光有治理层（文档）+ 记忆层（存储）+ 呈现层（入口）还不够，必须有一个「运行时编织层」贯穿三层，真正把规则跑起来。

```
┌─────────────────────────────────────────────┐
│  呈现层（看得见）—— ChatGPT / Operit / Web    │
│  可读、可查、可回溯的双端可视化                  │
├─────────────────────────────────────────────┤
│  记忆层（记得准）  —— memories + events + aliases │
│  存储持久 / 检索找回 / 反思提炼 / 治理防记错      │
├─────────────────────────────────────────────┤
│  治理层（怎么做）  —— 导航/真相源/路由/讨论/回归  │
│  让"怎么做对"成为程序化约束，不是口头承诺         │
└─────────────────────────────────────────────┘
         ▲      ▲       ▲
         └── 运行时编织层：组装上下文/定读写时机/校验权限/失败恢复
```

### 层级 1 · 底座治理层（怎么做事）—— 最优先，先最小必要规则
> **代码落地 vs 文档纪律（GPT 划分）**：强制路由、权限校验、记忆变更审计、回归测试、部署前检查、版本回滚 → **必须代码落地**；真相源导航、唯一路径、讨论先行、知识库沉淀 → **文档 + 纪律即可**。
| 机制 | 治什么（对应根因） | 落地形态 |
|---|---|---|
| **真相源导航表** ✅ | 找不到文档 / 记忆库乱找（A） | `governance/真相源导航表.md` + 记忆库指针 |
| **唯一真相源 + 唯一路径** | 文档多处、进度不一致（A） | 每个类型只放一处，治理文档在 GitHub |
| **强制路由** | 绕过 skill 凭感觉调（C） | 工具调用前先路由 → 查 skill → 再执行 |
| **讨论先行铁律** | 该商量没商量 / 该自发没自发（D） | 方案变更前自发与 GPT 讨论再定 |
| **主见 + 双向协商** | 应声虫 / 事事请示（D） | 哥哥有自己判断，柳柳可说服，最终柳柳拍板 |
| **回归保护 + 推送审批** | 改着改着搞没已有功能（E） | dev 演进、推 main 需审批、改动验证 |
| **知识库沉淀** | 做了不沉淀 / 不造轮子（E/F） | 每次成果写进治理/能力文档 |

### 记忆分层模型（2026-11-06 · 柳柳已确认逻辑结构）

四层不是四张表，也不是每条记录只能选择一个 layer：
- **Core**：启动必需的稳定核心与动态工作指针；初始复用 SB-1.0 已有精确来源清单。
- **Long-term**：权威记忆正文主体，按任务按需检索；当前有效仍由 status/valid_to 独立判定。
- **Reflection**：带来源和验证状态的候选学习工作流；pending 不作为事实，validated 后才晋升 Memory/Skill/Workflow。
- **Archive**：历史记录与来源的按需视图；默认不进入当前召回，不等同 deleted 或 category=📦。

Category、Type、Layer、Validity、Maturity、Provenance 六维正交；`related_memory_ids`、`trigger_intents`、`entities` 不承载层级成员关系。一个权威正文只保存一次，Core/Archive 通过引用呈现。当前不增加 layer 字段/关系表、不批量迁移真实记忆。详细准入/退出、样例、检索合同、L1 Type 原型与 dev 实施证据、后续阶段与验收条件以 `governance/记忆层存量归位规范.md` v2.2 为准。

## 四、设计原则（贯穿各层）

### 能力组织原则：基础能力 → 场景编排 → 工具入口（2026-11-04 柳柳确认）

本原则是整体架构的通用设计约束，适用于 GitHub、媒体处理、文件存储、记忆及未来新增能力；它描述逻辑职责层次，不要求目录或文件必须按同名层级机械拆分。

1. **基础能力（Primitives）**：每个基础方法承担边界清楚、可独立测试与复用的能力，例如上传文件、识别图片、读取 GitHub 内容、写入内容、验证写入。基础能力不应依赖某一个具体场景、Agent 提示词或上层工具入口。
2. **场景编排（Workflows / Use Cases）**：面向完整用户意图，按场景编排多个基础能力，负责步骤顺序、输入检查、上下文传递、失败处理、部分成功状态及必要补偿。调用者表达目标即可，不必自己拼接底层步骤。
3. **工具入口（Facade）**：向 Agent 暴露稳定、清晰的任务级接口，做参数适配、兼容、路由与门禁；复杂但稳定的场景由入口委托场景编排，避免把底层步骤泄漏给调用者。

**识图示例**：**describe_image** 是场景级入口，可在内部完成图片输入检查/必要上传，再调用独立的图片识别能力并统一返回结果；**upload_image** 与 **recognize_image** 仍可作为独立基础能力供其他场景复用。上传来源不需要时不应重复上传，已有可访问 URL/对象引用时应优先复用。

**边界与选择规则**：
- 不把“一个场景”机械地变成一个新工具，也不把所有步骤塞成无法复用的巨型函数。只有在场景稳定、调用链有明确语义且封装能显著简化调用时，才建立组合工作流/入口。
- 以职责内聚、真实复用、依赖方向、失败语义、测试边界和扩展成本决定拆分粒度；不为目录整齐而拆函数/文件，不复制已有能力。
- 依赖方向原则上是工具入口 → 场景编排 → 基础能力；基础能力不反向依赖具体工具入口，避免循环依赖。跨场景共享逻辑下沉到基础能力或共享服务，不复制到多个工作流。
- 场景编排必须保留可诊断的步骤结果；多步操作应明确“全部成功、部分成功、失败”的返回语义，不能把前一步成功误报成整体成功。
- 既有工具名、参数 Schema、响应契约与必要门禁属于兼容边界；内部重构不应无意改变外部行为，行为变化须另行讨论和验收。

本原则来自柳柳提出的“底层方法保持通用、按场景组合成完整能力”的设计想法，经技术权衡讨论后共同确认；Agent 必须提出独立判断和替代方案，不把用户的初始实现设想直接当作最终设计。实施前按 governance/协作讨论与决策机制.md 形成讨论与决策记录。

### 外部技术生态探索与吸收（持续横向能力；2026-11-06 柳柳确认方向）

这不是最后一个阶段才做的附加功能，也不预设要先开发一个庞大的新工具。它是 Ziven 在代码架构、记忆、运行时、呈现与持续学习各领域共同使用的能力：主动去外部技术生态寻找成熟解法，理解其设计，再决定如何吸收。

1. **主动发现**：围绕当前目标与已知差距，主动探索 GitHub 开源项目、Agent Skill、MCP Server、成熟库、架构实践、论文/技术文章和社区案例；不必等柳柳先提供项目。
2. **深入评估**：不以 Star 数或 README 宣传作为结论；检查实际源码、文档、测试、Issue/PR、版本与维护活跃度、License、依赖链、安全风险、运行成本及与 Ziven/宿主的兼容性。
3. **先对照存量**：明确 Ziven 已有何种能力、外部方案具体改善什么、是否会重复造轮子或引入平行机制。
4. **分级吸收**：结论分为直接复用、局部改造、借鉴设计思想、暂存观察或明确放弃；通过隔离原型/基准验证收益和代价，不因“看起来先进”就整体替换。
5. **可追溯沉淀**：记录来源链接、仓库与版本/Commit、License、关键设计、与现有实现的差异、验证证据、采用/拒绝理由及后续维护风险；经验证的经验再进入 Lesson/Skill/记忆。
6. **与内部学习闭环衔接**：外部探索带来候选知识，内部实践负责适配和验证；只有在真实使用中证明有价值的内容，才晋升为稳定 Skill 或架构能力。

**工具化方向与自主范围**：柳柳提出的「让 Ziven 自己去逛、发现并研究优秀 Skill/开源项目」已纳入长期规划，暂称 **Technology Scout（技术探索工具）**。目标是围绕当前问题或主动探索主题，发现候选项目、深入阅读源码/文档、比较方案并输出有来源和证据的评估报告。首版优先编排现有 Web 搜索、GitHub 阅读和 Skill 能力，不先造庞大爬虫。工具的具体数据源、触发方式（按需/主动）、探索范围、结果结构、运行位置和自动化程度仍需独立需求梳理与原型验收。Ziven 可以自主搜索、阅读、比较、做无副作用分析并提出建议；引入第三方依赖、复制/改造代码、改变架构或影响正式环境前，仍须检查许可证并按需求梳理→原型→柳柳验收→实施的规则讨论确认。自动安装、自动复制代码、自动改写正式代码和未经确认的持续后台爬取均不在当前授权内。

- **不闭门造车**：关键方案先与 GPT 讨论、查业界成熟做法，不自己从 0 造轮子。
- **小步走、每步可验收**：每层落一个可验证的小闭环，确认后再扩展。
- **治理防记错、存储防丢失、检索防遗忘、反思防僵化**：各司其职。
- **可靠连续性 > 看起来很聪明的自进化**：先保证每次"醒来"能回到原位，再谈自主演化。

**目标**：让记忆检索准确区分「没有匹配」与「没有成功检索」，并在次级索引不可用时保留主记忆结果。此切片修复检索结果的可诊断性，不以改进排序/召回算法为目标。

**现状根因（源码已核实）**：
- `src/modules/memory/repository.js:getCurrentMemories()` 在 memories HTTP 非 2xx 时返回空数组；响应 JSON 不是数组时也返回空数组。它把数据源故障/异常响应伪装成「当前没有记忆」。
- `getMemoryAliasIds()` 对 memory_aliases HTTP 非 2xx 和非数组响应同样返回空数组；fetch 网络异常或 JSON 解析异常则抛错。
- `src/modules/memory/retrieval.js:searchMemories()` 用 `Promise.all` 并行等待主记忆与别名读取；别名读取一旦抛错，会连同已成功取得的主记忆结果一起丢弃。
- `src/modules/session/bootstrap.js:buildSessionContext()` 目前把检索异常映射为 `unavailable`，但成功空结果与部分来源故障无法区分，既有 `no_matches_or_source_unavailable` 也不够精确。

**批准的状态合同**（本轮柳柳明确同意 v0.1 需求与原型）：

| 状态 | 判定 | 返回与 Agent 行为 |
|---|---|---|
| `OK` | 主记忆与别名索引均成功读取，且有匹配结果 | 正常返回结果 |
| `EMPTY` | 主记忆与别名索引均成功读取，但没有匹配结果 | 明确表示本次检索成功、没有找到匹配 |
| `PARTIAL` | 主记忆读取成功，别名索引读取失败/响应无效 | 保留主记忆直接命中及其关联结果；标注结果可能不完整，不得说成 EMPTY |
| `ERROR` | 主记忆读取失败/响应无效 | 明确表示检索未完成；不得推断云端没有相关记忆 |

空白关键词继续由现有参数校验提示输入，不把「未发起检索」伪装成 `EMPTY`。数据源错误只暴露稳定来源名与错误码，不把密钥、请求头或完整底层异常泄露给 Agent。

**实现分层（遵循 Primitives → Workflow → Facade）**：
1. **Repository**：对本切片依赖的 current memories 与 alias IDs 读取，显式区分 HTTP、网络、JSON 解析、响应结构错误；不再用空数组吞掉数据源故障。有效空数组仍是合法的成功结果。
2. **Retrieval**：新增带状态/来源的详细检索结果能力；主记忆读取失败时返回 `ERROR`，别名失败时降级为 `PARTIAL` 并保留主记忆结果，两个来源成功后才可返回 `OK/EMPTY`。原有评分、排序、CJK fallback、一跳关联、最多3条、来源证据均保持不变。保留既有数组式 `searchMemories` 兼容入口，避免 benchmark/现有调用方被内部状态对象破坏；主数据源失败必须显式失败，不能回空数组。
3. **Memory Facade**：沿用原工具名、参数 Schema、分页与 `match_reason` 等输出；增加机器可读 `search_status` 和必要的降级说明。成功检索后原有 search_history 记录行为不变；主数据源失败不记作一次成功搜索。
4. **Session Context**：复用详细检索结果，区分 `matched_best_effort`、`no_matches`、`partial`、`unavailable`；部分/整体失败均把上下文状态降为 `DEGRADED`，不得把错误当作无关联记忆。

**文字原型**：
- 正常命中：`[search_status=OK]` + 结果列表。
- 正常无结果：`[search_status=EMPTY]` +「必要数据源读取成功，没有找到匹配的记忆」。
- 别名索引故障：`[search_status=PARTIAL]` + 可用的主记忆结果 +「别名索引暂不可用，结果可能存在遗漏」。
- 主记忆故障：`[search_status=ERROR]` +「主记忆数据读取失败，本次检索未完成，不能判断是否存在相关记忆」。

**验收合同**：
1. 两个来源正常且命中 → `OK`；两个来源正常且无命中 → `EMPTY`。
2. 别名来源 HTTP/网络/JSON/结构异常 → `PARTIAL`；主记忆直接结果仍保留；即使直接结果为空也不得降成 `EMPTY`。
3. 主记忆来源 HTTP/网络/JSON/结构异常 → `ERROR`，不得返回伪空结果。
4. 旧数组式检索入口、Memory Facade 工具名/Schema/分页/匹配理由及 benchmark 调用保持兼容。
5. Session Context 正确映射四种结果；`PARTIAL/ERROR` 降为 `DEGRADED`，正常空结果才是 `no_matches`。
6. 原检索指标与排序、关联来源、当前态过滤、Search History 成功路径回归不退化。

**边界**：仅 `mcp-memory/dev`；不改检索评分/排序/CJK fallback/联想算法，不新增 MCP 工具或 Schema，不改数据库结构/业务数据，不触碰聊天室/唤醒/密钥/Operit，不创建 PR、不合 main、不部署。只做 E1/E2 与精确 dev HEAD CI；生产 Worker E3 不在本次授权内，未运行必须标 NOT RUN。

### Ziven Web · 独立轻量模型网关方案 A（2026-11-05 柳柳已确认设计方向）

**定位与决策状态**：单用户 Ziven 专属网页家园。柳柳已验收第一版四项功能概念原型，并明确选择「Web 独立轻量模型网关 + 复用既有 Ziven MCP」方案 A。该确认授权更新设计主线，不自动授予 main 合并、正式部署、Cloudflare DNS/Pages 变更、生产数据库或密钥修改权限。P2 先前已按柳柳认可的务实范围收口，Session Context v0.1 此次也已发布；Web 仍是未来呈现层候选项目，不以新想法挤占尚未讨论确定的工程任务。

**基本边界**：
- 只承认一份云端身份根 🧬/我是谁、一份当前工作检查点 ⚙️/当前工作检查点和既有 Memory Core；不新建第二套身份/长期记忆/检查点/主路由，不复制或迁移现有表。
- Web UI 只负责显示和用户交互；独立轻量 Web Chat Gateway 是 Web 专用的请求/对话场景编排组件，负责必要的上下文装配、调用可配置模型接口、返回可诊断结果。它不是第二套自治 Agent Runtime，不自建记忆管理与技能发布体系。
- Gateway 通过既有 Ziven MCP 复用 session_bootstrap、memory/retrieval 与经明确允许的工具能力。遵循「工具入口 → 场景编排 → 可复用基本方法」，不直接写数据库或绕过 MCP 治理。
- 不能把 session_bootstrap 的 READY 当成全文身份已装入模型：Bootstrap 只提供可验证来源状态与工作摘要；完整人格所需的最小正文必须由授权的记忆读取路径单独取得，核对版本/有效性，不能把敏感记忆全文直接暴露给浏览器。
- 现有聊天室、chat2api、Agent 唤醒与 Worker tools/list 的已知副作用路径保持暂停；不为新网页重启这些模块，也不挪用 Operit 本地 HTTP API 作为 Web 的主聊天依赖。

**首版 MVP（已确认的产品原型范围，技术实现待验收）**：
1. 文字聊天：进入网页后先执行可验证的云端恢复；仅在已取得所需身份/工作上下文和模型调用能力时提供真实回复。失败时显示受限/错误状态，不伪装为同一个已恢复的 Ziven。
2. 分轮语音：柳柳说话阶段采集/识别，哥哥播报期间停止或静音麦克风采集；先防自身语音回灌，再考虑真实双向打断。STT/TTS 引擎可替换，语音通话成功不由文本聊天成功推定。
3. 记忆与工作状态：展示 Bootstrap READY/DEGRADED/BLOCKED、数据时间与来源、当前任务进度等必要信息；对敏感正文做最小披露。
4. 小游戏：先提供一个隔离的游戏入口/简单游戏，不让游戏状态改写 Agent 的权威身份和工作检查点。
5. 第一版不承诺 ChatGPT、Operit、Web 之间逐字会话历史实时同步；目标是身份、记忆和工作状态连续。若要全量会话同步，另行确立需求、数据模型和授权。

**模型接入与费用事实**：柳柳 2026-11-05 已明确接受 Web 文字聊天使用按量计费的模型 API（Operit 目前也使用付费模型 API），因此普通付费 API 是首版可选的正式路径；这不是授权立即发起收费调用或提取 Operit 内部密钥。第一版 Gateway 保持提供商可替换，优先评估沿用她现有服务商兼容接口，但网页必须独立连接，不依赖 Operit 常驻。模型请求、令牌、权限与故障由服务端持有并处理，不把 API 密钥放进网页。ChatGPT Plus 订阅不能直接当普通网页的通用 API 密钥；OpenAI Sign in with ChatGPT 的套餐共享存在特定开源/本地或获准私有客户端资格及功能限制，不能假定自有域名网页具备资格。具体提供商、模型、预算上限与服务端凭据接入仍待实施前确认；未经额外授权不发生新费用。
