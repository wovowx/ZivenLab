## 一、为什么需要这两张表（背景）

整体架构记忆层的目标不是多存，而是记得准、想得起、可追溯、当前唯一。单靠 KV 记忆库做不到三件事：
1. 追溯：记忆被改/被删，改前是什么、谁改的、为什么——没有账本。
2. 当前有效唯一判定：一条记忆被纠正后，怎么知道当前该信哪条。
3. 防误改误删：没有只追加、禁改删的事件表，意外覆盖就永久丢了。

这两张表就是治这三点的最小骨架。

## 二、表 1：memories（当前记忆状态）

职责：只存「当前有效」的记忆。被纠正/废弃就在此更新 status+version，旧版本指向 supersedes_id，而不是删掉。

> 实际落地：沿用现有 `memories` 表（`key`/`value`/`category`/`title`），在其上加 version/status/supersedes_id/source_ref/valid_from/valid_to/type（2026-10-17 升级，无损——旧数据保留，新列默认 status='active'、version=1、valid_from=now()）。

字段（现有 + 新增）：
- id uuid 主键
- key text 记忆键（语义标识）
- value text 记忆内容
- category text 分类（🧬/💕/📦/⚙️ 等）
- title text 标题
- type text fact/quote/inference/agreement（新增）
- status text active/superseded/revoked（新增，默认 active）
- version int 版本号（新增，默认 1，乐观锁防覆盖）
- supersedes_id uuid 被替代的记忆ID（新增）
- source_ref text 原始来源引用（新增）
- valid_from timestamptz 有效开始（新增，默认 now()）
- valid_to timestamptz 有效结束（新增，空=当前有效）
- created_at timestamptz
- updated_at timestamptz

当前有效判定：status='active' AND valid_to IS NULL。

---

## 三、表 2：memory_events（追加式事件账本）

职责：只追加、永不删除修改的事件流水。每次 create/update/revoke/restore 记一条。

字段：
- id uuid 主键
- memory_id uuid 关联记忆
- event_type text create/update/revoke/restore
- actor text user/agent/system
- idempotency_key text 唯一 幂等键防重复入账
- version int 对应变更后的记忆版本
- old_value jsonb 变更前
- new_value jsonb 变更后
- reason text 变更原因
- source_ref text 来源引用
- created_at timestamptz

---

## 四、硬约束（GPT 强调）

1. memory_events 禁止 UPDATE/DELETE，只能 INSERT。
2. 记忆变更与事件追加同一事务。
3. 版本号+乐观锁防并发覆盖（WHERE version=X）。
4. supersedes_id+status+valid_from/to 实现当前有效唯一判定。

  ADD COLUMN IF NOT EXISTS valid_to timestamptz;

### 5.2 memory_events（新建 · 2026-10-17 已执行 ✅）
```sql
CREATE TABLE memory_events (
  id uuid primary key default gen_random_uuid(),
  memory_id uuid not null references memories(id) on delete cascade,
  event_type text not null,
  actor text not null,
  idempotency_key text unique,
  version int default 1,
  old_value jsonb,
  new_value jsonb,
  reason text,
  source_ref text,
  created_at timestamptz default now()
);
-- 硬约束①：追加式账本，禁 UPDATE/DELETE（触发器，2026-10-17 已加 ✅）
CREATE OR REPLACE FUNCTION prevent_memory_events_modify() RETURNS trigger AS $
BEGIN RAISE EXCEPTION 'memory_events is append-only: UPDATE/DELETE forbidden'; END;
$ LANGUAGE plpgsql;
CREATE TRIGGER trg_memory_events_append_only
  BEFORE UPDATE OR DELETE ON memory_events FOR EACH ROW
  EXECUTE FUNCTION prevent_memory_events_modify();
```

> 端到端验证（2026-10-17）：①账本 INSERT 可写 ✅ ②UPDATE/DELETE 被触发器拦 ✅ ③真实追溯——一条记忆完整生命周期 create(v1)→update(v2) 带 actor/reason/version/时间 可逐条查回 ✅ ④当前有效判定 `status='active' AND valid_to IS NULL` 实测成立 ✅

### 5.3 memory_aliases（多钥匙检索入口 · 2026-10-18 已执行 ✅）

**职责**：一条记忆补多个检索入口（项目名/简称/技术名），解决「想不起 key 也能找到」。GPT 建议（2026-10-18）：「memories 存事实，memory_aliases 存检索入口，memory_events 存变更历史」，三者职责分开。

```sql
CREATE TABLE memory_aliases (
  alias text not null unique,
  memory_id uuid not null references memories(id) on delete cascade,
  created_at timestamptz default now()
);
-- 检索改进：status 索引（2026-10-18 已加 ✅）
CREATE INDEX IF NOT EXISTS idx_memories_status ON memories(status);
CREATE INDEX IF NOT EXISTS idx_memories_status_key ON memories(status, key);
```

> 多钥匙检索流程：先关键词 search 查 content/key → 再匹配 memory_aliases.alias → 合并 memory_id → 统一过滤 status='active'（当前有效）。

> 验证（2026-10-18）：建表 ✅；索引 ✅；给「对GPT自称规则」补别名「怎么称呼GPT」「公共区自称」→ 用别名查到关联记忆 ✅（多钥匙链路通）。

## 六·type 分类规则（2026-10-18 落地 · 上下文组装数据准备）

**用途**：让「上下文组装」能区分事实/原话/推断/约定，不把推断当事实（整体架构运行时编织层要求）。

**四类 type 定义（GPT，2026-10-17）**：
- `fact`：事实/记录/技术结论/文档指针
- `quote`：柳柳原话/语录（定案原话，可复述）
- `inference`：哥哥的推断/判断（须标注依据）
- `agreement`：规则/约定/铁律/柳柳拍的偏好

**分类映射（按 category 前缀自动推断，柳柳 2026-10-18 拍板方案 A）**：
- ⚙️/📦/📋/📝/🔥/🎭/chatroom-*/mcp-memory/release-guard/chat2api/github-edit/deploy/治理记录/lesson → `fact`

- 💕关于柳柳·附录-语录 → `quote`
- 💕日常对话归档 / 💕0822换框交接 / 默认类（事件/记录/需求）→ `fact`
