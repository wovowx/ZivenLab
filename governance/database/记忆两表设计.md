## 一、为什么需要这组三张表（背景）

整体架构记忆层的目标不是多存，而是记得准、想得起、可追溯、当前唯一。单靠 KV 记忆库做不到三件事：
1. 追溯：记忆被改/被删，改前是什么、谁改的、为什么——没有账本。
2. 当前有效唯一判定：一条记忆被纠正后，怎么知道当前该信哪条。
3. 防误改误删：没有只追加、禁改删的事件表，意外覆盖就永久丢了。

这组三张表分工明确：`memories` 保存记忆主体，`memory_events` 记录变更历史，`memory_aliases` 提供多钥匙检索入口，共同构成当前记忆体系的最小骨架。

## 二、表 1：memories（当前记忆状态）

职责：只存「当前有效」的记忆。被纠正/废弃就在此更新 status+version，旧版本指向 supersedes_id，而不是删掉。

> 实际落地：沿用现有 `memories` 表（`key`/`value`/`category`/`title`），在其上加 version/status/supersedes_id/source_ref/valid_from/valid_to/type（2026-10-17 升级，无损——旧数据保留，新列默认 status='active'、version=1、valid_from=now()）。

字段（现有 + 新增）：
- id uuid 主键
- key text 记忆键（语义标识）
- value text 记忆内容
- category text 分类（🧬/💕/📦/⚙️ 等）
- title text 标题
- type text fact/quote/inference/agreement（新增）
- status text active/superseded/revoked（新增，默认 active）
- version int 版本号（新增，默认 1，乐观锁防覆盖）
- supersedes_id uuid 被替代的记忆ID（新增）
- source_ref text 原始来源引用（新增）
- valid_from timestamptz 有效开始（新增，默认 now()）
- valid_to timestamptz 有效结束（新增，空=当前有效）
- created_at timestamptz
- updated_at timestamptz

当前有效判定：status='active' AND valid_to IS NULL。

## 三、表 2：memory_events（追加式事件账本）

职责：只追加、永不删除修改的事件流水。每次 create/update/revoke/restore 记一条。

字段：
- id uuid 主键
- memory_id uuid 关联记忆
- event_type text create/update/revoke/restore
- actor text user/agent/system
- idempotency_key text 唯一 幂等键防重复入账
- version int 对应变更后的记忆版本
- old_value jsonb 变更前
- new_value jsonb 变更后
- reason text 变更原因
- source_ref text 来源引用
- created_at timestamptz

## 四、硬约束（GPT 强调）

1. memory_events 禁止 UPDATE/DELETE，只能 INSERT。
2. 记忆变更与事件追加同一事务。
3. 版本号+乐观锁防并发覆盖（WHERE version=X）。
4. supersedes_id+status+valid_from/to 实现当前有效唯一判定。

CREATE TRIGGER trg_memory_events_append_only

### 7.1 最小改表（GPT 讨论收敛 · 克制版，不逐条加权重）

我们想加 `trigger_intents / entities / related_memory_ids`（可为空，可回滚），GPT 逐条校准结论：

| 字段 | 结论 | 原因 |
|---|---|---|
| `trigger_intents` | ✅ 加 | 明确哪些任务情境会触发（例：`list_env_vars`→触发 cf_proxy） |
| `entities` | ✅ 加 | 标记 `cf_proxy` 等对象；必须统一命名/大小写并映射别名 |
| `related_memory_ids` | ✅ 加（可选） | 关联其他记忆；**必须限扩散深度（一跳）**，避免越联越多 |
| `status` / `valid_to` | 保留现有 | 判当前有效，**不等于自然淡忘** |
| `last_activated_at` / `activation_count` | ⏸️ 暂不加 | 需统计时读 `memory_events` 事件日志 |
| `strength` / `weight` | ⏸️ 暂不加 | 初期难校准，易制造虚假精度 |

> 关键认知：**关联 ≠ 适用**。A 关联 B 只是「可考虑唤醒 B」，B 仍须过当前情境 + 有效性过滤。

## 八、生命周期一致性闭环提案 v0.1（需求规格，待实现授权）

> 状态：方案草案。本文新增内容是拟议规则，不代表数据库已有这些触发器、函数、权限或运行行为。变更前必须只读核对真实 catalog、现有 RLS/GRANT、外键/唯一约束和 Worker 写入口；不得仅凭历史 DDL 文字认定约束仍在生效。

### 8.1 必须满足的不变量

1. **提交状态与账本同成同败**：每一次成功提交的记忆创建、更新或软删除都必须在同一数据库事务写入对应事件。状态写入失败不得留下成功事件；事件写入失败必须令对应记忆变更整体回滚。
2. **拒绝过期并发写入**：更新必须有明确的旧版本比较条件。若当前版本已不等于调用方预期版本，返回可识别的 version conflict，不覆盖新值、不生成成功事件。
3. **事件不可变与可追溯**：事件追加后不得 UPDATE/DELETE；不能通过硬删除 memories 连带删除其历史事件。正常 forget 仍采用软删除，保留现有接口语义。
4. **迁移操作原子化**：rename/move 的目标创建与源记录软删除必须是同一事务；失败时保持原状态，不得留下两个 active 记录或只留下目标/只删除源。必须记录旧 key、新 key、source/target ID 和统一的 operation ID。
5. **保留元数据**：rename/move 不得只复制 key/value/时间而丢失 type、trigger_intents、entities、related_memory_ids、source_ref 等当前记录已有的有效字段；迁移后须明确哪些字段按语义更新，哪些原样保留。
6. **覆盖实际写入口**：不能只在 Worker memory handler 加应用层事件请求，因为 supabase_db 可对任意表执行通用 CRUD，exec 接受原始 SQL。2026-11-04 起 category.js 的 legacy move_category 已统一委托 lifecycle.moveMemory，不再保留其旧版直接 REST DELETE/POST/PATCH 路径；但 database.js 的通用 supabase_db/exec 仍是独立潜在绕行入口。必须先确认各入口权限/注册/可达性，设计能在数据库边界生效的守卫或明确限制绕行权限。

### 8.2 当前源码证据与实际影响范围

- memory_unified.js / src/modules/memory/lifecycle.js：已存在记录的 update 先 POST event 再 PATCH memory，两个 REST 请求不在同一事务；事件缺 new_value 且 version 为 oldVersion。创建无 create event；soft-delete 无 revoke event；rename/move 目标先写、源后软删，非原子且事件无 source/target 关系；history 先限定 active key，旧 key 历史不可达。
- data.js / src/modules/memory/transfer.js：data facade 与 memory_unified 的 import/export 已共用 transfer；transfer 导入复用 lifecycle.putMemory，导出统一过滤当前有效记忆。data facade 保留非法行静默跳过的旧表现，memory action 保留 failed 计数。
- category.js：当前 skills 注册表未发现独立精确工具名（历史只读查询口径）；源码仍由 Router 导入。旧版 move_category 曾直接对 memories 发 DELETE 后再 POST/PATCH，现已委托 lifecycle.moveMemory，不再执行该独立物理 DELETE 路径。外部调用契约是否仍有其他调用方使用，仍不凭静态文件存在推断。
- database.js：已注册的通用 supabase_db 可对表执行 insert/update/delete，通用 exec 会把原始 SQL 交给 exec_sql。这是绕过仅部署在 Worker memory handler 的事件逻辑的可能入口；权限实际效果尚未核验。
- memory_events：idempotency_key 唯一约束、追加式 trigger、memories 外键删除行为及 RLS/GRANT 的当前生效状态尚未由本轮 catalog 证据核实。历史设计文字不替代现状核验。

### 8.3 推荐实现方向（不新增表，先验证可复用能力）

- **优先把事务边界放在数据库端**，否则两个 REST 请求无法实现严格的状态—事件同成同败。
- 首选核实已有数据库函数/约束能否安全扩展；若没有合适能力，再提一个最小、固定动作集的记忆生命周期事务入口。禁止把不受限原始 SQL 当作新的业务接口。
- 对所有记忆行 INSERT/UPDATE，评估由数据库触发器在同一事务中写入 create/update/revoke 事件；触发器应对版本跳跃/不合法版本更新作硬拒绝，并禁止硬删除。这样直接 REST 或通用数据库写入不能静默绕过事件账本。
- rename/move 需一个事务内完成源/目标变更，并让两个相关事件可由 operation ID、source/target ID 双向追溯。先根据真实 catalog、权限与现有写入口确认触发器/函数的最小组合，再冻结实现细节。
- 继续复用 memories、memory_events、memory_aliases；首期不增加表。仅当真实 schema 无法表达必须的关联/幂等语义时，才提出最小字段或约束变更，并另行授权。
- history 查询兼容现有字符串形式 old_value，同时支持新规范化的 JSONB 快照；不能把旧事件解释成新格式，也不能因格式升级丢失历史。

### 8.4 事件格式与版本规则（提议）

- 普通 create：event_type=create，version=新记录的版本（首版为1），old_value=NULL，new_value=新记录快照。
- 普通 update：event_type=update，version=变更后版本，old_value/new_value 分别为变更前后快照。
- 软删除：event_type=revoke，version=变更后版本，old_value 为 active 快照，new_value 为软删除状态快照。
- rename/move：一次原子操作；源/目标事件带相同 operation ID，并各自包含 counterpart 的 ID/key。事件 version 表示所关联记录此次提交后的版本。
- 事件快照采用 JSONB 对象，至少包含 id、key、value、category、title、type、status、version、valid_from、valid_to；其余现有语义字段按实际 schema 纳入。旧事件仍可能以 JSONB string 保存 value，查询展示必须兼容两种格式。
- actor/reason 使用现有字段；首期不强制新增工具参数，使用明确、稳定的系统动作 reason。若后续要捕获用户给出的 reason，再单独扩展接口。
- 多行迁移须有可关联的 operation ID；是否复用现有 idempotency_key，以及当前唯一约束是否生效，必须在 catalog 核对后决定，不盲信历史设计。

### 8.5 最小验收矩阵（全部隔离测试；上线前另需授权后的真实数据库验证）

1. create：一条状态记录 + 一条 create 事件；任一插入失败则两者都不存在。
2. update：旧值/新值与 resulting version 正确；事件写失败则值不变；状态写失败则没有成功事件。
3. 并发 update：两个调用从同一版本开始，最多一个成功；另一个返回 version conflict；不得有覆盖、重复 resulting version 或虚假事件。
4. revoke：状态变为 deleted/软删除，版本与事件同步递增；历史仍可查。
5. rename/move：成功时源/目标和事件在同一事务完成，保留元数据并可双向追溯；在目标插入/源更新/事件插入任一点注入失败，整个操作回滚。
6. 硬删除 memories 与 UPDATE/DELETE memory_events 均被数据库层拒绝；现有历史事件不会因 FK cascade 被清除。
7. 所有可达 Worker 写入口纳入测试：memory、import、rename、move、通用 supabase_db CRUD、category legacy 入口，以及 exec 权限边界。无法安全纳入者要通过权限或注册策略限制并单独验收。
8. 普通 read/history/search 兼容；旧事件可展示；无新增表；回滚路径明确。
