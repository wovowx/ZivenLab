## 一、为什么需要测试集（背景）

> GPT 反复强调：**记忆存得再多，检索不出 = 白存**。

哥哥一直有记忆库（memories 表 180+ 条），但从未验证「提问→能召回对的那条」到底做得好不好。凭感觉以为能搜到，实际（2026-10-17 实测）很差——问技术配置召回的是换框杂项，问午餐召回的是语音存档。不建测试集，这个病永远看不见。

**测试集的目的**：给「检索质量」一把可量的尺子，改一次测一次，防退化（回归测试）。

## 二、5 项核心指标（GPT 给）

| 指标 | 问什么 | 含义 |
|---|---|---|
| Recall@K | 该找回的，进没进前K？ | 漏不掉该有的 |
| MRR / 排名 | 正确那条排第几？ | 别让对的沉底 |
| 误召回率 | 拿错的当答案的比例 | 别用无关的糊弄 |
| 关联依据准确率 | 关联结果能否指出来源 key、关联理由与共同实体？ | 不把一跳关联伪装成原始文档引用；原话/source_ref 核验不属于 v0.1 |
| 过期命中率 | 旧版还当当前事实吗？ | 别信被纠正过的 |

## 三、3 类压力测试（GPT 给）

### ① 能找到（该命中）
用不同说法问同一件事，看能不能召回正确那条：
- 别名 / 换措辞 / 模糊描述

### ② 不该命中（该拒绝）
问一件不存在的事，看会不会**编造**（不该命中却乱给）：
- 应当诚实「没有」，不硬凑相似记忆当答案

### ③ 新旧冲突（改了要认新版）
记忆被纠正过多次后，正常 search 应返回**当前有效版本**；若需查看旧版，再通过 history action 单独追溯，不把过期版混入当前结果：
- 验证 `status=active AND valid_to IS NULL` 判定生效；旧版由 history action 单独查询

## 五、怎么跑 + 判定

1. 本节记录的是早期人工验收流程：可用 `query_memory` 或 `memory` 工具 search 对照观察；普通 `memory.search` 会写入既有 search_history。
2. 对每条：看是否正确命中（①）/正确拒绝（②）/返回当前有效版（③）。v0.1 自动基准不走此 Facade，直接调用 searchMemories 并使用 GET-only Mock。
3. 统计 5 指标：Recall@K / MRR / 误召回率 / 来源准确率 / 过期命中率。
4. **改检索机制后必跑一遍**（回归），退化即回滚。

## 七、当前代码事实与历史结论校正（2026-11-05）

本节以 **mcp-memory/main v6.41.0、main SHA 5e4cf739a5ffd21c0434db96217267edb2af57bd、Cloudflare Worker #535** 的源码为当前基线；不是生产端到端检索 E3 结论。

1. repository.js 的 getCurrentMemories 同时请求 status=eq.active 与 valid_to=is.null，并在返回后再次用 isCurrentMemory 过滤。
2. retrieval.js 的直接候选考虑 key phrase、value/combined phrase、全部拆分词、alias、trigger_intent、entity；按匹配分数排序，同分再按创建时间排序。
3. 只有直接候选为零时，才启用受约束的中文 CJK bigram fallback；不是所有查询一律走 n-gram。
4. 有直接命中后才扩展一跳关联：先显式 related_memory_ids，再共享具体业务实体；关联最多3条、去重、当前有效过滤，直接结果始终排在关联结果前。
5. 关联结果带 _match.reason、related_from_key，共享实体还带 matched_terms。现有 Facade 会把这些信息格式化显示。
6. memory.search Facade 还会调用 recordSearchKeyword 写入既有 search_history。因此新基准直接调用 searchMemories 原子检索方法，不调用 Facade，避免把既有搜索历史写入混进测试，也不触碰业务记忆。

**对 v1.5 的校正**：上节 2026-11-04 手工复测的7条查询结果仍是当时真实宿主观察，保留为历史证据；但该节最后关于当前源码仍采用 keywords.every、只按 created_at 排序的判断，已不适用于 v6.41.0。当前代码已有匹配评分、别名/情境线索、CJK fallback 和一跳关联，不能再以旧实现描述现状。

## 八、记忆检索质量基准 v0.1（文字原型 · 待柳柳验收）

### 8.1 目标与边界

目标：建立一套**确定性、可重复、可比较**的质量基准，回答“该找的有没有找回、排位如何、无关内容有没有混入、旧记忆有没有冒充当前记忆、关联依据是否正确”。

v0.1 只评估当前 Memory Core 的 searchMemories 检索原子能力，不改检索算法、不改数据库、不新增 MCP 工具或模型服务。

- 测试数据：完全合成的记忆记录，不复制柳柳私人记忆正文，不从 Operit/聊天记录导入真实数据。
- 执行方式：Node 本地测试 + globalThis.fetch Mock；所有 Mock 请求必须为 GET。
- 生产边界：不连真实 Supabase、不读写生产记忆、不调用普通 memory.search Facade、不产生 search_history 写入。
- 宿主边界：不要求 Operit 执行，不消耗 Operit Token；E3 生产/宿主实测不属于 v0.1。
- 范围边界：不测 query_memory 向量/语义通道，不做时序/情绪联想、时间衰减、图谱、星球 UI 或数据库结构改动。

### 8.2 数据集结构

建议新增合成 Fixture：tests/fixtures/memory_retrieval_benchmark_v0_1.json。

Fixture 分为三部分：
1. memories：约10–14条合成记忆，包含当前记录、过期记录（valid_to非空）、软删除记录（status=deleted）、明确一跳关系、共享业务实体、只有通用称谓的干扰项、完全无关项。
2. aliases：少量合成别名，至少一条别名可在原始 key/value 不出现查询词时命中目标记忆。
3. queries：约14–16条固定查询，每条声明 id、query、kind、expected_direct_ids、expected_association_ids、forbidden_ids，以及适用时的预期匹配理由/关联来源。

首批查询覆盖：

| 用例 | 示例查询 | 预期验证 |
|---|---|---|
| Q01 精确 key | 网关选型 | 目标直接命中，reason=key_phrase |
| Q02 value 短语 | 当前网关方案采用独立模型网关 | 短语命中 |
| Q03 多词 | chat2api timeoutMs | 全部拆分词命中 |
| Q04 别名 | 长问题超时参数 | 通过 alias ID 命中，不依赖原文含该词 |
| Q05 情境触发 | list_env_vars | trigger_intent 命中 |
| Q06 实体 | cf_proxy | 明确实体命中 |
| Q07 中文长句 | 边缘网关部署日志需要保留完整请求链路以及超时诊断 | 仅在直接候选为空时走 CJK fallback；使用纯合成文本 |
| Q08 负向拒绝 | 昨晚看的火星电影叫什么 | 不存在记录时返回零命中 |
| Q09 近似干扰 | 网关选型后我昨晚看的火星电影 | 不能因少量重叠词就误召回；查询额外字符确保 n-gram 覆盖低于回退阈值 |
| Q10 新旧冲突 | 网关方案 | 当前版本命中，过期旧版不得出现 |
| Q11 仅旧记录 | 旧网关方案 | 只有过期/删除记录时应零命中 |
| Q12 显式关联 | 网关选型 | 直接命中后补一跳 ID 关联并标来源 key |
| Q13 共享实体 | 网关选型 | 共享具体业务实体的记忆可补充并标出实体 |
| Q14 通用实体干扰 | 网关选型 | 仅共享柳柳/哥哥/Ziven/项目等通用称谓不能建立关联 |
| Q15 关联上限 | 网关选型 | 去重、最多3条关联、直接命中永远在前，超额候选不出现 |

Q12–Q15 可以复用同一组 fixture，但各自保留独立断言，避免一个宽泛断言掩盖不同缺陷。

### 8.3 指标定义

**直接召回与排序**（只统计直接命中，关联结果不得抬高直接召回成绩）：
- Recall@1 / Recall@3：所有正向查询的 expected_direct_ids 中，有多少进入前1/前3条直接结果。
- MRR：每条正向查询第一个正确直接结果的倒数排名取平均；未命中记0。
- Direct Precision@3：前3条直接候选中，属于该查询 expected_direct_ids 的比例；其补数作为直接误召回占比。

**拒绝与有效性**：
- Negative False-Hit Rate：负向查询中出现任意直接命中的查询数 / 负向查询总数。
- Stale Hit Rate：新旧冲突/仅旧记录用例中，返回任意 expired/deleted ID 的查询数 / 这类用例总数。

**关联质量**：
- Association Recall@3：预期关联 ID 中，实际在最多3条关联结果里找回的比例。
- Association Provenance Accuracy：实际返回的关联结果中，reason、related_from_key 与（共享实体场景）matched_terms 均符合 Fixture 预期的比例。

说明：当前 Facade 暴露的是关联来源 key、关联理由与共同实体；并不把原始文档 source_ref 作为完整可见引用。因此 v0.1 的“来源准确率”严格限定为**关联依据可追溯准确率**，不冒称原始文档/原话来源核验。

不把这些指标压成一个任意加权总分；每项单独报告，避免权重掩盖退化。

### 8.4 CI 硬合同与基线策略

首轮运行先建立当前 v6.41.0 检索代码的实测基线；在得到真实数字前，不预设 Recall/MRR 的任意百分比门槛。

以下不变量从 v0.1 起就是 CI 硬门槛：
1. 负向查询不得出现直接误命中。
2. expired/deleted 记录不得进入直接或关联结果。
3. 直接结果全部排在关联结果之前。
4. 关联结果总数不超过3条，且 ID 不重复。
5. 每条关联结果必须有正确的 related_from_key 与理由；共享实体关联还必须给出正确共同实体。
6. 仅共享通用称谓不得建立关联；没有直接命中不得凭空扩展关联。
7. 测试期间所有请求均为 GET，不允许 POST/PATCH/DELETE。

首轮基线记录后，将确定性指标写入版本化 baseline 文件；后续改动以该基线做非退化比较：Recall@K/MRR/Precision/来源准确率不得下降，负向误命中率/过期命中率不得上升。若未来主动调整目标阈值，必须记录原因并经讨论确认，不通过悄悄改 Fixture 降低标准。
