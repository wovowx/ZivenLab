# 协作讨论与决策机制

> **一句话**：讨论不是为了得到答案，而是为了确保答案不是某一个人的答案。
>
> 本文件 = 怎么讨论、怎么判断讨论是否有效、讨论产物必须带什么、谁有权决定执行。
> 配套：协作协议 v4.2（总规则）→ 本文件（行为规则）→ action_guard（未来 Runtime 实现蓝图）。
> 状态：**confirmed（2026-09-04 柳柳拍板）**。

---

## 1. 核心原则

> **讨论的目标不是获得同意，而是共同降低方案不确定性，直到双方对执行边界达成一致。**（协作协议 v4.2）

> **分析可以委托，决定不能转让；方案可以共创，执行权不能自授。**（2026-09-04 讨论收敛）

**设计来源**（为什么会有这份文件）：
- 知识存在但未进入生效路径（写了协议，但行为没被触发）
- 讨论标准存在但未被使用（有定义，遇到事却走了「找答案→输出」路径）
- Proposal 被当成 Decision（GPT 回复 ≠ 授权执行）

---

## 2. 什么是讨论

### 定义

> 讨论 = 在做决定之前，把自己的判断拿出来，让其他参与者真正影响它，最后形成一个经过共同修正的方案。

### 判断标准（一问现形）

> **如果没有另一个参与者参与，我最后的方案会不会一样？**

- **会一样** → 那是咨询 / 请教 / 汇报，不是讨论。
- **不会一样** → 那才是讨论。

### 讨论的意思

> 讨论不是为了获得答案，而是**确保答案不是某一个人的答案**。

所以柳柳要的永远是一份**产物**，但必须是「经过两者碰撞后的产物」——不是「单方面丢问题给 GPT，再自己整理转述」。

---

## 3. 什么不是讨论（反例）

❌ 把问题丢给 GPT，然后自己整理答案回给别人。

❌ 把 GPT 的回复转述成「共同方案」。

❌ 自己写完方案，让别人盖章。

❌ 收到意见，但没有改变方案、也没有记录为什么不改。

❌ 先让 GPT 说，然后自己整理给柳柳（顺序换了一样不是）。

> 共同点：**讨论闭环里只有一个人的判断，另一个人的输入没有真正影响产出。**

---

## 4. 讨论产物要求（必须带「讨论痕迹」）

> 不靠检查「当时有没有讨论」，靠要求产物必须携带**可追溯的讨论痕迹**——没痕迹，不能叫讨论后的成品。

### 一个「讨论后的方案」必须能回答

| 字段 | 说明 | 表字段 |
|---|---|---|
| 原始想法 | 我最初想怎么做 | initial_position |
| 关键挑战 | 参与者提出了什么不同/风险/补充 | challenge_points |
| 发生变化 | 方案哪里因此变了（或证明为何不变） | changes_made |
| 未采纳意见 | 哪些意见没采纳、为什么 | （rejected 记录） |
| 最终方案 | 当前版本是什么 | final_proposal |

### 关键：不是「必须变化」，是「必须被解释」

真讨论也可能是：
> 挑战「权限是否过大」→ 分析「当前需求无写入风险」→ 决定「保留原方案」。

这也是讨论，因为它留下了 **挑战 → 响应 → 决定** 的轨迹。

> 写不出「因此发生的变化」或「为何不变」= 没有可证明的讨论 = 只能标「转述」，不能交付。

## 5. 决策与执行分离

### 三层，永远不混淆

```
讨论（Proposal）    GPT/Ziven 讨论产物，不进入执行
        ↓
确认（Decision）    柳柳作为目标与约束的共同定义者，参与形成并授权
        ↓
执行（Execution）   Runtime 根据 Decision 授权；无 Decision 拒绝
```

### 对应存储

- `discussion_evidence` 表：存「为什么这样改」（讨论痕迹）
- `decision` 表：存「谁授权这样改」（柳柳确认，status=confirmed）
- `execution` 表：存「具体执行动作」（挂 decision_id）

> **讨论证明 ≠ 授权**。GPT 和 Ziven 讨论一小时，柳柳说「不采用」= 不执行。

### 谁必须进入讨论（触发边界）

| 需要讨论（必须带痕迹） | 不需要讨论（直接做） |
|---|---|
| 改变系统行为 | 修明显 bug（不改变设计） |
| 改变权限 | 格式调整 / 文档 typo |
| 改变数据结构 | 测试补充 |
| 改变长期规则 / 工作流 | 已确认方案的实现细节 |
| 改变 Agent 能力边界 | 按钮间距这类体验微调 |

> 判据：**这个动作会不会改变系统未来怎么运行。**

## 6. 系统实现方向（action_guard 蓝图）

> ⚠️ 本节是**未来 Runtime 实现蓝图**，不是「当前系统已拦截」的事实。

### 核心思想（与 release_guard 同款）

> 不做提醒工具，做「让没有讨论证据的结构性执行在系统里没有合法入口」。

### 分层

```
action_guard（执行闸门层）
├── release_guard（发布纪律）
└── discussion_guard（决策依据）
```

### discussion_guard 逻辑（只查不判）

```
执行前检查：
  是否存在 decision.status == confirmed
  且 decision.scope 匹配该 action
有 → 放行
无 → 阻断：「No confirmed decision for this action. Create discussion before execution.」
```

> guard 只查「有没有记录」，不判「讨论质量」——那属于人的判断领域。

### 三段职责（不可互替）

```
Runtime 发现缺失 → 自动阻断（不会忘）
Agent 还原讨论事实（不能伪造：evidence 引用 source/commit/PR）
柳柳 确认授权（Decision，不是盖章）
```
