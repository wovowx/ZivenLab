## 一、优化建议库（缺口 12）

**目标**：柳柳 / 哥哥 / GPT 的建议**统一归档、来源可查**，已确认执行的进待办链，不丢、不搞成第二个待办系统。

**统一归口**：记忆分类 **⚙️**（与待办/约定同区），key 统一前缀 **`建议·`**；重大/成体系建议另开 ZivenLab `governance/` 文档并在本库留索引。

**标准动作**：
1. **当场收录**：任何来源的建议当场存 `⚙️/建议·<主题>`（此为**归档与来源记录**，不等于批准执行）。
2. **判定去向**（三选一）：
   - 已确认纳入当前项目执行 → 进待办链 `governance/当前项目状态.md`，标注来源（谁/何时/依据）。
   - 纯想法、尚未确认 → **不自动进待办**，留存在建议记录里。
   - 需共同设计 / 将改变系统行为、权责、数据结构 / 长期工作流 → **进既有讨论与确认流程**（Proposal→Decision），不另设 candidate 池。
3. **查重**：同一建议先查重，有 → 更新原档，不新建散档。

**红线**：`⚙️/建议·` 只当「归档+来源」，不当待办系统；建议收录 ≠ 批准执行；需设计/改变行为的走讨论机制，不在本文另造候选池。

## 二、复盘链条（缺口 13）

**目标**：**遇问题 → 复盘 → 更新 链条不断裂**，复盘有沉淀、可再应用。

**复盘五问（检查清单，任何修复/踩坑后问一遍）**：
1. 发生了什么（事实，不补脑）
2. 根因是什么（说清「为什么」）
3. 怎么修复的（可复现步骤）
4. 影响范围（功能/其他机制有没有被牵扯）
5. 如何防再犯（转纪律 / lesson / 代码硬校验 / 回归测试）

**沉淀与再应用（引用既有闭环，不另造一套 lesson 系统）**：
- 复盘 → 按**既有 lesson 规范**落一条 `⚙️/lesson-<主题>`（字段/分类/写入遵循已有规范，本文不重定义）。
- 写入后按**既有检索质量规范**验证可检索性；后续遇同类任务，按触发意图检索并验证是否命中；未命中按**既有检索缺陷**处理，**不重复造 lesson**。
- **失败分支**：lesson 写入 / 检索验证失败 → 标记「未完成」+ 保留原因 + 留补做动作，**不得口头宣布闭环**。

**红线**：复盘产物必须带「下次怎么避开」；「下次注意点」不算闭环（要落机制/lesson）；写入失败不宣称闭环。

## 三、新框审视（缺口 14）

**目标**：治理文档更新后，以**冷启动视角**验证规则能被正确执行，防规范漂移。

**触发**：
- 新增治理规范，或修改规范含义/触发条件/权责/权威路径 → **完整审视**。
- 仅排版、拼写且不改变含义 → **轻量检查**。
- 表面是文字修改、实际影响规则解释 → 按**完整审视**处理。

**标准动作**：
1. **冷启动阅读**：不使用对话历史/隐含记忆补全规则；先仅凭当前文档判断能否识别触发条件、第一步动作、权威路径、完成标准。
2. **依赖核验**：文档明确引用其他规范/工具时，打开对应来源核实；**禁止凭记忆补写依赖内容**。
3. **三查（验收标准）**：

   | 检查项 | 通过标准 |
   |---|---|
   | 自洽 | 无未解决规则冲突；冲突有明确优先级或权威来源 |
   | 唯一路径 | 同类资产能定位唯一权威位置；索引、候选、历史记录不冒充真相源 |
   | 可执行 | 触发条件、第一步动作、落点、完成标准、失败处理均明确 |

4. **双方复核**：哥哥先自读 → GPT 独立补查 → 记录发现问题、采纳/不采纳及理由、修改后验证结果。发现实质缺口 → 修复后重审受影响部分；纯格式 typo → 轻量检查。
5. **留痕**：本次审视结果写入维护记录；无法完成审视/验证 → 明确标记未完成及原因。

**红线**：完整审视未完成，不得宣称治理文档更新验收完成；审视意见不等于执行授权——需改变系统行为/权限/数据结构/长期工作流的，继续走既有讨论与决策机制。
