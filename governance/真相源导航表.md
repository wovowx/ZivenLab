### 已明确的职责边界与重复信息治理

- **目标 vs 现状**：`整体架构.md` 讲目标；`现状架构.md` 讲当前已核实的实现；`架构差距矩阵.md` 记录两者差距与验收，不互相替代。
- **需求 vs 规则**：`治理与记忆_最终需求.md` 讲需求和验收意图；`policy-index.md` 负责规范索引；具体协议/Skill 承载规则原文，真实运行效果仍由代码和测试证明。
- **索引 vs 事实**：`README.md` 是轻量入口；本表是详细导航；`资产全景.md` 是资产索引；源码、实时 Schema、注册表和测试才是实现事实证据。
- **路线 vs 状态 vs 历史**：`roadmap.md` 只决定行动顺序；云端 `⚙️/当前工作检查点` 保存唯一当前工作状态；驾驶舱做治理摘要；CHANGELOG 记录变更历史。旧路线与旧交接不自动重新激活。
- **旧阶段编号隔离**：本次整体架构升级统一采用 `roadmap.md` 的六阶段编号；`资产盘点与整理升级计划.md` 原有阶段 0–4 仅指旧的资产整理子流程，不与全局阶段混用。
- **重复实现处理**：阶段 3 已核对主要静态调用链与实时注册表；动态引用、外部兼容契约和逐项 endpoint 行为仍有缺口。阶段 4 决定是否包装/收敛前，必须先完成这些待核项。既有 `buildErrorResponse` 重复导出已在 v6.35.0 收敛；`data.js` 复用 `memory_unified.js` 的读写函数，而 `category.js` 自建 CRUD。此静态事实足以登记职责重叠，不足以直接删除旧 handler。

## 三、按事实类别确定权威来源

| 事实类别 | 唯一权威来源 | 其他位置的职责 |
|---|---|---|
| 系统目标架构与治理规则 | ZivenLab 对应治理文档 | 组件文档引用；运行时是否生效另需验证 |
| 系统当前实现地图与跨仓库差距 | ZivenLab `governance/现状架构.md`、`架构差距矩阵.md`（汇总层） | 作为索引/总结；不得覆盖组件证据 |

| 数据库实际结构 | 当前目标环境的实时 Schema | GitHub 文档记录语义、规范和变更历史 |
| 身份与长期不可变约束 | 云端 `🧬/我是谁` | 角色卡是宿主投影 |

| 文档定位 | 本导航表 | 只负责指路，不创造或覆盖事实 |

**生效状态必须分开标注**：已定义（权威文档存在）≠ 已接入（有真实加载/调用路径）≠ 已验证（有可复核测试证据）。不得把文档写好表述成运行时已生效。
