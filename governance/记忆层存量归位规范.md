## 一、设计目标与核心决策

目标不是把记忆拆成四套存储，而是让同一份权威记忆在不同场景下以不同方式被加载、检索、学习和追溯，同时避免重复正文、相互覆盖和历史污染。

**已确认的架构决策：四层是逻辑视图/工作流/历史策略，不是四套物理存储，也不是互斥的单字段。**

- Long-term 是权威记忆主体；Core 是从中精选的启动视图；Reflection 是候选学习工作流；Archive 是历史记录与来源的按需检索视图。
- 一条权威正文只保留一份。Core、Archive 通过 ID/key/source 引用权威记录；Reflection 候选引用来源，不覆盖来源。
- 一条长期记忆可以同时被 Core 引用；记录失效或被替代后可从 Core 撤下，并由 Archive 以历史身份呈现。
- 不增加 layer 字段、不新建 layer-membership 表、不批量搬迁现有记忆。只有实际使用证明现有引用方式无法管理时，才另行设计最小关系机制。

## 二、六个正交维度

| 维度 | 解决的问题 | 当前/目标载体 | 不可混淆之处 |
|---|---|---|---|
| Category | 内容属于哪个领域 | memories.category、key 前缀 | 不是保存层级；📦 不自动等于 Archive |
| Type | 内容是什么性质 | memories.type：fact / quote / inference / agreement | 不是验证状态，也不决定是否常驻 |
| Layer | 如何保存、加载、检索和维护 | 本文定义的四种逻辑视图 | 不判断真假，不强制单值 |
| Validity | 内容在当前时间是否仍成立 | status、valid_from、valid_to、版本因果 | 当前有效不等于内容已被证明真实 |
| Maturity | 反思候选是否验证 | Reflection 候选的状态标记 | 只作用于候选流程，不是当前 memories 的新列 |
| Provenance | 内容来自哪里、凭什么 | source_ref、原话/对话归档、文档/Commit/测试证据 | 不能由模型补造来源 |

### 2.1 Type 目标语义（L1 已按 §2.4 在 dev 实施；以下保留原型制定依据）

- `fact`：有可说明来源的事实、记录或已验证技术结论。
- `quote`：保留说话者原意与原文，不把转述伪装成原话。
- `inference`：模型或 Agent 的推断、假设、未验证判断；必须标注依据和不确定性。
- `agreement`：柳柳明确确认的约定、规则或偏好；不能仅因模型觉得合理就标为 agreement。

**建议目标：不按 Category 前缀推导 Type，也不把无法判断的内容默认写成 agreement。** 模型判断未验证时优先作为 inference/Reflection 候选；无法可靠分类时暂缓写入权威长期记忆。该规则是 L1 的行为设计建议，不是本次已获批的运行时变更；需在 L1 原型中向柳柳展示参数/写入/展示合同并验收后才能实施。当前 Skill/运行时未同步，本次也不批量重标历史记录。

### 2.3 L1 Type 写入链原型 v0.1（已验收并在 dev 实施；原型历史正文保留）

本节是进入编码前的可验收原型，不代表已经修改 Worker、Skill、注册表或真实记忆。

#### 2.3.1 Type 语义与写入规则

- `fact`：有可说明来源的事实、记录或已验证结论。
- `quote`：保留说话者原话；转述不得标成 quote。
- `inference`：模型/Agent 的推断或未验证判断；必须在正文中标明依据与不确定性，不得作为 fact/agreement 使用。需要验证的临时假设在 Reflection 工作流落地前不写成长期事实。
- `agreement`：柳柳明确确认的规则、决定或偏好；模型自行推断“应该如此”不构成 agreement。
- 新版 Memory Management Skill 对新写入应先分类，能可靠分类时通过独立 `type` 参数传递；无法可靠分类时不把它伪装成 fact/agreement，也不默认 agreement。为兼容旧宿主，运行时参数保持 optional；旧调用未传 type 时允许存为 SQL NULL，展示为“未标注”，不做历史回填。

#### 2.3.2 对外参数 Schema（建议）

`memory` 工具增加一个可选顶层参数：

```json
{
  "type": "string",
  "enum": ["fact", "quote", "inference", "agreement"],
  "description": "记忆性质；fact=有来源事实，quote=原话，inference=明确标注的未验证推断，agreement=柳柳明确确认的约定。省略表示未标注，不自动推断。"
}
```

- 不加入 `required`，保留旧宿主/旧调用兼容；既有 `action` 仍是唯一必需参数。
- 由 `mcp_router.js` 提供一个共享的 Memory Schema augmentation helper，并同时用于 `getExposedInputSchema`（tools/list 对外展示）与 `getToolSchema`（dispatchGuard 校验），保证“客户端看到的 Schema”和“服务端实际校验的 Schema”一致。
- 该扩展随 Worker 代码版本管理，不写 Supabase `skills.input_schema`，不改注册表，不新增 DB 字段/表。理由：`memory` 是 Worker 内置核心 handler；用同一代码 helper 在暴露与校验两处扩展，避免生产 DB 注册表先变、Worker handler 尚未支持的半发布状态。
- 当前对话中已缓存的 GPT 工具参数定义不会被本次文档改变；新 Schema 生效后需由宿主重新发现/刷新工具定义。Operit 是否使用同一动态发现链，仍以其实际刷新后的工具清单为准。

#### 2.3.3 remember / update 行为合同

| 场景 | 调用 | 预期持久化行为 |
|---|---|---|
| 新建且分类明确 | `remember(..., type='quote')` | `memories.type='quote'` |
| 旧宿主新建未传 type | `remember(...)` | type 保持 NULL，不默认 fact/agreement |
| 更新正文但不改性质 | `update(...)` | 保留 existing.type；不因省略参数清空 |
| 明确修正性质 | `update(..., type='agreement')` | 更新正文与 type；不传 type 不改变现有性质 |
| 非法枚举 | `type='opinion'` | Router Schema 校验拒绝；不得触发 memories/events 写入 |
| 无法可靠分类的新候选 | 不调用长期记忆 remember | 等 Reflection 工作流可用，或保留在当前任务，不伪装成已验证事实 |

- remember handler 仅在 `safeArgs.type` 存在时将其传给 `putMemory`。
- update handler 不再把 existing 整行作为“新输入”来猜测用户意图；只传正文与时间，只有调用方显式提供 `safeArgs.type` 才附加 type。Lifecycle update 只在 data 明确含 type 时 PATCH type；省略则保留原值。
- Router 按 enum 校验；handler 对直接调用路径做轻量 allow-list 校验。内部 rename/move/import 对历史 NULL type 保持兼容，不把 NULL 当非法值。
- 不提供 `type=null` 清除操作；清空/降级性质若未来确有需求，另立语义，不用 null 混淆“未提供”与“明确清除”。

#### 2.3.4 生命周期与事件快照

- 新建记录仅在收到有效 type 时写入；未收到时沿用数据库 nullable 列的 NULL。
- 更新若显式修改 type，事件快照建议使用现有 JSONB 列：`old_value={value, type}`、`new_value={value, type}`；旧事件中 string/null 形态继续兼容。
- History renderer 兼容旧 string 与新 object 快照，显示旧值、新值及对应 type；不把缺失的历史事件补造出来。
- 当前 lifecycle 是“先 INSERT event、再 PATCH memory”的两步请求，不是事务/CAS。L1 不宣称修复原子性；若 PATCH 在 event 成功后失败，仍可能留下未完成的事件意图。这是已知 L6 生命周期一致性差距，后续若功能依赖可靠自动迁移再单独解决。

#### 2.3.5 查询展示合同

- Search 不再用 `i.type || 'fact'`；合法类型显示自身值，NULL/空值显示 `未标注`，未知历史值显示为显式未知值，不伪装成 fact。
- Recall 增加性质行，明确展示 `fact/quote/inference/agreement/未标注`。
- History 同时兼容旧事件格式和新结构化快照；普通 current-only 检索、四态状态、别名、一跳关联、match_reason 与排序均不改变。
- 不对现有 NULL/旧类型进行自动回填、重分类或批量修改。

#### 2.3.6 Memory Management Skill 与宿主兼容

- 移除“在 value 内标注 type”和“无法判断默认 agreement”；改为调用 memory 时传顶层 `type`。
- 说明四类定义、agreement 必须有柳柳明确确认、quote 必须保留原话、inference 必须显式标注不确定性。
- 新 Skill 对新写入尽量显式传 type；旧客户端未传时继续兼容并显示未标注。
- Worker text Skill loader 固定从 GitHub main 取文件；因此 dev 内的 Skill 文件修改只作为候选，不能声称已被当前 Worker 加载。代码与 Skill 应在取得独立发布批准后同一发布切片进入 main，避免 Skill/handler 不匹配。

#### 2.3.7 合同测试矩阵与验收

1. Router：tools/list 对 memory 暴露 optional enum；dispatchGuard 对四个合法值放行、非法值拒绝；tools/list 仍无 skills/usage/business 写入。
2. Handler/Lifecycle：typed remember 落库；untyped remember 保持 NULL；update 省略 type 保留旧值；显式 update 改变 type；rename/move/import 对 NULL 与合法类型兼容。

## 三、四层定义、准入与退出

### 3.1 Core · 核心常驻视图

**职责：** 在新会话/新宿主启动时，恢复身份、关系、全局协作约定和当前工作位置所必需的最小上下文。

初始核心范围（已与 mcp-memory/dev 的 `BOOTSTRAP_KEYS` 静态核对）：
- 身份根 `🧬/我是谁`。
- 柳柳主档 `💕/关于柳柳`。
- 恢复协议 `⚙️/恢复协议·Session Bootstrap SB-1.0`。
- 权威导航记录 `记忆位置导航（换框/换设备自举·2026-10-18）`。
- 唯一动态工作指针 `⚙️/当前工作检查点`。

Core 分成两个子视图：
1. **Stable Core**：身份根、关系主档、跨任务协作铁律等稳定内容。
2. **Operational Core**：当前工作检查点、当前任务授权与恢复协议等会变化但启动必需的操作指针。

准入必须同时满足：
- 跨会话/跨宿主持续有效；
- 缺失会显著影响身份、关系、关键行为或工作连续性；
- 已由柳柳明确确认，或有充分、可复核的事实依据；
- 确实需要启动时读取，而非仅仅“很重要”；
- 可以用简短摘要/引用表达，不把完整长期记忆库塞进上下文。

禁止进入：
- 未验证推断、临时任务细节、单次对话碎片、重复副本；
- 仅因最近使用频繁、模型评分高或模型主观认为重要而自动置顶。

退出/降级：
- 被明确纠正、替代、撤销或不再需要启动时读取时，从 Core 视图撤下；
- 原记录与证据保留在 Long-term/Archive，不因撤下而删除；
- 当前检查点更新必须继续使用同一 canonical key 的最新覆盖，不另造平行检查点。

初始实现边界：
- 先复用 SB-1.0 已有的精确来源清单，不增加表或字段。
- 当前 Session Bootstrap 的 READY 只证明来源读取/结构检查达到契约，不代表完整身份根/主档正文已自动装入每个宿主上下文。全文装载和宿主首轮行为必须单独验收。
- 如未来需要动态 pin 更多 Core 记忆，先做一个只存 ID/key 引用的最小清单原型；不复制正文。是否需要独立清单记录，留到 Core 实施切片验证后决定。

**预算与截断**：
- 初始核心内容总预算建议 24000 Unicode code points，不冒充 token 数；具体宿主可容纳性须实测。固定来源/有界诊断控制元数据增长，最终序列化响应大小另有测试记录。

### 3.2 Long-term · 长期记忆主体

**职责：** 保存经确认、具备长期价值或可复用价值的权威记忆正文，作为默认按需检索的知识主体。

准入：
- 柳柳明确要求记住的偏好、原话、约定或重要经历；
- 有可靠来源的事实、项目决策、配置结论；
- 已通过证据验证的经验与教训；
- 可以保留为 inference 的有价值判断，但必须明确标记推断，不得伪装为 fact/agreement。

不准入：
- 尚无证据的模型猜测（先进入 Reflection）；
- 临时执行中间态、无长期价值的重复片段；
- 已在权威归档位置完整保存、且没有必要再复制的原始全文。

检索与退出：
- 默认按任务情境按需召回，不把全部 Long-term 内容注入启动上下文。
- 当前默认读取继续遵循 `status='active' AND valid_to IS NULL`；检索可靠性四态 OK/EMPTY/PARTIAL/ERROR 必须保留。
- 事实被纠正、替代、撤销或过期时，按明确生命周期语义处理；历史证据保留，不因长期未使用就自动失效或删除。
- Long-term 是权威正文主体，不表示其中每条记录永远有效；Validity 独立判定当前状态。

### 3.3 Reflection · 反思与候选学习工作流

**职责：** 从失败、重复纠正、测试结果、用户反馈和外部研究中提出可验证的候选认识，避免把即时感想直接写成事实。

标准流程：

经历/来源 → 候选观察 → 假设 → 证据验证 → validated / rejected / deferred → 晋升到 Memory / Skill / Workflow，或保留来源后归档。

候选最小信息：
- candidate_id 或可追溯标题；
- hypothesis（必须标为推断/待验证）；
- source_refs（原始对话、代码、测试、Commit、外部链接）；
- evidence（支持/反驳证据）；
- validation_state：pending / validated / rejected / deferred；
- target：memory / skill / workflow / none；
- decision_reason（晋升、驳回或暂缓的原因）。

准入：
- 失败或回归、柳柳纠正、重复出现的工作模式、已验证前后的差异、值得验证的外部技术方案。

退出：
- validated：只提炼真正成立的结论进入 Long-term；可执行步骤进入 Skill；回归工件留在 tests/learning。
- rejected：保留必要来源与驳回原因，不晋升为当前事实。
- deferred：保留候选状态，等待新证据；不得当作已确认决策。
- 候选内容不需要为了“占一层”而写入 memories；优先复用现有 lesson / learning artifacts / 治理文档，不新建数据库表。

#### 3.3.1 L3 Reflection v0.1 · 已验收的施工原型（保留原提案文本作为设计依据）

**使用场景**：柳柳指出哥哥一次错误、某次回归失败，或 Technology Scout 发现值得借鉴的做法。系统先产生**候选假设**，保留完整来源与反证；验证之前不升级为当前事实、长期约定或可执行 Skill。本节记录实施前的候选方案；其后已获柳柳同意并在 dev 完成最小实现，具体证据见 §3.3.2。

**存量对照与技术判断（2026-11-06 只读）**：
- `tests/learning/run_learning_tests.py` 目前校验工件必填字段、test_id/状态/非空检查等**结构**，不是对 Agent 下一次行为的端到端检验；`tests/learning/*.json` 已有 `status=candidate` 与现役 lesson 工件、CI `learning-regression.yml`，不能把结构 PASS 说成「哥哥已学会」。
- 原先可以新建 `reflection_candidates` 数据表或再造独立记忆系统；但这会增加同步/迁移成本且违反单一正文原则。本原型优先复用现有学习工件，暂不引入数据库表、外部运行时或新的 MCP 工具。
- 借鉴 [Reflexion](https://arxiv.org/abs/2303.11366) 的「反馈→反思→后续尝试」循环，以及 [LangMem](https://langchain-ai.github.io/langmem/) 对事实/经历/操作规则的职责区分；**不直接复制**它们的存储或后台自动写入架构。

**候选数据形状（JSON 原型；非生产 Schema）**：
```json
{
  "test_id": "learning_example_feedback_001",
  "status": "candidate",
  "lesson_key": "PROPOSED:lesson-example-feedback",
  "reflection": {
    "candidate_id": "feedback-001",
    "hypothesis": "当用户要求记住规则时，回复已存档前必须有真实写入证据",
    "source_refs": ["user_feedback:example", "tool_trace:example"],
    "evidence_for": ["示例：曾出现语言承诺但没有对应记忆工具调用"],
    "evidence_against": [],
    "validation_state": "pending",
    "target": "skill",
    "decision_reason": "待检查写入证据与同类反例"
  }
}
```
这个片段只展示新增的 `reflection` 语义；真正 `tests/learning` 工件仍需保留现有 `name/trigger/checks/blocked_actions/verification` 等必填字段。示例来源是**合成占位符**，不能当真实证据。既有 `status` 是回归工件生命周期；新增 `validation_state` 是反思假设成熟度，两者不得相互替代。

**推荐实现边界（待确认）**：
1. 采用同一 `tests/learning/*.json` 工件、可选 `reflection` 字段与既有 `candidate` status；**不新建并行候选仓库**。新候选只写开发分支中的工件，不直接写权威 `memories`。
2. 独立的纯函数负责 `validateCandidate`、`decideCandidate`、`previewPromotion`；场景工作流负责收集来源/对照反证/产出候选，永不把 pending 隐式变为 validated。暂不暴露新 MCP facade，避免 v0.1 扩散宿主 Schema。
3. `pending → validated / rejected / deferred`；deferred 获得新来源可回 pending；validated 必须有可追溯测试/事实证据与决定原因。**validated 只生成晋升预览**，实际写入 Memory/Skill/Workflow 仍需各自的权限、用户验收及现有发布流程；rejected/deferred 不晋升。
4. 在现有 learning runner 外增加真正的**合成行为合同**：缺失来源拒绝验证；有反证必须记录；pending/rejected/deferred 不晋升；validated 只有预览不写库；重复候选 ID 不重复晋升；旧 `tests/learning` 合同不退化。模拟操作与日志应断言零真实网络写入。
5. 回归合同 E1/E2 通过不等于真实 Agent 已改变行为。以后发生相同触发条件时，仍须以可核查的实际工具调用/行为轨迹验证，再认定「学会了」；若 GPT 宿主被安全拦截，E3 标 BLOCKED/NOT VERIFIED 而非 PASS。

### 3.4 Archive · 历史归档视图

**职责：** 保留被替代、过期、撤销、暂停或具有历史价值的记录，使其可追溯但默认不污染当前判断。

纳入：
- 被新事实/新约定替代的旧版本；
- 已撤销、已过期、已暂停方向的历史资料；
- 原始对话归档、历史决策依据、失败记录；
- 被驳回但值得复盘的 Reflection 候选。

检索：
- 默认不进入普通当前记忆召回和启动上下文。
- 仅在明确历史意图（例如“以前怎么说的”“当时为什么这样决定”“旧方案发生了什么”）时主动检索。
- 返回时必须标注历史时间、来源、当时状态；不得与当前有效记录混为一条。
- 当前 Worker 的 history action 主要按精确 key 回看记录/events；它不等于已具备完整、通用的 Archive 全文搜索。
- memory_events 生命周期事件尚不完整，因此 Archive 可追溯性有缺口；不得补造缺失事件。

退出/恢复：
- 归档内容只有经过重新核验并有明确恢复依据，才能重新成为当前 Long-term 记录；不能仅因被再次搜索到就自动恢复。
- Archive 不等于物理删除；不等于某个 Category 名称；不等于 status 的某一个未经核实的枚举值。

### 3.4.1 L4 Archive v0.1 · 已验收 A 方案施工原型（dev-only）

- `src/modules/mcp_router.js` 的 `tools/list` 将动态工具映射为 `{name,description,inputSchema}`；补入的静态 `session_context`/`session_bootstrap` 也只含这几个字段，**当前未对外提供 MCP `annotations`**。按 MCP ToolAnnotations 默认 `readOnlyHint=false`、`destructiveHint=true`、`openWorldHint=true`；只是风险默认值，并非官方已认定 Ziven 危险。参考 https://modelcontextprotocol.io/specification/2025-06-18/server/tools 和 https://developers.openai.com/plugins/build/mcp-server。
- `memory` 是单一混合读写 Facade：`recall/search/history` 与 `remember/update/forget` 共用同一个工具描述与安全标注。不能对整个 `memory` 标 `readOnlyHint:true`，因为写/删确实可能发生；工具标注在**Tool 级**，不能按 `action=history` 自动切换。
- `src/modules/mcp_router.js:autoIncrementUsage` 对正常 `memory` 成功调用会更新技能 usage；即使 `getMemoryHistoryByKey` 仓储层只有 GET，**完整 MCP memory(history) 调用也不保证绝对零数据库状态变化**。`session_context` 和 `session_bootstrap` 被该 usage 函数显式排除，属于更合适的只读标注候选（以实际调用链再次核实为前提）。
- `getMemoryHistoryByKey` 查询整条历史与 memory_events.old_value/new_value；`include_core=true` 从五份权威记录返回较完整的私人正文，风险范围比普通摘要/当前 recall 广。**这只是功能数据范围差异，不证明内容泄露、恶意意图或模型安全分类具体规则。**
- `history` 和 `recall` 共用同一 Tool 级 annotations/描述，仍出现不同结果：**缺失 annotations 是一个真实的契约缺口，却不能单独解释这次按 action 分化的拦截**。应同时考虑平台按参数语义/上下文做风险判定以及已公开确认的只读误拦截。

**外部官方证据**：OpenAI 官方 https://developers.openai.com/plugins/plan/tools 要求 readOnlyHint 按工具实际状态变更性质标注；OpenAI Support 在 2026-08-05 与 2026-08-16 的 https://community.openai.com/t/chatgpt-app-mcp-tool-calls-blocked-by-openai-safety-checks-before-reaching-mcp-server/1386059 承认部分合法只读操作被误拦截、改进后仍可能发生；官方建议带失败时间、连接器和是否到达 MCP server 的日志向 Support 报告。这些外部案例只能证明**可能发生**，不是本项目的直接定因证据。

**下一步不写代码的验证（P0）**：
1. 必须使用 **Cloudflare Workers 请求执行日志/Live Logs**（不是 deploy/build logs）+ 同时间成功的合成 recall 控制请求，确认日志采集确实正常。被挡的 history 调用如果没有请求日志，只能描述「在有效采样范围内未观察到」，再结合调用 Trace/官方支持确认宿主前置拦截。
2. 对照 ChatGPT 发送的工具名、原始 action、参数 JSON 和当前 tools/list 公开注解/Schema（注意脱敏），若服务器收到请求而返回 `DISPATCH_GUARD_REJECT` 或 REST 错误，才进入 Worker 层修复；如果没有进入 Worker，则不再以改 Supabase/业务查询作为首选。
3. 收集同一对照组 `recall` 成功/`history` 被拦的时间戳、会话请求标识（仅在用户允许且平台可见范围内）、Worker 日志覆盖范围；不能把 `DEPLOY_VERIFIED` 误当 `REQUEST_RECEIVED`。

**架构候选，尚未确认**：
- A（最低改动）：补全**确实纯读取工具**的准确 annotations 与数据范围文案；保留现有 `memory` 混合属性，不能把它误标只读。优点无新 Facade；缺点 `history` 仍混用读写工具，可能继续触发不透明的平台判定。
- B（更清晰的能力边界）：在已有 history primitive 上新增**仅按完整 key 读取、无写入/无 usage 更新副作用**的单一只读场景入口（如 `memory_history_read`），正确标注 `readOnlyHint:true`、`destructiveHint:false`、闭域时 `openWorldHint:false`；保持 `memory(history)` 兼容但不在新场景中优先使用。它是实际最小权限能力分离，**不是改名来躲过平台安全检查**。新增一个工具、宿主刷新及发布 E3 仍需柳柳单独批准；成功也不能保证。
- **推荐顺序**：先拿请求级证据再决定 A/B（倾向若需改造选 B 的真实只读分离）；未经柳柳确认不改变工具 Schema、usage 规则、生产代码、main、密钥、数据库或部署。不重复试探已被平台拒绝的工具调用；如平台拒绝持续，尊重拦截并报官方支持。L5 轻量原型保留，不把这次诊断变成全仓安全审计。

## 四、视图关系与生命周期

四层关系可概括为：Canonical Memory/Source 是唯一权威正文；Core、Long-term、Archive 是引用或检索视图；Reflection Candidate 引用来源，并在验证后才晋升为新结论/Skill/Workflow。

关键规则：
1. Core 是 Long-term 权威记录的精选引用视图，不复制正文。
2. 同一条记录可同时被 Core 与 Long-term 使用。
3. 旧版本仍保留原始 ID 与来源；Archive 以历史视图呈现，不覆盖新版本。
4. Reflection 是候选流程，不是当前事实存储层；它引用来源而不是改写来源。
5. `related_memory_ids` 表示语义关联，`trigger_intents/entities` 表示情境/实体触发；都不能用来表达 Layer membership。
6. Category 与 Layer 完全正交。例如 `📦/巡检自续规则` 若仍有效且启动必需，可以被 Core 引用；`📦/历史归档` 是一个主题分类，也不能代替历史有效性判断。

### 8.1 L5 v0.1 · 记忆存量映射器最小原型（方案 A 已验收，dev 合成实施获准）

**要解决的问题**：哥哥已能将记忆按 Core / Long-term / Reflection / Archive 的职责处理，但旧存量中哪些记录适合被哪个视图引用、哪些来源不明、哪些可能重复还没有可靠的**解释性盘点**。L5 不整理/搬迁旧记忆，而是先产出「有哪些、建议怎么看、凭什么、哪里不确定」的只读映射。

**存量与约束（经 v6.45.0 源码核对）**：
- `getCurrentMemories` 只返回 `status=active AND valid_to IS NULL`；适合验证当前有效性，但不能声称覆盖软删除/过期历史。旧 `getAllMemories` 也有 `status=active` 过滤，且读取失败时可能返回空数组，因此不能拿它当全库盘点或把 0 条当真零。
- `getMemoryHistoryByKey` 能按**精确 key**回看不活跃版本/事件，不是全库分页索引。若未来需真实全量盘点，应另行限定只读 metadata SELECT 与分页/计数/失败四态，不能偷用 current-only 的结果冒充全存量。
- 当前已有的六维 Category / Type / Layer / Validity / Maturity / Provenance 必须分别描述。`type=agreement` 不自动进 Core；分类前缀 `📦` 不自动等于 Archive；活跃记录即使有历史事件，也不代表当前版本失效；`Reflection` 候选来自 learning 工件，不应把任意 memories row 推测为反思。

**原型流程**：`Synthetic fixtures → 只读标准化 → 规则判定（输出理由和疑点）→ 人类可审核映射报告 → 柳柳确认后才考虑极小范围真实 metadata-only 预览`。首版只做**纯函数 + 合成 E1/E2**；不暴露新 MCP 工具、不读取用户私人正文、不改数据库。是否执行真实 metadata-only 读取、覆盖哪些 key/Category、输出物应如何保管，仍单独征求柳柳同意。

**单条产物（合成 JSON 示意，不是实际用户数据）**：
```json
{
  "record_id": "synthetic-001",
  "key": "⚙️/示例规则",
  "category": "⚙️",
  "type": "agreement",
  "validity": { "status": "active", "valid_to": null },
  "suggested_views": ["Long-term"],
  "core_inclusion": "not_in_core_5_keys",
  "evidence_refs": ["synthetic:input-row"],
  "reasons": ["current_active_record", "not_a_bootstrap_core_key"],
  "uncertainties": ["agreement_confirmation_source_unverified"],
  "recommendation": "review_only",
  "writes_executed": false
}
```

**判定边界**：
1. `status=active && valid_to==null` 的已知记录可提出 Long-term 当前有效**候选引用**；它不说明内容真实、也不证明 agreement 有过柳柳确认。
2. Core 默认**仅精确 5 个 BOOTSTRAP_KEYS**（身份根/柳柳主档/导航/工作检查点/恢复协议）且仍须当前有效+原文可读；缺正文完整性时 `UNCERTAIN` 而非直接纳入。其它键不根据关键词自动晋升 Core；未来扩展须另定需求。
3. 非当前记录（deleted/expired 或 valid_to 已设置）建议 `Archive` **历史视图**，但保留其真实性/原类型，不作物理移动或 category 改写；已启用的旧记录可以有 Archive 事件引用，同时仍 Long-term 当前有效。
4. Reflection 的 `pending/validated/rejected/deferred` 只针对 learning 候选，不把 Memory `type` 或 Key 直接改作 Reflection 状态。
5. `status/type/key/category/provenance` 缺失或互相矛盾时，列在 `uncertainties` 和 `UNCLASSIFIED`，不用模型猜，也不替用户补写 source_ref；不同记录有相同 key 或内容相似，只报告可能重复，**不自动删除/合并**。

**验收场景**：五个核心键 vs 普通 key；active/current vs retired/expired；`📦` 活跃并不自动 Archive；缺 type/source、冲突状态、重复 key 不造事实；反思候选不污染长期记忆；合成 E1/E2 零网络写/零注册表变更；旧 recall/history/Session E1/E2 不退化；真实存量覆盖率不经实际只读采样不得声称。
